Part of the stability epic (`STAB0`). Moved here from T254 on 2026-11-27: parts T164, T160 and T82 (their text below, as it
was). It is PR B of T254's plan (2026-11-24); the design is restated so that this item stands alone. T160's kernel half is done
(T177/KT9: `thread_spawn` and `process_start` reply NO_MEMORY); its test is not. T82's two proposed fixes were overtaken by the
spurious-fault retry (T241 part 4), which OD152 (2) accepts as the end state; one residual is left.

**Why it is a stability item.** A thread running on a freed kernel stack, or a stack handed out twice, is the kind of fault that
shows as a rare, unrelated crash elsewhere; today nothing detects it (T164: the faithful control was tried and nothing failed).

## The parts, as they were

### T164: The fault-early-reap control proves a missing record panics, not that a reused stack is caught

*(area testing, horizon near, risk L)*


#### Shortcut

`fault-early-reap` (L11d, PR 264) reaps the exiting thread before its switch, record and stack together; the switch then finds no record and the kernel panics, which `teardown_with_threads_on_other_harts` reports as a crash. The Fable review (2026-11-19) pointed out a faithful control frees only the stack and keeps the record: that was tried, and nothing detects it, because a freed `KStack` is neither unmapped nor poisoned, so the thread simply goes on running on memory that is still intact.

#### Why acceptable

The record-removal variant still shows the harness detects a premature reap; the real protection is the big lock (T163) until L12.

#### Proper fix, and when

A debug feature of `KStack`: poison a stack on free (and fill the guard), so a thread still running on a freed stack, or a stack handed out again while in use, fails the guard check ("stack of thread ... was overwritten") the way SCHED-SMP-SPEC 3.6 expects. Then make `fault-early-reap` free only the stack. With L12.


### T160: Thread creation panics when the kernel is out of frames for a kernel stack

*(area kernel, horizon long, risk H)*


**What:** `new_kthread` in `kernel/src/thread.rs` ends in `expect("memory for a kernel stack")`. A user program that starts threads until the frame pool is empty reaches it.

**Why acceptable for now:** found by the KT3 review (2026-11-18); thread counts are bounded by the job limits, and the suite does not drain frames.

**Risk:** H. A user-controlled path to a kernel panic.

**Proper fix:** `new_kthread` returns an error, `thread_spawn` and the process start path reply `NoMemory`, and a test exhausts frames with a job-less process. Tied to KT8 (the assert and allocation blind spots).


### T82: New kernel pages (heap, stacks) assume a local-only `sfence.vma`

*(area kernel, horizon long, risk L)*


#### Shortcut

**New kernel pages (heap, stacks) assume a local-only `sfence.vma`** (Fable review): growth and stack mapping flush on the mapping hart only; correct while an invalid-to-valid change cannot be cached remotely except by speculative walks, which RVA23 (Svvptc) allows to be absent

#### Why it was acceptable

Svvptc in the target profile

#### Proper fix, and when

Assert Svvptc from the profile check, or broadcast a flush on growth

## Stability epic (2026-11-27)

**Scope (one PR, kernel slice).** From T254's plan: (1) `Drop for KStack` fills the stack with a poison word (guard words
included; below `sp` less 512 bytes if the caller runs on it) and records the count with the slot; `kstack::alloc` checks every
poisoned word of a recycled slot and panics naming the slot and word ("kernel stack slot N was written after it was freed"); the
zero fill stays; gate `cfg(any(debug_assertions, feature = "kstack-poison"))`; volatile reads for the poison check and for
`guard_intact` and `stack_used` (T253 item 1 in T256: strike it there). (2) `fault-early-reap` keeps the record and frees only
the stack, then reschedules; the Makefile's control expects the new panic. (3) T160's suite test
`threads_until_the_frames_run_out_get_no_memory`. (4) T82's residual: a lock-free read-only walk of the kernel root before the
`bkl::violates(Class::Vmo)` fatal check in the trap path, so a stale entry met while a memory lock is held is retried, not fatal;
kernel table frames are never freed, which the walk's SAFETY comment states.

**How to investigate.** Watch the control fail first: build `fault-early-reap` as stack-only and boot it once by hand (a targeted
experiment): today the suite passes on it (that is the defect of the control). Count the poison's cost on
`count_thread_create_join` (`bench/counts.tsv`): build the counts kernel without the feature or re-record from the CI log.
**Kani** fits the slot and poison arithmetic (`sp` to slot, the margin, "the poisoned range never covers live frames") and the
lock-free walk over `kcore::pagetable` (bounded tables): recommended if the OD is granted (`STAB0`).

**Acceptance (each run under two hours).** The stack-only control panics with the new message (one boot by hand; the standing
control is tier 2: the owner's); a kernel self-test `a_freed_stack_that_is_written_is_caught` (mutation: delete the fill, the test
fails); the frame-drain suite test passes with no panic and the leak oracle balanced; a host test of the walk against
`PageTable::translate` over random tables. QEMU never caches invalid entries, so the T82 residual is checked on the host only: the
PR says so. Review by Opus (the epic's rule, `STAB0`), Fable only on escalation.
