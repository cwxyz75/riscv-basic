---
id: Q-T42
kind: decision
title: Should the kernel enforce that DMA frames outlive a killed driver (T42)?
area: drivers
horizon: near
---

T42 asks the kernel to enforce what the supervisor does by convention: a DMA VMO's frames must not be freed while a device may still write to them. Enforcing it needs a choice that reverses the S6b decision ("ownership, not a kernel mechanism", `S6-SPEC.md` kill safety) and adds ABI, so it is the owner's.

**Today.** `vmo_create_dma` frames are freed when the last handle to the VMO closes, like any VMO. The supervisor (`devmgr`, `netsup`, the suite's `BlkRig`) keeps its own handle across driver lifetimes and resets the device (`STATUS = 0`) before the buffer goes to the next driver. A supervisor that closes the handle early or dies loses the frames to the device. Safe only because every supervisor is trusted boot code and there is no IOMMU (OD14).

**Options.**

1. **Keep the policy (recommended for now).** Close T42 as accepted for as long as drivers are trusted (OD14). Revisit when an untrusted driver or an IOMMU exists. No kernel change, no new ABI.
2. **Quarantine.** The kernel does not return a DMA VMO's frames to the allocator when it is freed; it parks them until a new call (`dma_release(resource, ...)`, needing MANAGE) says the device was reset. A supervisor that dies leaves the frames parked for good (a bounded leak: `MAX_DMA_TOTAL_PAGES` is 1024 pages), so a restart loop could exhaust the pool unless the supervisor is itself restarted with the same resource. Adds one syscall, a quarantine list under the frame lock order (INVARIANTS), and a Fable review and soak run.
3. **Reset on free.** The kernel remembers which MMIO window a DMA VMO was bound to and writes `STATUS = 0` to it before freeing. Only works for virtio-mmio (the kernel would learn one device class's reset protocol) and needs a bind call as well; it moves driver knowledge into the kernel, which the architecture avoids.

**Recommendation:** 1 now; 2 if drivers ever stop being trusted.

Source: T42.
