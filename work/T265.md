### T227: process_teardown_returns_every_frame lost 91 frames once, in the four-hart suite shard (smoke a), cause unknown

*(area kernel, horizon long, refs [L19, L20])*


At the first epic gate of phase 6f the test reported 91 frames missing after a process teardown, in smoke a only; the next run (after the lock-order fixes in #452 and #453) passed. Not reproduced, not explained. Suspects: heap service or idle growth taking frames between the two reads of the oracle (the read is now repeated until stable), the sliced teardown (L19) or the dead-process cleanup running concurrently, the VMO call split (L20). The failure message prints the four terms (database, caches, stacks, heap) before and after, so the next occurrence says which moved. If it recurs, start from that term; if forty smoke runs pass, close it as a flake of the fixed races.

**Recurred 2026-11-23** (PR 479's smoke a, run 45223872573, 4 harts): `free frames 60011 -> 60010 (database, caches, stacks, heap: (58277, 32, 66, 1636) -> (48217, 100, 8234, 3459))`, one frame short after the 200-tick settle, not 91. The four terms move by -10060, +68, +8168, +1823, which sums to -1, so the frame is not in any one term: one frame is somewhere none of the four counts (in flight in a per-hart cache, or a frame a dying thread holds), or a term is read at a slightly different moment than the free count. Next step: print the per-hart frame-cache fill and the number of threads not yet reaped in the failure message, and keep the check's wait but read both sides under one lock if it can be.

### T238: thread_stacks_are_charged_to_the_job_and_credited_back failed once with NO_MEMORY at "the thread now fits" (two harts, debug)

*(area kernel, horizon long, refs [HD2])*


**What.** Seen once on 2026-11-23 (local k shard at two harts, debug build, while AB9 was being tested): `thread_stacks_are_charged_to_the_job_and_credited_back` failed with `the thread now fits: status -5` (NO_MEMORY): the page limit is `used + 4` after a 4-page stack was mapped and the thread still did not fit. Two reruns of the same shard passed (293 tests).
**Likely cause.** Random placement (HD2): where the child's stack and the arena land decides whether the thread's start needs one more page-table page, which the job is charged and the test's `used + 4` does not allow for.
**Why acceptable.** One occurrence, development only, a test that measures an exact charge.
**Proper fix.** Make the test's room not depend on placement (a limit of `used + 4` plus the page-table pages a thread's stack can add, or run it under `aslr=off`), or read the charge from `job_info` after a first start and set the limit from it. Confirm with `make os-repeat TARGET=os-ktest-small N=20`.

### T209: volmgr_serves_volumes_by_the_table failed once in the phase 8 epic gate (OD140: a defect until its cause is known)

*(area kernel, horizon long, refs [OD140])*

**Proper fix.** Reproduce it from the smoke-a log (the harness prints the volmgr lines around it), find whether the restarted volmgr never published or the open retried against a dead channel, and fix that. **Second occurrence (2026-11-22).** The same test failed the same way (`unexpected status -100 at suite.rs:11217`) in a full local boot of the latency-trace kernel at four harts with `bench=full` (`make os-latency`, the whole suite, 264 user tests passed). It is a different binary and a far heavier run than the gate's smoke a, so the cause is not the gate's load alone; the `open_volume` retry of 15 s ran out both times. That boot's log has the volmgr lines around it.

### T251: smp_churn_stress: a crash-test process ended with 112 (process_map refused) once, in the two-hart ktest boot of the epic smoke

*(area testing, horizon near, refs [T250, T206])*


**What.** Epic smoke run 45479967782 (head 20cb630), `kernel (ktest)`, the two-hart boot: `smp_churn_stress` failed with "churn process 4 ended with 112", which is `process_map(me, vmo, at, 0, 4 pages, 3)` failing in the `crash` program's random loop (`init/src/bin/crash.rs`, case 1: create a 4-page VMO, map it into itself at one of eight slots, touch, unmap). Then find the cause: an overlap with a region still dying (T207's unmap), NO_MEMORY under the 6 concurrent churn processes, or a window effect. If it does not recur in the next smokes, close it with that evidence.

### T226: a_thread_killed_before_it_ran_runs_no_user_code is a race at more than one hart

*(area testing, horizon long, refs [SC2, L20])*


The test makes a thread in a child (`thread_on_stack`, free placement) that would exit(42) at once, and kills the child straight after. On one hart the thread cannot start before the parent's next syscall; on four it can start on another hart as soon as it exists, and it won the race in the first boot of phase 6f (the parent's syscall return became lock-free and the child's start no longer waits for the big lock, which moved the odds). The test now tries up to forty times and requires three runs (or at least one in forty) where the kill came first, and no outcome other than the kill's code or the thread's own. A deterministic version needs the placement masks of SC2 (pin the new thread to the parent's hart, which does not yield until the kill), then this item closes.

### T222: once_and_semaphore failed once in the release ktest (two posts, two taken: got 1)

*(area testing, horizon long, risk L, refs [T167, T178])*


#### Shortcut

`once_and_semaphore` failed once in `kernel (ktest release)` on the epic PR of phase 6d (PR 421, run 45054605311): "two posts, two taken: got 1, want 2", and with it `init_runs_in_user_mode_and_passes`. The re-run of the job passed. The test starts three semaphore sleepers, naps 30 ticks, posts twice and naps 60 ticks, then counts the takers; the semaphore (`rt::sync::Semaphore`) is correct for any order of start and post, so either a sleeper did not run within 90 ticks on a loaded runner (T167: a fresh user thread was seen taking 0.7 to 2.4 s to start) or a futex wake was lost (L14's lock-free `futex_wake`).

#### Why it is open

TESTING.md rule 11: an intermittent kernel-test failure is a defect with a work item, not a re-run.

#### Proper fix, and when

Reproduce under the perturbation run (KT7) and in a loop at `-smp 4` release. If a thread was only late, the test waits for the takers with a deadline (poll `SEM_TAKEN` up to the 5 s the workers allow) instead of a fixed nap, and T167 carries the start latency; if a wake was lost, that is a futex defect and the fix is in `kcore::futex` / `futex_wake`'s quiet path. Do this with the next change to the futex path (phase 6e).

### 2. Design, with what was rejected

1. **T251.** (a) Move every fixed test address out of the arenas the kernel randomises: use `process_map` with ANYWHERE in the churn (unmap by the returned address), or a fixed window below `0x8_0000_0000` that no arena covers (check `abi::user` first). Sweep `init/src/bin/*.rs` for literals in `[MAP_ARENA_BASE, STACK_ARENA_END)` and fix each or justify it in a comment. (b) `smp_churn_stress` finishes all six processes, then reports every non-zero code. (c) If a later occurrence prints 1105: follow hypothesis two (count class-R refusals per boot in the failure message; Q4). Rejected: retrying the map in `crash.rs` (hides a kernel race if there is one); `aslr=off` for the smp tests (removes the placement paths from the stress).
2. **T227.** Make the oracle say where the frame is before changing any kernel path. (a) A **walk oracle**, independent of the formulas: count the frames actually present under the kernel-stack window and the heap window (leaves and tables) by walking the kernel page table, and compare with `kstack::frames_held` and `heap::frames_held`'s grown part; run it once at the frame check and print both in the failure message. (b) An `IN_TRANSIT` atomic around the two in-hand windows of `rebalance_pool`, added as a fifth term (it should read 0 at a quiet time). (c) Print per-hart cache fill, `kstack::LIVE`, threads not yet reaped and `fp::entry_count()` in the message. (d) If the walk disagrees with a formula, fix the path that leaks the table (`make_slot`/`grow` undo, or count tables instead of deriving them): that is the kernel slice, PR B. Rejected: reading all four terms under one lock (the caches belong to no lock; nesting `Kstack`, `Frame`, `Heap` ascending is legal but does not cover the in-hand window, and moving cache-to-pool under `Heap` would take `Frame` after `Heap`, a lock-order violation); a longer wait (a leak does not settle, and the recurrence outlived 200 ticks).
3. **T238.** Freeze the job for the measured window instead of guessing what else can be charged: suspend the child (`process_suspend`, SIG2) after the settle loop, measure, set the limit, create the thread (it is charged at creation; it parks instead of running), resume, then continue. Keep the "at most one page-table page after the refusal" allowance. Add a host property test in `ksys/tests` for the rule itself: `charge_thread` is exactly `KSTACK_PAGES` and one slot, all or nothing, at limits `used+3` and `used+4`, over random prior charges (rule 8: an accounting rule belongs on the host). Rejected: `aslr=off` (boot-wide, hides placement); a slack limit (`used + 4 + n`: then the test no longer checks the exact charge); a first throwaway start to learn the charge (the number learned can still move).
4. **T209.** First read the two logs (the smoke-a log of PR 383's run via `gh run view --log` if still kept; the 2026-11-22 local log is gone unless saved) for the `volmgr:` lines. Then, whichever it was: (a) `volmgr` retries a probe that fails while the device was Busy a moment before, instead of ignoring the device for good; (b) the test's wait covers the server's own budgets (5 s per device plus 15 s, so 30 s; it costs time only when failing) and on failure prints what the registry lists; (c) `volmgr` logs each stage with the clock so the next log is decisive. Rejected: only raising the test's timeout (if the probe was dropped, no timeout helps).
5. **T222.** Workers wait with a deadline far beyond the test's (60 s) and record how they got the permit (`Status::Ok` wake or timeout); the test polls `SEM_TAKEN` with a 10 s deadline per stage instead of napping, fails with "lost wake" if a permit was taken after a timeout, and prints each worker's start time on failure (late start goes to T267/T167, not here). A lost wake, if ever shown, is a kernel futex fix on its own PR (F2). Rejected: the item's "poll up to the 5 s the workers allow" (masks a lost wake, see the trap above).
6. **T226.** Not designed: Q1 decides between a test-only pin, accepting the one-hart determinism, and a user-visible call.

### 5. Invariants, lock classes, and how this goes wrong

| Part | INVARIANTS rows | Lock classes (klock order) |
|---|---|---|
| T227, PR B | H6 (death releases everything), M3 (frame counts conserved), J2 (every charge credited once), K6 (heap grows only at safe points), P2 (kernel top-level slots fixed) | `Kstack` 10, `Frame` 11, `Heap` 12, and `kmem::KPT` (taken before `Frame`, T224); ascending only |
| T251 | M1, M3, J1 (charge all or nothing), the class-R rule of KT9 | `Obj` 1, `As` 2, `Procs` 3, `Vmo` 5, `Jobs` 6 |
| T238 | J1, J2 | `Jobs` 6, `Kstack` 10 |
| T222 | F1, F2 (word read and enqueue in one bucket-lock region), F3 | `Futex` 4, then `Tt` 8, `Rq` 9 for the wake |
| T226 | AF1 (planned row: a pinned record is homed only on its hart) if a pin is used | `Tt` 8, `Rq` 9 |

Ways to get it subtly wrong:

1. The walk oracle takes `KPT` and `Frame` while the caller holds something higher, or runs with interrupts on: call it from the same place and state as `free_frames_accounted` (inside `irq::without`), and take nothing after `Heap`.
2. `IN_TRANSIT` incremented after the pop or decremented before the push reintroduces the window it measures; it must bracket the in-hand frame, and it must be a plain atomic (no lock).
3. Counting page-table frames by walking changes the oracle's meaning for every caller (`selftest.rs`, `smp_tests.rs:776/967`): keep `free_frames_accounted` as it is in PR A and add the walk beside it; switch only in PR B, with the review.
4. T238 with a suspended child: a thread created in a stopped process parks before user code, so `thread_info`/signals read differently from today; the kill at the end must still reap it (EX1's park path). If `process_suspend` itself charges anything, measure after it.
5. T222: a poll deadline at or above the workers' wait deadline hides a lost wake (the trap in section 1).
6. T251: ANYWHERE draws from the entropy pool on every call; 1500 iterations times six processes is fine, but do not use it in a path whose instruction count is in `bench/counts.tsv`.
7. T209: a probe retry must stay bounded (a hostile device costs eight block reads today, FS-SPEC); bound it by the same 5 s.
8. Fixing the cascade in `smp_churn_stress` must not turn a hang into a pass: `user::finish` on a process that never ends blocks for ever; keep the harness timeout as the backstop and say which process.
