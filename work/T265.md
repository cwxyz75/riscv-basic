### T227: process_teardown_returns_every_frame lost 91 frames once, in the four-hart suite shard (smoke a), cause unknown

*(area kernel, horizon long, refs [L19, L20])*


At the first epic gate of phase 6f the test reported 91 frames missing after a process teardown, in smoke a only; the next run (after the lock-order fixes in #452 and #453) passed. Not reproduced, not explained. Suspects: heap service or idle growth taking frames between the two reads of the oracle (the read is now repeated until stable), the sliced teardown (L19) or the dead-process cleanup running concurrently, the VMO call split (L20). The failure message prints the four terms (database, caches, stacks, heap) before and after, so the next occurrence says which moved. If it recurs, start from that term; if forty smoke runs pass, close it as a flake of the fixed races.

**Recurred 2026-11-23** (PR 479's smoke a, run 45223872573, 4 harts): `free frames 60011 -> 60010 (database, caches, stacks, heap: (58277, 32, 66, 1636) -> (48217, 100, 8234, 3459))`, one frame short after the 200-tick settle, not 91. The four terms move by -10060, +68, +8168, +1823, which sums to -1, so the frame is not in any one term: one frame is somewhere none of the four counts (in flight in a per-hart cache, or a frame a dying thread holds), or a term is read at a slightly different moment than the free count. Next step: print the per-hart frame-cache fill and the number of threads not yet reaped in the failure message, and keep the check's wait but read both sides under one lock if it can be.

### T278: Intermittent: three processes and a thread outlived init in smoke a (iommu-kernel epic, run 45913768540)

*(area testing, horizon near, risk M, refs [OD140, OD160, T265, T227, IOMMU6, IOMMU7])*

**Where and when.** The epic smoke of `epic/iommu-kernel` at `abb97a7` (GitHub Actions run 45913768540, 2026-11-26, job
`kernel (smoke a)`, `make os-boot-test-smoke-a`, four harts, QEMU 11.1.3 built from source on the hosted runner). Every user test
passed (`init: 0 of 315 user tests failed`; no `##TEST ... FAIL` line from the suite), init exited 0, and then four of the kernel's
checks after init failed:

```
process_teardown_returns_every_frame FAIL free frames 59108 -> 56403 (database, caches, stacks, heap: (56799, 43, 66, 2199) ->
  (42837, 88, 8225, 5250); a dying VMO still to drain: false; after one more drain: 56403)
no_process_or_vmo_survives_init FAIL 3 processes and 242 VMOs left (wanted 0 and 2), 0 futex sleepers, 0 pager waiters or pagers;
  (jobs, processes, threads) (1, 5, 1, 10, 128, 3288), wanted (1, 0, 0, 0, 0, 0); device domains, I/O-mapped pages, leaked holds
  [0, 0, 0]; vectors live and leaked [0, 0]
no_kernel_thread_survives_init FAIL kernel threads 5 -> 6
process_exit_releases_all_objects FAIL 10 kernel objects left alive after init exited
```

The checks had waited 200 ticks for the processes and 200 more for the frames: about 0.4 s of guest time (a tick is a millisecond)
on a hosted runner at four harts, so a teardown that was only slow is not ruled out. What the numbers say: one user thread is alive
(kernel threads 5 -> 6, and the root job charges one thread), so at least two of the three processes in the table have no thread at
all (never started, or every thread gone); three processes are in the process table but the root job is charged for five, so two
more are between `teardown_take` (out of the table) and the end of `teardown_memory` (where the job is credited), or their credit
was lost; 128 IPC bytes are queued; the IOMMU and vector counters are zero, so no device domain or vector was left. The 2705
frames missing are all in the database term (56799 -> 42837); the growth of the stack and heap terms is pool growth that the
oracle counts as free. A plausible shape (not shown): a live thread of one surviving process is inside a teardown it
started (a `handle_close` or `process_kill` of a never-started process tears it down in the caller, `request_kill`), stuck or very
slow there, with that teardown's victim and a nested one uncredited; candidates for a long stay are the IOMMU drain at the end of
`teardown` (`settle_moves` can retry a route that does not open 4096 times, each bounded by the 100 ms fence bound) and the sliced
handle drain. Which processes they were is not in the log: a process has no name, and the failing check printed only counts.

**What was tried.** Nine local runs of `make os-boot-test-smoke-a` at `abb97a7` (plus the diagnostics below, which change no
behaviour) at four harts with QEMU 11.1.3 (Homebrew, macOS arm64): six one after another on a quiet host, then three at the same
time (host overload). All nine passed the four checks. Two of the three overloaded runs failed one other test,
`a_real_time_thread_stays_responsive_while_hogs_run_and_a_normal_one_does_not` (the host-pause latency of T267/T219). Not
reproduced, so this is rule 11's item. The previous smoke of the epic (run 45906519497 at `84421c9`) did not show it.

**Diagnostics added (the PR that wrote this item).** When `no_process_or_vmo_survives_init` or `no_kernel_thread_survives_init`
fails, the kernel now prints, before the summary:

- `leak: live objects [...]`: every live kernel object by kind, and each process object with its pid and whether it ended;
- `leak: proc <pid>: ...`: every process left: state, detached, privileged, killed and exit codes, stopped, threads alive and their
  ids, its handles by kind (a fingerprint of which program it is), its VMOs, job, object, bootstrap end, exception channel and entry;
- `leak: thread <tid> ...`: every thread that was not there before init started: name, pid, scheduler state, whether it is on a
  hart, its saved return address and the kernel-text words on its stack (`[stack ...]`, link addresses: KASLR's slide is taken off,
  so `python3 scripts/resolve_trace.py <kernel ELF> <addr>...` or `llvm-addr2line -e <kernel ELF>` names where it waits; a thread
  on a hart or in transit is named without its stack; at most 32 threads);
- `leak: <n> ms later: ...`: the check then watches up to 5 s more and prints what is left (processes, threads, ledger, objects,
  free frames), so the next occurrence tells a slow teardown from a stuck one. (The check has failed already on the first counts.)
  `process_exit_releases_all_objects`, if it fails alone, prints the object and process lines too.

**How to reproduce and trace.** `make os-repeat TARGET=os-boot-test-smoke-a N=20` (OD160 permits it), also with two or three boots
at once; the harness prints the serial output of a failing run, and `OS_SHOW=leak:` prints the report lines of a passing one. On the
next occurrence: resolve the `[stack ...]` of the surviving thread; if it is in `teardown`, `iommu::drain` or a settle loop, the
thread is the cause and the fix goes there; if it is in user mode on a hart, a lost kill (the kick IPI) is the suspect; the
`handles` fingerprint names the test whose child it was.

**Closes** only on a named cause or a demonstrated test race (OD160), never on a count of green runs.

### T270: thread_stacks_are_charged_to_the_job_and_credited_back: kill got BadState once in os-latency on a hosted runner

*(area testing, horizon near, refs [T251, T233])*

**What.** Soak re-run of 45526124119 (2026-11-25), job `smp`, `make os-latency` (the latency-trace kernel, four harts): `thread_stacks_are_charged_to_the_job_and_credited_back` failed at its last step, `process_kill(p, 3)` returned `BadState` ("kill: got Some(BadState), want Some(Ok)"). Not reproduced: three local `make os-latency` boots passed that test, and the same boot passed in the first attempt of the soak and in the epic smoke.

**Why acceptable.** One occurrence on a loaded runner. It may be the child ending by itself (the bootstrap wait returned, so `return 9` ended the process), the process being ended by the job, or a kill that raced a thread exit. Which, is unknown.

**Risk.** A wait that returns early on the bootstrap channel, or a kill that sees a live process as ended, would be a kernel fault.

**Proper fix.** On a recurrence, read the failing-boot log: the process's exit code (9 means the wait ended by itself), the thread's signals and `process_info` at the failure. Make the test report them (it reports its detail for the earlier steps, not for the kill). If it never recurs in three soaks, close it as load noise.

### 2. Design, with what was rejected

1. **T251.** (a) Move every fixed test address out of the arenas the kernel randomises: use `process_map` with ANYWHERE in the churn (unmap by the returned address), or a fixed window below `0x8_0000_0000` that no arena covers (check `abi::user` first). Sweep `init/src/bin/*.rs` for literals in `[MAP_ARENA_BASE, STACK_ARENA_END)` and fix each or justify it in a comment. (b) `smp_churn_stress` finishes all six processes, then reports every non-zero code. (c) If a later occurrence prints 1105: follow hypothesis two (count class-R refusals per boot in the failure message; Q4). Rejected: retrying the map in `crash.rs` (hides a kernel race if there is one); `aslr=off` for the smp tests (removes the placement paths from the stress).
2. **T227.** Make the oracle say where the frame is before changing any kernel path. (a) A **walk oracle**, independent of the formulas: count the frames actually present under the kernel-stack window and the heap window (leaves and tables) by walking the kernel page table, and compare with `kstack::frames_held` and `heap::frames_held`'s grown part; run it once at the frame check and print both in the failure message. (b) An `IN_TRANSIT` atomic around the two in-hand windows of `rebalance_pool`, added as a fifth term (it should read 0 at a quiet time). (c) Print per-hart cache fill, `kstack::LIVE`, threads not yet reaped and `fp::entry_count()` in the message. (d) If the walk disagrees with a formula, fix the path that leaks the table (`make_slot`/`grow` undo, or count tables instead of deriving them): that is the kernel slice, PR B. Rejected: reading all four terms under one lock (the caches belong to no lock; nesting `Kstack`, `Frame`, `Heap` ascending is legal but does not cover the in-hand window, and moving cache-to-pool under `Heap` would take `Frame` after `Heap`, a lock-order violation); a longer wait (a leak does not settle, and the recurrence outlived 200 ticks).
3. **T238.** Freeze the job for the measured window instead of guessing what else can be charged: suspend the child (`process_suspend`, SIG2) after the settle loop, measure, set the limit, create the thread (it is charged at creation; it parks instead of running), resume, then continue. Keep the "at most one page-table page after the refusal" allowance. Add a host property test in `ksys/tests` for the rule itself: `charge_thread` is exactly `KSTACK_PAGES` and one slot, all or nothing, at limits `used+3` and `used+4`, over random prior charges (rule 8: an accounting rule belongs on the host). Rejected: `aslr=off` (boot-wide, hides placement); a slack limit (`used + 4 + n`: then the test no longer checks the exact charge); a first throwaway start to learn the charge (the number learned can still move).
4. **T209.** First read the two logs (the smoke-a log of PR 383's run via `gh run view --log` if still kept; the 2026-11-22 local log is gone unless saved) for the `volmgr:` lines. Then, whichever it was: (a) `volmgr` retries a probe that fails while the device was Busy a moment before, instead of ignoring the device for good; (b) the test's wait covers the server's own budgets (5 s per device plus 15 s, so 30 s; it costs time only when failing) and on failure prints what the registry lists; (c) `volmgr` logs each stage with the clock so the next log is decisive. Rejected: only raising the test's timeout (if the probe was dropped, no timeout helps).
5. **T222.** Workers wait with a deadline far beyond the test's (60 s) and record how they got the permit (`Status::Ok` wake or timeout); the test polls `SEM_TAKEN` with a 10 s deadline per stage instead of napping, fails with "lost wake" if a permit was taken after a timeout, and prints each worker's start time on failure (late start goes to T267/T167, not here). A lost wake, if ever shown, is a kernel futex fix on its own PR (F2). Rejected: the item's "poll up to the 5 s the workers allow" (masks a lost wake, see the trap above).
6. **T226.** Not designed: Q1 decides between a test-only pin, accepting the one-hart determinism, and a user-visible call.

### 5. Invariants, lock classes, and how this goes wrong

| Part | INVARIANTS rows | Lock classes (klock order) |
|---|---|---|
| T227, PR B | H6 (death releases everything), M3 (frame counts conserved), J2 (every charge credited once), K6 (heap grows only at safe points), P2 (kernel top-level slots fixed) | `Kstack` 10, `Frame` 11, `Heap` 12, and `kmem::KPT` (taken before `Frame`, T224); ascending only |

| T238 | J1, J2 | `Jobs` 6, `Kstack` 10 |
| T222 | F1, F2 (word read and enqueue in one bucket-lock region), F3 | `Futex` 4, then `Tt` 8, `Rq` 9 for the wake |
| T226 | AF1 (planned row: a pinned record is homed only on its hart) if a pin is used | `Tt` 8, `Rq` 9 |

Ways to get it subtly wrong:

1. The walk oracle takes `KPT` and `Frame` while the caller holds something higher, or runs with interrupts on: call it from the same place and state as `free_frames_accounted` (inside `irq::without`), and take nothing after `Heap`.
2. `IN_TRANSIT` incremented after the pop or decremented before the push reintroduces the window it measures; it must bracket the in-hand frame, and it must be a plain atomic (no lock).
3. Counting page-table frames by walking changes the oracle's meaning for every caller (`selftest.rs`, `smp_tests.rs:776/967`): keep `free_frames_accounted` as it is in PR A and add the walk beside it; switch only in PR B, with the review.
4. T238 with a suspended child: a thread created in a stopped process parks before user code, so `thread_info`/signals read differently from today; the kill at the end must still reap it (EX1's park path). If `process_suspend` itself charges anything, measure after it.
5. T222: a poll deadline at or above the workers' wait deadline hides a lost wake (the trap in section 1).
6. T251: ANYWHERE draws from the entropy pool on every call; 1500 iterations times six processes is fine, but do not use it in a path whose instruction count is in `bench/counts.tsv`.
7. T209: a probe retry must stay bounded (a hostile device costs eight block reads today, FS-SPEC); bound it by the same 5 s.
8. Fixing the cascade in `smp_churn_stress` must not turn a hang into a pass: `user::finish` on a process that never ends blocks for ever; keep the harness timeout as the backstop and say which process.

## T265's PR (2026-11-27): what was built, run and found

Built (one PR into `epic/stability`):
- **The walk oracle** (T227 a): `PageTable::frames_in_range` counts the tables and leaves a walk finds under a range (host test
  `kcore/tests/pagetable_model.rs` `the_range_walk_counts_what_the_model_holds_*`, against the model, both formats; mutation by hand: the
  range's lower edge `<=` made `<`, both tests failed). The formulas moved to `kcore::kwindow` and are **proved by Kani** against a page by
  page count of the tables (OD177, OD182: `the_heap_formula_counts_every_frame_the_window_maps`, every page count up to 1100, 115 s;
  `the_stack_formula_counts_every_frame_the_slots_map`, every slot count up to 130, 13 s; mutation by hand: the stack formula's
  `div_ceil` made `/ + 1`, the proof failed). The kernel compares the walk with the formulas at boot
  (`kernel_windows_hold_what_their_formulas_say`) and after init (`..._after_init`); mutation by hand (the stack formula plus one): both
  failed, `stack window (6, 7)` and `(8045, 8046)`. In every boot since, both agree: the formulas are not where a frame hides.
- **The pool's moves** (T227 b): `heap::rebalance_pool` marks a frame in hand (`IN_TRANSIT`) and counts finished moves (`POOL_MOVES`);
  `kmem::free_frames_accounted` keeps only a sum read with nothing in hand and no move finished meanwhile. The review found that the oracle
  read its terms one after another with no common lock, so a move between the pool and a hart's cache that began and ended between two
  of the reads made the sum one high (a refill counted in both) or one low (counted in neither), and "two reads agree" does not exclude
  it when an idle hart moves several frames. **A one-high reading of the count before init makes every later reading "one short"**, which
  is the shape of the 2026-11-23 recurrence (one frame, in no term). That is a candidate cause, not a shown one: a scratch kernel with a
  2 ms planted delay inside both in-hand windows (old oracle, kernel-only shard, four harts, one boot) did not fail a frame check; the same
  plant on the new oracle passed too.
- **More terms in the failure** (T227 c): per-hart frame-cache fill, the frame in hand, live kernel stacks, exited threads not reaped,
  FP and vector records, and the walk, before init and now.
- **The dying record** (T278): `kernel/src/user/dying.rs` notes each process from the kill or whole-process exit (`Ending`) through
  `teardown_take` (`Taken`), the device drain and `teardown_memory` to its job's credit; the leak report prints `leak: dying <pid>` for
  every process on its way out, in the table or already out of it (the two that T278's root job still charged), with the stage, the
  thread, and how long it has been ending and out of the table; the 5 s watch waits for it to empty.
- **Process and job churn** (T40's part, the reproduction stressor): `crash` churn operation 6 makes a job with one to three processes
  that never start, each with two committed pages mapped, ended by `process_kill`, by closing the handle, or by `job_kill` (torn down by
