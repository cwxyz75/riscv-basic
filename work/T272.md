**What.** Seen on `main` (the merge of phase 12c, run 45526107354, 2026-11-25 01:31, job `kernel (ktest 4 GiB, latency)`: both tests) and on PR 572 (run 45545474252: `kernel (ktest release)` the sparse test, `kernel (ktest 4 GiB, latency)` both). The same tests pass on other runs, including `main` at fd5d4f2's neighbours. The PR changes only documents, so this is not caused by it.

**Likely cause (a reading, not shown).** Both tests (`init/src/bin/suite.rs` near lines 3058 and 3332) map 2 GiB at the fixed address `BASE = 0x10_0000_0000`. Since HD2 a program's image, heap and library are placed at random (`ksys::place_anywhere`, `kernel/src/user/loader.rs`), so some layouts overlap `BASE .. BASE + 2 GiB` and `process_map` answers INVALID_ARGS. The same family as T251 (fixed addresses in the stack arena). It would explain why it comes and goes with the random draw and why only these two tests, which map the most memory at a fixed place, show it.

**Why acceptable.** Test-only; the kernel answers correctly for an overlapping fixed mapping.

**Proper fix.** Map with ANYWHERE (the C library's placement) and use the returned address, or ask `process_map_info` for a free 2 GiB range first. Then run the two tests many times with `os-repeat` to see that the failure is gone (OD160: close on a named cause). If the failure persists with a free range, the cause is something else and this item stays open.
