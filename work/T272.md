**What.** Seen on `main` (the merge of phase 12c, run 45526107354, 2026-11-25 01:31, job `kernel (ktest 4 GiB, latency)`: both tests) and on PR 572 (run 45545474252: `kernel (ktest release)` the sparse test, `kernel (ktest 4 GiB, latency)` both). The same tests pass on other runs, including `main` at fd5d4f2's neighbours. The PR changes only documents, so this is not caused by it.

**Likely cause (a reading, not shown).** Both tests (`init/src/bin/suite.rs` near lines 3058 and 3332) map 2 GiB at the fixed address `BASE = 0x10_0000_0000`. Since HD2 a program's image, heap and library are placed at random (`ksys::place_anywhere`, `kernel/src/user/loader.rs`), so some layouts overlap `BASE .. BASE + 2 GiB` and `process_map` answers INVALID_ARGS. The same family as T251 (fixed addresses in the stack arena). It would explain why it comes and goes with the random draw and why only these two tests, which map the most memory at a fixed place, show it.

**Why acceptable.** Test-only; the kernel answers correctly for an overlapping fixed mapping.

**Proper fix.** Map with ANYWHERE (the C library's placement) and use the returned address, or ask `process_map_info` for a free 2 GiB range first. Then run the two tests many times with `os-repeat` to see that the failure is gone (OD160: close on a named cause). If the failure persists with a free range, the cause is something else and this item stays open.

**Sightings since (rule 11).** The epic smoke of `epic/iommu-kernel` at 14e9694 (run 45922828828, job `kernel (ktest)`): the sparse test, in the
**one-hart** kfast boot (`OS_SMP=1`, the first boot of `os-ktest-small`), not the two-hart one. The IOMMU4 engineer saw the same once at two harts
(PR 579). Neither the hart count nor the epic matters: the test predates the epic (fork point 58894ca) and the first sightings were on `main`.

**Cause (shown, not only read).** A boot with the suite printing its mappings at the start of the sparse test (`print_mappings`) showed, in the
mapping arena `[0x9_0000_0000, 0x30_0000_0000)` (156 GiB), the suite's image (about 1 MiB) and the system library (12 KiB) at random places
(0x17e0a35000 and 0x2680828000 in one boot), and the suite's own thread stacks at 0x28_0000_0000 and up. A fixed 2 GiB at 0x10_0000_0000 overlaps
when either random base falls in a window of about 2 GiB: roughly 2 x 2/156, so 2.6% of boots per test, and `process_map` answers INVALID_ARGS
for an overlap (SYSCALLS.md: "overlap with an existing mapping"). The kernel is right; the tests named a place that is not theirs.

**Fix.** Both 2 GiB tests map ANYWHERE (`map_anywhere`, which prints the process's mappings and the length when the kernel refuses). Every other
fixed address the suite, `init` and `crash` mapped in the mapping arena or the stack arena moved to the 32 GiB above the stack arena
(`FIXED_WINDOW` in `suite.rs`), where nothing the kernel places lands: the suite's own thread stacks (`NEXT_STACK`), the network tests' rings,
the two fresh-child tests (`reserved_abi_space_is_refused`, `mappings_per_process_are_bounded`), the "mapped by nothing" probe of
`debug_write_pointer_rules`, `init`'s `rights` aid, and `crash`'s shootdown page and its mapping churn. To close (OD160, a named cause): the
epic's smoke green with this change; the manager closes it.

**Runs (2026-11-26, on the epic at 14e9694).** Before the fix, with the layout printed: seven kfast k-shard boots (two at one hart, five at two),
no failure; the image and the library were at seven different places each (one boot put the library at 0x113f272000, 3 GiB above the old
window's end). After: one boot at one hart, one at two, one at two harts with 4 GiB (both 2 GiB tests ran), and `s4a_serial_test` (`init`'s
`rights` aid): all passed. Host pin: `ksys/tests/place_anywhere.rs` (nothing ANYWHERE lands above the mapping arena; it fails when
`place_anywhere`'s upper bound is moved to the top of the user half).
