title: The kernel's page table, the heap window and the stack slots have locks of their own; what `heap`, `kstack` and `kmem::get` still assert about the object lock
area: sched
horizon: long
refs: [L20]
---

Built with L20's third step (2026-11-23): `kmem::KPT` (class `KSTACK`, instance 1) serialises the edits of the kernel page table (the heap window's growth, the stack windows' mapping), `kstack`'s slot allocator is `KSLOTS` (instance 0), the kernel's address-space object is `KASPACE` (instance 2, between `JOBS` and `FRAME`: `kmem::get_as`, for the kernel's page-fault handler and the self-tests), `kmem::get`, `jobs`, `frame_alloc`, `frame_free_sole`, `heap::grow` and `rebalance_pool` no longer assert the object lock, and `KStack::drop` takes no lock but its slot lock (it used to take the big lock under whatever the dropper held).

Left: nothing known; if a boot shows a path that touched these under another lock's protection (a hart reading the stack window while another maps a slot is the case to think about: a slot is mapped before it is handed out, and slots are never unmapped), it is a defect of this item.
