## Shortcut

**SQLite (a port that exercises the file system), 2026-11-17**: `sqlite3` (the 3.45.1 amalgamation and its shell, unmodified, one thread, no loadable extensions, no write-ahead log, no memory mapping, temporary files in memory) runs. The shell test runs seven SQL scripts through it and through the host's `sqlite3` (the oracle), a database file two processes use (a journal, `fsync`, truncate), and a database on the disk volume with `pragma integrity_check`. It found that the memory file server did not answer `SYNC`. **Shortcuts:**

- (1) **advisory locks are granted and not enforced** (`fcntl` `F_SETLK`/`F_SETLKW` succeed, `F_GETLK` says unlocked): two processes writing one database at once are not protected from each other (one writer at a time is the user's business)
- (2) `fsync` is the server's `SYNC` (real on the disk volume, a no-op in memory), `fdatasync` the same
- (3) file times cannot be set (`utime`, `utimes`: `ENOSYS`), so the shell's `.archive`-style commands and `readfile`/`writefile` times do not work
- (4) `getrusage` is all zeros
- (5) it is in `/etc/trusted` and the user's profile with the `store` volume, so it is a trusted program (a root and the volume)
- (6) the in-memory database is the only temporary storage (`SQLITE_TEMP_STORE=3`): a query that needs more than memory fails.

## Why it was acceptable

A large real program on the C library and the file system, checked against an independent implementation.

## Proper fix, and when

- (1) record locks in the file server (FS-SPEC)
- (3) a call for file times in the file protocol.
