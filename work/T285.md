Part of the stability epic (`STAB0`). This is PR B of T266's plan (2026-11-24), moved into an item of its own on 2026-11-27 so
that it is one PR; its design is restated here with the owner's answers (OD161) applied, and T266's plan keeps the reasoning.

**What.** T233's second symptom (`a_dead_client_frees_everything`: `socket_read` returned INVALID_ARGS for the queued data of a
killed client) and the plan's candidate 2: `SOCKET_READ` and `CHANNEL_READ` verify the destination (`verify_writable`), dequeue,
and defer the big copy (`finish_out`, `kernel/src/user/trap.rs`), which uses the fault-capable `copy_to_user` after the bytes are
gone. A copy that fails there loses the data with the error. `kcore::usercopy::resolve` maps `VmoGone` and `MapFailed` to
INVALID_ARGS (`NoMemory` was fixed to NO_MEMORY on 2026-11-24).

**Owner's decision (OD161).** A channel or stream read does not dequeue until the copy to the caller's buffer has succeeded:
peek, copy, commit; a failed copy leaves the message queued. `VmoGone` and `MapFailed` on a user copy report the bad-address
status the caller would see touching the memory itself; NO_MEMORY only for real exhaustion. SYSCALLS.md says so per call.

**Scope (one PR, kernel slice).**
1. Peek, copy, commit for `channel_read`, `socket_read` and the reply of `channel_call`, including the deferred (big) copies that
   run outside the object lock: the commit re-takes the object lock and removes exactly what was copied, and a second reader
   that ran in between is handled (design it: a per-endpoint read claim, or commit-by-sequence-number that fails the second
   reader's commit with SHOULD_WAIT and makes it retry; the plan rejected re-queueing at the front because it reorders a stream).
2. `usercopy::resolve`: every `FaultError` arm deliberately mapped, a table-driven `kcore` test against `SYSCALLS.md`'s list.
3. T233-e: the big-lock check of `user::state()` and `fp::state()` an `assert!` in the `release-checked` profile (check the cost
   and that no release path runs it without the lock; coordinate with T256, which owns `fp.rs` aliasing).
4. `SYSCALLS.md` and `INVARIANTS.md` rows (T10/KT9: nothing may fail for memory after a message is taken) updated in the PR.

**How to investigate.** Start from T266's PR A result (its chaos point between `dispatch` and `finish_out`, and the
pattern-checked kill storms): that names whether a live cause remains besides the `current_space()` fix of PR 491. Then write
the host test first: `ksys` with `defer_out`, a lazily backed destination and a frame allocator that fails on demand
(`ksys/tests/allocfail.rs`): today a failure after the dequeue loses the message (the test fails); after, the queue is intact.
Reason through every interleaving of a kill, a peer close and a second reader between peek and commit: a **TLA+** model of the
read protocol (peek, copy, commit, with a killer and a second reader) is the right size for TLC and is recommended (needs an OD:
`STAB0`, "Tools that need an OD"); without it, a shuttle model of the commit over the real `kcore::ipc` queue.

**Acceptance (each run under two hours).** The `ksys` host test above (fails before, passes after; mutation: commit before copy
fails it); the `kcore` mapping table test; T266's channel and stream kill storms pass at four harts in one targeted boot; the
allocation-failure sweep's scenarios for the read calls (`ksys/tests/allocfail.rs`, host) pass. Review by Opus (the epic's rule,
`STAB0`); Fable only on escalation.

## Built (2026-11-28, PR 627)

**Cause and fix (part 1).** T266's mutation run (PR 618) tied T233's INVALID_ARGS to the pre-PR-491 `current_space()`; it showed no
other live cause. The defect this item names is still real independently of it: `finish_out` copied with the fault-capable
`copy_to_user` *after* the dequeue, so any failure there (a sibling's unmap or decommit, no memory for a commit or a copy-on-write,
a pager page) lost the message with the error. Fixed by peek, copy, commit (OD161): `kcore::ipc::{channel_claim, channel_commit,
socket_claim, socket_commit}` name what a read takes (a message by a per-endpoint serial, stream bytes by the end's read count `taken`,
both under an `ObjId` with its generation). The design chosen is commit-by-name: a commit that finds its claim gone (another reader
took it) returns `Moved` and the kernel makes the read again from the start (`trap.rs` loop; `channel_call` waits again, to its
deadline). Rejected: re-queueing at the front (reorders a stream), a per-endpoint read claim that blocks a second reader (a reader
that dies mid-copy would wedge the endpoint). Handles go into the table and their numbers are written inside the commit; a failed write
takes them back (`HandleTable::take_back`). A killed process's commit takes nothing (the message stays for another holder). The big
copy keeps running outside the object lock from a kernel copy of the claimed bytes, allocated before anything is taken.

Interleavings reasoned and tested: a second reader (plain, txid, inline, deferred), the reader's handle closed (teardown), the endpoint
destroyed, the peer closed, a failing copy, a failing handle-number write: `ksys/tests/read_commit.rs`; shuttle over the real queue
with a writer, a killer, a closing peer and two negative controls: `kcore/tests/read_commit_concurrency.rs`. TLA+ was not used: this
machine has no Java runtime, and the shuttle model runs the real `kcore::ipc` code (the ticket's named fallback). A shuttle DFS of
the three-message model did not finish 2,000,000 schedules (31 s, no violation); of a two-message model without the closer, not within
25 minutes (no violation); the regular test is 20,000 random plus 5,000 PCT schedules per model.

**Part 2.** `kcore::usercopy::fault_status` names every arm; `kcore/tests/usercopy_status.rs` checks it against SYSCALLS.md's new
table (mutation: VmoGone to NO_MEMORY fails it).

**Part 3 (T233-e).** No code change needed: the `release-checked` profile sets `debug-assertions = true` (Cargo.toml, KT12), so the
`debug_assert!` big-lock checks of `user::state()` and `fp::state()` already run there; the SAFETY comments now say so (KT14 rows
added). T256 was not touched.

**Part 4.** SYSCALLS.md (copying, `channel_read`, `socket_read`, `channel_call`) and INVARIANTS.md H7.

**T287's cascade is not this item's subject:** the channel tests in `suite.rs` share `BOOTSTRAP`; a test that fails early (a timing
`ensure!`) leaves its late reply queued (a TIMED_OUT call's reply stays queued, as SYSCALLS.md says), and the next test reads it. Those
messages are under 1 KiB, so no deferred copy is involved.

**Spec problem (for the owner; not changed):** SCHED-SMP-SPEC 3.10 ("Copy-out of a message: `AS { verify; OBJ { dequeue }; copy the
first chunk }` ... the call fails with INVALID_ARGS and the message is lost") describes the protocol OD161 replaced. It wants a dated
amendment (dequeue after the copy; nothing lost), which agents may not write.

**Noted by the review, left as they were (existing design):** the kernel's copy of a big read (up to 64 KiB per reading thread) is a
transient class-R heap allocation, not charged to a job; the pager-need slot is global, so a copy that stops for a pager page can
overwrite another hart's pending need (a retry, not a loss; `vmo_rw_call` does the same); the L22 dequeued-call note and
`lend_to_reader` are separate lock sections, as before.
