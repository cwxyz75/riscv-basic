title: A kernel panic in the four-hart kernel-only boot: slice::get_unchecked range check (seen once, CI)

**What.** CI, PR 478 (a test and harness change, so none of its code is in the kernel shard), job `kernel (ktest 4 harts)`, run 45215984804: after `bystander_cost_of_sleeping_bindings` PASS the kernel printed `##PANIC panicked at library/core/src/slice/index.rs:492:32: unsafe precondition(s) violated: slice::get_unchecked requires that the range is within the slice` and the boot ended. The next test is `a_dead_client_frees_everything` (stream queues, then `process_kill` of the client). The panic location is the standard library's, so the caller is not known; no `get_unchecked` exists in this repository, so the caller is a library function over a range that is not within its slice (an index computed from a length that changed between two steps is the likeliest: T215 made big stream and message copies run outside the object lock).
**Not reproduced:** four local boots of the same shard at four harts passed (macOS, debug build); the second soak's `smp` boots passed.
**Why acceptable.** One occurrence, development only; but it is a possible memory-safety fault, so it stays `near`.
**Risk.** A real out-of-range access on the stream or message copy path under a kill.
**Proper fix.** Find the caller: a panic handler that prints the return address chain (frame pointers), or the same boot repeated until it recurs (`make os-repeat TARGET=os-ktest-4 N=20`); read the staged and deferred copy paths in `kernel/src/user/trap.rs` and `ksys/src/lib.rs` for a range computed before the lock was dropped.
