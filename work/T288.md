### T135: A flaky shuttle test in CI

*(area testing, horizon someday, risk M)*

#### Shortcut

**A flaky shuttle test in CI** (2026-11-17): `klock`'s `spin_concurrency::the_lock_excludes` (run under the shuttle model checker in the `host` job) failed once on PR 205 (`shuttle-0.8.1/src/runtime/execution.rs:203`, a panic inside the checker's execution) and passed on rerun; `klock` was not touched by that PR. Not reproduced. Shuttle explores schedules at random, so a failure can mean a real interleaving bug in the lock or a checker limit (its step or thread bounds); the log was not kept past the failure line.

#### Why it was acceptable

Cannot say which without the schedule.

#### Proper fix, and when

If it recurs, keep the shuttle seed and schedule from the log (`SHUTTLE_*` replay) and bisect the lock.

(Migrated from the old TIDY-UP register, section "Concurrency and kernel structure", 2026-11-18.)

#### Cause named (2026-11-27)

~~Not reproduced~~. **Cause: T155's shared hart number** (closed 2026-11-19, PR 259, two days after this sighting on PR 205 of
2026-11-17, which ran the test as it was before that fix). The model gave its threads hart numbers from one process-wide counter
that each model run reset, and the binary's two tests run in parallel, so now and then two threads of one model got the same
number. The second's take passed `Spin::lock`'s recursion check before the first took the ticket, then found `held_by(0)` true in
`Ticket::lock` and deepened instead of drawing a ticket; both released, `serving` passed `next`, and the next ticket drawn was never
served: an endless spin.

- **The line, from the source.** `execution.rs:203` in shuttle 0.8.1 is the `panic!` of the `NextStep::Failure` arm of
  `Execution::step`, a failure of the scheduler itself (the step bound, "exceeded max_steps bound 1000000"; a deadlock; "no task was
  scheduled"), not a task's own panic (that is re-raised by `resume_unwind` further down). A ticket spin lock has no blocking
  operation, so the failure is the step bound.
- **Reproduced.** The pre-T155 test (`git show ad25f83e^:klock/tests/spin_concurrency.rs`, against today's lock), whole binary
  repeated: 16 failures in 500 runs (14 s), 10 at exactly `execution.rs:203:17` ("exceeded max_steps") and 6 at the recursion check
  ("recursive take of a Jobs lock"). Each failing schedule **does not replay alone** (`shuttle::replay` of the 99-character
  recursion schedule `91025eade3c3d8f8d3ed8d4890044214254a222991a4249122298992488a2249521445512445` +
  `9292288aa44452924801` ends with "schedule ended early"; the 760 kB max-steps one with "scheduled task is not runnable"): the
  numbers came from outside the model, which is why the rerun passed. Forcing one number for both threads reproduces it
  deterministically: `RandomScheduler::new_from_seed(2, 2000)` fails at `execution.rs:203`, seeds 1 and 3 at the recursion check.
  Step by step: `Ticket::lock(0)` twice with two depths, two unlocks, then `try_lock` can never succeed (`serving` is past `next`).
- **The bounded hunt on today's test** (no failure in any piece): `shuttle` random, seeds 0..20000 x 2000 iterations, 3 rounds
  (593 s); seeds 0..4000 x 2000, 6 rounds (236 s); PCT depth 2, seeds 0..10000 x 2000 (261 s); PCT depth 3, seeds 0..10000 x 2000
  (266 s); PCT depth 4, seeds 0..4000 x 2000, 6 rounds (182 s); the committed binary as CI runs it (both tests in parallel) 3000
  times (99 s). loom, one round (as CI): green (7 s); loom, two rounds: did not finish in the time given (see the PR). Miri over
  klock's host tests: green (22 s).
- **The control.** `klock/tests/spin_concurrency.rs` `two_threads_with_one_hart_number_are_caught` (shuttle): the model with one
  hart number for both threads must fail with "exceeded max_steps" or the recursion check; mutation (both numbers distinct again):
  it fails, "the shared number was not caught". `Spin` now also panics on a hart index that has no ticket owner id.

## Stability epic (2026-11-27)

**Scope (one PR).** From T259's plan (section 2.C item 2): generate the kernel's order probes from `klock::Class` (every ordered
pair, expected = the pure table) instead of the 16 written by hand (14 classes today); make `Held::release` strict for every class
but `Uart` (a panic breaks it), now that the big lock's hand-overs ended (L20). T85 (4) (`Machine::hart` is `u32`) and (6) (the
park model has one waiter and one wait round) are checked and struck or done: (6) wants a second waiter and a second wait round
in `kcore/tests/park_concurrency.rs`. T135: find what shuttle's panic at `execution.rs:203` means in shuttle 0.8.1 (read the
source: a step bound, a deadlock report or an internal assertion), then either fix the test's bounds or the lock.

**How to investigate.**
- T135: run `klock`'s `spin_concurrency::the_lock_excludes` under shuttle with many random schedules and with the PCT scheduler
  (`shuttle::check_pct`), seeds printed, bounded to one hour; shuttle prints a replayable schedule on failure
  (`shuttle::replay`): keep it in the item. Run the same test under loom if it fits loom's bounds, and under Miri (`make os-miri`
  runs `klock` there: a targeted `cargo +nightly miri test -p klock` is an experiment, not the soak).
- Strict release: turn it on and read what the suite says (one targeted kernel-only boot at four harts); every report is a real
  double release or a release on the wrong hart (TESTING.md rule 11 applies to anything that appears).
- **Kani** fits the pure order table: a bounded proof that the table is a strict total order on the classes that the kernel
  nests, and that `Held`'s push/pop never accepts a descending acquisition (needs an OD, `STAB0`).

**Acceptance (each run under two hours).** `klock/tests/order.rs` gains "every ordered pair matches the table" and "a release of an
unheld non-reentrant class panics" (mutation: make the release lenient again, the test fails); the in-kernel order test probes
every pair of the table (one targeted boot shows the count); T135's cause is named from the source and the schedule (or, if the
bounded hunt finds nothing, the item records the seeds and schedules tried and stays open, OD160). Review by Opus.

## Done (2026-11-27, the T288 PR)

- **Every ordered pair.** `klock/tests/order.rs` `every_ordered_pair_matches_the_table` (15 x 15 classes at instances 0 to 2,
  against a table written out in the test, not read from `Class`) and `every_ordered_pair_under_a_held_chain_matches_the_table`
  (every legal pair held, every class taken); the kernel's `lock_order_violations_are_detected` generates its probes from
  `Class::ALL`: one boot prints `lock order: 229 ordered pairs of 15 classes probed, 118 flagged`. Mutations: a table that drops
  `KSTACK` from "two at a time" fails both host tests; a checker that ignores the probe's instance fails the kernel test
  ("holding As 0, taking As 1: expected flagged=false").
- **Strict release.** `Held::pop` panics on a lock the hart does not hold for every class but `UART`
  (`a_release_of_an_unheld_lock_panics_for_every_class_but_the_console`: never taken, released twice, another instance, a reentrant
  class released once too often). Mutation: the old lenient rule fails it. The kernel-only shard at one and four harts and in the
  release build, and both suite shards at four harts, ran with it: no double release, no release on the wrong hart.
- **Kani** (`cargo kani -p klock`, five harnesses, about 90 s): the class order is strict and total; no sequence of five takes and
  out-of-order releases lets the stack accept a descending take; a release finds exactly the held entries; an unheld release
  panics, and a console one changes nothing. Mutations: `class >= top` in `check` and a release that ignores the instance each fail
  a harness.
