The scheduler algorithm is to be overhauled as a whole, some day (OD150). Every tidy item that is specific to the *current* scheduling algorithm (its normal-band fairness, its balance, placement and real-time budget policy, the allocation in its core, its donation design) is folded here instead of being fixed one by one: the fixes would be replaced by the overhaul. Items that survive any algorithm (hart power management, shared futexes, the PI futex word, thread lists, time-keeping, the park protocol) stay where they are: T257, T258, T259, T260, T74.

Parts: T247, T78, T163, T217, T221, T77, T169, T170, T210, T211, T231, T107, T108, T72. Each section below is the item as it was; the plans written for T257, T258 and T259 on 2026-11-24 stay in those bundles and contain sketches (the class-N prepaid-room design, the donation graph, the fair class in T72's section) that the overhaul can take over. Defects in here that bite today (for example hart 0's scheduler clock, which is T168's, and T211's normal thread that waits on another hart) are a reason to bring the overhaul forward, not to patch them.

### T247: The scheduler core allocates on sleep, wake, spawn and migration (class N, with a reserve)

*(area kernel, horizon long, refs [KT9, T177, T246])*


**What.** `kcore::sched2` (`RunQueue`, `timers`, `hard_timers`, `demoted`, the per-hart `threads` maps) and `kernel/src/thread.rs` (`Kernel::threads`, the queues) grow with the infallible collections whenever a thread is spawned, sleeps, wakes or moves. They are class N (T177): inside `heap::nofail` or with a `TT`/`RQ` lock held, which the allocator's reserve (1 MiB plus 256 bytes per live kernel stack, `heap::reserve`) lets through when class R is refused.
**Why acceptable.** A thread that exists cannot be refused a wake, so the scheduler cannot report `NO_MEMORY`; the reserve keeps room for the allocations the population makes, and the population cannot grow once class R is refused (thread creation is an R point).
**Risk.** The reserve is an estimate. A fragmented free-list heap may not serve one large growth of a queue (one priority level with tens of thousands of threads) even with the reserve free.
**Proper fix.** Per-thread nodes made at spawn (intrusive run queues, a timer heap of slots), so that wake, sleep and migration allocate nothing. When: the next time `Sched2` is opened, or the FZ1 review.

### T163: Exited detached threads are freed inside finish_switch under the big lock, not from a per-hart dead list at a safe point

*(area sched, horizon near, risk L)*


#### Shortcut

L11c part 1 (PR 262) frees an exited detached thread in `finish_switch` (`reap_if_dead`), with interrupts off and the big kernel lock held, where SCHED-SMP-SPEC 3.6 has `finish_switch` move it to `PerHart.dead` and the hart reap at a safe point (`preempt_point()`, return to user, idle) with no lock held, plus `reap_quiesce()` for leak oracles. Review (Fable, 2026-11-19): the work (stack scan `note_stack_use`, map remove, heap and stack frees, two scheduler lock takes) is now charged to whichever thread resumes, possibly an RT thread, where the reaper thread paid it before. The safety argument depends on the big lock covering exit through `finish_switch`; `join` of a joined thread relies on the same.

#### Why acceptable

The lock follows the thread until L12, so no reap can race a switch; the leak tests pass. The work is the same as the reaper's.

#### Proper fix, and when

L12 (the scheduler leaves the big lock): per-hart `dead` list filled by `finish_switch`, drained at the safe points, `reap_quiesce()`, and `join` using the same hand-over; check B3 wake latency before and after. Do it with L12.

### T217: a PI futex lets one confined program lend a real-time priority to a normal-band thread without being charged for it

*(area sched, horizon long, refs [L23, L25, T77])*


**What.** A process with a real-time-base thread W and a normal-base thread L: L takes a PI futex and spins, W blocks on it with no deadline. L then runs at W's real-time priority. The job's real-time budget (L25) charges only threads whose **base** is real-time (`charge_job`), so L's time in the real-time band is not billed and L is never demoted; only the per-hart cap of 80 ms in 100 ms (NM1, when the normal band has work) applies. The donation graph also ignores demotion: a demoted donor still lends the priority it had before it was demoted.

**Why acceptable.** The program can only do this to itself and its own job's threads, so it gains nothing a program with a real-time thread did not have; the per-hart cap keeps the normal band alive. T77 records the same for `channel_call` across processes. The budget's purpose, bounding a runaway real-time thread, is met for the threads that are real-time by their own priority.

**Proper fix.** Charge the real-time band by **effective** priority (a thread running in the band on a donation is billed to its own job, and demoted like one), and have a demoted donor lend its demoted priority. It needs the accounting to know why a thread is in the band; do it with L22 (donation through `channel_call`), which has the same question.

### T221: no donation between a call's request being queued and the server reading it (the provisional edge of SCHED-SMP-SPEC 4.8 at wake)

*(area sched, horizon long, refs [L22, L24, T77])*


**What.** L22 lends the caller's priority to the thread that **reads** the request; L24 places the woken server on the caller's hart (direct hand-off). Between the wake and the read the woken server runs at its own priority: a low-priority server that was woken but not yet scheduled (the harts busy with higher-priority work) is not boosted until it reads. SCHED-SMP-SPEC 4.8 wants a provisional edge at wake, confirmed or dropped when the thread reads.

**Why acceptable.** The common case, a server blocked in receive, is placed on the caller's hart by the hand-off and runs as soon as the caller blocks. A server that waits on a **port** (the service runtime) is registered on the port, not on the channel end, so the commit cannot tell which woken thread serves this call without more bookkeeping.

**Proper fix.** Have the wait table report which object each released registration was on (and, for a port poller, which bound object's touch released it), match it to the call's peer end, and `retarget` the caller's edge from the provisional waiter to the thread that reads (`pi_lend` of `lend_to_reader` already would have to retarget instead of refusing a second donation).

### T169: L13 leftovers: equal-priority balance only at timer events, timer slack not settable from user mode, no RT window entry

*(area sched, horizon near, risk L)*


#### Shortcut

L13b (no tick) leaves: (1) `Sched2::balance` (the share-out of equal-priority queues, T107 (3)) ran at every tick and now runs at timer events only (a slice end or a sleeper's deadline on that hart), so a lopsided queue of equals on a hart that has no event stays lopsided until a thread blocks or the hart's slice rotates; (2) the thread's `timer_slack` (default 50 µs normal, 0 RT) has no user-mode setter (the reserved flags of `thread_set_sched`, SCHED-SMP-SPEC 4.11); (3) the RT window boundary timer entry (4.11) does not exist because RT budgets are not enforced yet; (4) hart 0's clock and the scheduler's first charge start at the first event (benign).

#### Why acceptable

The suite and the smoke gate pass; (1) only affects fairness among equal-priority threads on busy harts, (2) and (3) are features nothing uses yet.

#### Proper fix, and when

(1) give an overloaded hart a slice-end action (balance at the slice end that already exists, and on a mark), with a test on the pure model that equal queues converge without ticks; (2) with the SC/RT syscall work; (3) with RT enforcement. Before L14.

### T170: L13b review leftovers: round-robin build slice arm, the debug watchdog is a 100 ms tick in disguise, acceptance bounds

*(area sched, horizon long, risk L)*


#### Shortcut

From the Fable review of PR 273 (2026-11-19), not fixed there: (1) in the `sched-round-robin` build `RoundRobin::next_event` makes a slice end an event for any queued thread, but `after_enqueue` marks a remote busy hart only for an equal or better thread, so a lower-priority thread queued remotely behind a lone runner arms no slice timer (a user-mode spinner never yields); (2) in debug builds a hart with queued work arms the watchdog every 100 ms and the interrupt runs a full `tick_on`, which repairs a lost slice-end arm or lost poke within 100 ms: the release suite alone can see such a bug, and the `fault-skip-poke` control is weaker than before (it still ends in `starved thread`); a lower-priority thread queued remotely on a lone-runner hart arms nothing, so real starvation there goes unreported unless another hart has queued work; (3) the L13 acceptance "100 µs for an RT thread" is a 4 ms bound (the emulator's interrupt jitter), `wake_before_block_is_not_lost` allows 12 ticks, `harts_come_online` lost its per-hart one-shot check, the idle and lone-runner tests allow a few interrupts and only check hart 1; (4) wakes stamp `runnable_since` from the hart clock: fixed for `wake_inner` (charged first), not for `spawn_on` and `fresh_as`; (5) a lone runner's `slice_left` is drained by `charge` and not refilled until an interrupt (the first equal peer rotates it at once); (6) without `menvcfg.STCE` the first `csrw stimecmp` traps before the readable assert (loud anyway).

#### Why acceptable

Debug-only or emulator-jitter effects; the pure model and the smoke gate pass.

#### Proper fix, and when

(1) ask the class whether a queued thread makes a slice event (a `Class::needs_slice_timer(eff)`), mark on that; (2) make the debug watchdog sample call only `starved` without `tick_on`, and arm it when any hart has queued work; (3) tighten the bounds when a quiet-host soak shows the margin, test every hart; (4) charge in `spawn_on`; (5) refill on idle-to-busy; do (1) and (2) before L14.

#### Note (2026-11-27): `wake_before_block_is_not_lost` no longer times its first half

The release kernel at four harts failed the first half (prepare, wake, wake, block, then at most one tick since before the prepare) on
the stability epic's checkpoint smoke, CI run 46085592181. Cause: a pause of the host, not a lost wake. A lost wake cannot fail that
check: nothing else wakes the test thread, so a planted one hangs the boot (no output for 60 s after the previous test); the CI test
returned. With the host-stall injector (`OS_HOST_STALL=10:40`) a loop of 40,000 rounds of the first half crossed the bound 10 times with
`block` blocking in none (9 of the 10 windows covered by the pause detector), and never without the injector (worst round 166 µs).
The first half is now judged by what the call did (`thread::block` returns whether it blocked) and a rescuer thread turns a lost
wake into a failure instead of a hang. The second half (block, woken after 3 ticks) starts its window before the waker is made (a
pause between the two could make it short), takes again a window that a pause covers, and its waker repeats only a wake that did not
count (`thread::wake_counted`): after a counted wake it waits for the thread, and one still blocked after `WBB_RESCUE_TICKS` is a
lost wake, reported as such. Both planted lost wakes of the first half (a wake to oneself dropped; `block` dropping a notification)
fail the test with "the rescuer woke it"; a counted wake planted as lost fails the second half. Bound (3) above still stands for the second half's 12-tick slack.

### T210: devmgr starts drivers in jobs with a real-time ceiling and a budget (SCHED-SMP-SPEC 4.9, the last line of L8's policy)

*(area sched, horizon long, refs [SCHED-SMP-SPEC, L8])*


**What.** 4.9 says driver jobs made by `devmgr` get an RT ceiling and a budget, so interrupt threads can sit in the real-time band. L8 built the mechanism and the rest of the policy (the launcher's 20 and no budget, the session job's 31); `devmgr` still spawns `blkd` and the other drivers into its own job, which has the root's 63 and the whole window, and no driver runs a thread at a real-time priority.

**Why it waits.** A driver job's ceiling and budget are only meaningful once something enforces the budget (L25) and a driver has an interrupt thread that asks for the band; `devmgr` also has no job handle of its own to make child jobs from (`job_root` goes to `init` and `sessiond`), so the change is a handle hand-over in `init` plus a job per driver. Doing it now would set numbers nothing reads. The risk of waiting: none today (drivers run at the default priority); the root-sized ceiling is the status quo.

**Proper fix.** With L25: `init` gives `devmgr` a MANAGE handle to a `drivers` job below the root with `max_prio` 50 and `rt_budget` 20 ms per window; `devmgr` makes a job per driver below it; the first driver interrupt thread that wants the band (HD items) sets it, and a suite test shows a driver job cannot exceed its ceiling.

### T211: GP1 is excused on a hart whose real-time share is spent (L25): find why a normal thread then waits on another hart

*(area sched, horizon long, refs [SCHED-SMP-SPEC, L25])*


**What.** L25's throttle (NM1) holds a hart's real-time queue back when its share of the window is spent and the normal band has work. The GP1 audit (`kcore/src/sched_smp.rs` `audit`) and the two walk references (`kcore/tests/sched2_smp_model.rs`, `sched2_kernel_walk.rs`) skip such a hart for every waiting thread, not only real-time ones.

**Why it is acceptable for now.** The only violations seen are a normal thread waiting on another hart a little longer than strict priority allows while a hart is in the throttle (never a lost thread, a double dispatch or a real-time thread running past its share: the NM1 and demotion tests check those directly). The Fable review of PR 390 asked for the narrow form (excuse only real-time candidates) and it fails: `gp1_and_gp2_hold_on_random_walks_over_one_to_eight_harts` seed 904 step 331 (hart 3 runs priority 15, thread 66 of priority 19 waits on hart 4, whose queue is led by held-back real-time threads), and seed 964 step 67 without the mid-switch excuse.

**Proper fix.** Find which settle or pull misses it (the pull of the best normal thread behind a held-back real-time queue, or the push offer that should mark hart 3), fix it, and narrow the excuse to real-time candidates. Do it with the next change to placement (SC2) or when the walks are next touched.

### T231: Spread placement can put two new light threads on one hart when the first has already gone to sleep (seen in CI)

*(area sched, horizon long, refs [PM4, PM1])*


**What.** At the phase 10 gate, `kernel (ktest 4 harts)` and `kernel (ktest release)` failed: two light periodic threads created one after the other were taking their wakes on one hart. Spread puts a thread on an idle hart; the first thread, run and asleep before the second was placed, leaves its hart looking idle, so the second joins it, and each then keeps waking on its last hart.
**Why acceptable.** It is the rule working as written (a thread returns to its last hart when it would run there; an asleep hart is idle), and nothing is lost but spread across harts for two light threads. The tests now create the pair with interrupts off and give the spread measurement three tries.
**Risk.** None for correctness.
**Proper fix.** If spread should prefer an unloaded hart to an idle one that already has a sleeper homed on it, `select_spread` needs a per-hart count of homed threads (a hint); decide with the SC2 measurements.

### T72: The normal band has no fairness

*(area sched, horizon someday, risk M)*
#### Shortcut

**The normal band has no fairness**: fixed priority and round robin; a high-priority spinner starves lower ones, a program gets a share per thread

#### Why it was acceptable

Today's behaviour, kept on purpose

#### Proper fix, and when

The hierarchical fair class (SCHED-SMP-SPEC 4.7), deferred

(Migrated from the old TIDY-UP register, section "Concurrency and kernel structure", 2026-11-18.)

#### Plan (2026-11-24)

**Status of the premise.** Not overtaken: the shortcut is real and the fix is still deferred on purpose. KERNEL-V1-SPEC 1 (line 33) lists "a fair scheduling class" as a v1 non-goal and the old work plan (retired 2026-11-25; git history) ("Not in this plan") names T72; no OD entry decides the open points of SCHED-SMP-SPEC 4.7. So this plan is for *after* the v1 freeze and must not be started inside a v1 phase without the owner saying so.

**Evidence that would justify starting** (any one): (a) the owner asks for per-program CPU shares or a per-job CPU quota; (b) a real workload shows the starvation (an interactive session stalls behind a higher-priority or many-threaded job; `os-bench` or the suite records it); (c) PR 1's fluid-model report, which is cheap and host-only, shows a share error above the tolerance on a scenario that occurs in the system (not only on a synthetic one); (d) three or more parts of T259/T258 that say "fix: the fair class" are otherwise ready to close. PR 1 alone may be done at any time as measurement; it changes no kernel behaviour.

##### 2. Proposed design

A third normal-band class `Fair` in a new pure file `kcore/src/fair.rs`, selected by a new feature `sched-fair` beside `sched-round-robin` (OD32's mechanism, unchanged). RT band, idle band, precedence, NM1 and the RT budget code are not touched.

1. **Per hart, EEVDF over threads.** `class_words` = `[vruntime, vdeadline, lag, weight]`. Weight from `eff` by a 31-entry constant table (`1024 * 1.25^(prio-16)`, integers, generated once and checked by a test against the formula). A hart keeps the weighted average virtual time `V` and the weight sum. Eligible: `vruntime <= V`; pick: earliest `vdeadline` among the eligible; `vdeadline = vruntime + slice * 1024 / weight`. `account` advances `vruntime` by `ran * 1024 / weight` and reports "slice over" when the deadline is passed and anything is queued; `next_event` is `None` for a lone runner (OD131: no event without a competitor).
2. **Priority stops being an order inside the band.** `displaces` returns false for normal against normal (as `RoundRobin` does, `sched2.rs:407`); wake preemption is `preempts(cur, now)` (the woken thread is eligible and has the earlier deadline). `would_run`'s early `cand <= cur` test must move behind the class for the normal band. The class still reports one priority to the other bands and harts through `top()`; for `Fair` that is a constant band level, so pull and push move normal work only to idle harts or by load (3).
3. **Across harts: virtual time is per hart; lag travels.** On `Deq::Migrate`/`Enq::Migrated` and on block/wake the class stores `lag = V - vruntime` (clamped to one slice either way) and re-bases on enqueue (`vruntime = V_dst - lag`). Load is a per-hart atomic weight sum in the hint record (next to `queued_len`); `select_hart` for the normal band picks the least-loaded allowed hart unless the last hart is within a margin; `balance` compares weight sums, not queue lengths, and runs at the slice end and on a mark (T169 (1)'s fix).
4. **Hierarchy, depth one, by weight division (second PR set).** A thread's weight is `prio_weight * job_weight / runnable_threads_of_the_job`, with `cpu_weight` and a runnable count kept as atomics in `JobSchedTable` and the weight re-read lazily at `enqueue` and `account` (the idiom the RT demotion already uses: nothing walks a job's threads, no lock under `RQ`). `ThreadSched.group` gets the job slot.
5. **Donation inside the band:** a boosted thread takes the larger of its own and its donor's weight while boosted (`Enq::AttrChanged` keeps lag, never resets it). Charging the donor's entity (T77) stays out.

Rejected:

| Alternative | Why not |
|---|---|
| Full per-hart entity tree per job (the letter of 4.7, Linux group scheduling) | needs group shares recomputed across harts and per-group per-hart queues: the hardest part of CFS, for a system with tens of jobs. Keep as the fallback if (4) misses the fluid tolerance |
| One global virtual time / a shared fair queue | a global lock or a contended atomic on every switch; contradicts 4.4's rejection of a shared queue |
| Decay-usage priority adjustment on top of `FixedPrio` (BSD style) | small, but gives no weights, no per-job share and no bound to test against |
| Stride/lottery or plain weighted round robin | no latency control for sleepers (no lag), which the interactive session needs |
| Changing the ABI priority range or adding a "nice" call | 4.7 says the ABI does not change |

##### 5. Invariants, locks, and how this goes wrong

- **Lock classes.** All class state is per hart under `RQ` (9), at most two `RQ` locks, ascending hart index. Job weight and counts are read as atomics; `JOBS` (6) is before `RQ` in the order, so it must never be taken from the class (the ledger writes the mirror while it holds `JOBS`, as `set_budget` does). `TT`, `PI` and `OBJ` are not touched. No new lock class.
- **Rows.** GP2/C4, AF1, AC1, NM1, TR1/RQ1, X7 and DN1 to DN3 must hold unchanged. **GP1 changes**: for the normal band under `Fair` it reduces to work conservation (no idle hart while an allowed normal thread is queued); new rows are needed (names to be allotted): bounded lag per thread on a hart, weight-sum hint equals the queued weights at quiescence, lag is preserved by migration and by `AttrChanged`. PR1/PR2 (limits never exceed the parent's) extend to `cpu_weight` semantics once it is live.
- **Subtle failures.** (1) sleeper gaming: a thread that sleeps briefly, or calls `thread_set_sched` on itself, must not gain lag (clamp, never reset on `AttrChanged`); (2) fixed-point rounding makes the lags not sum to zero and `V` drift: use wrapping comparisons relative to `V` and test long runs (weight ratio 31 to 1 is about 800:1); (3) migration ping-pong between harts of near-equal load (the margin in design 3); (4) a remotely queued normal thread that arms no slice timer on a lone-runner hart (T170 (1) again: every queued `Fair` thread is a slice event, so `after_enqueue` must mark); (5) the T211 excuse in the audit widens silently if the normal clause is rewritten carelessly; (6) a demoted RT thread arrives at `DEMOTED_PRIO` 31, the heaviest weight (Q6); (7) kernel threads pinned to hart 0 skew load placement; (8) tests that rely on "higher normal priority runs first" (suite, libc, `pthread_create`'s `handle_of` spin, T83 (7)) change meaning; (9) any allocation added to enqueue or wake worsens T257 (use the existing queue storage or a fixed structure); (10) the debug watchdog's 500 ms limit can fire for a priority-1 thread legitimately held to 0.1%.
