title: A user thread that has used floating point still takes the big lock at every trap return (fp::return_to_user)
---

## Shortcut

L12b (PR 267) lets a tick or reschedule IPI from user mode skip the big lock, but `fp::return_to_user` takes it whenever the frame's `sstatus.FS` is not Off, so a thread that has used FP (state Clean) takes the lock on every such return anyway (Fable review, 2026-11-19). The acceptance test uses a thread that never touches FP.

## Why acceptable

Correct, only slower for FP users; the tick path itself is lock-free for them until the return.

## Proper fix, and when

Per-thread FP state readable without the lock (T57: FP state in the thread record, as the kill flag was made an epoch): then the Clean case needs no table access. With the L12 follow-ups or the FP work.
