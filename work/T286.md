Part of the stability epic (`STAB0`). Gathered on 2026-11-27: T209 (from T265), T44 (from T264), and T122 and T269 (merged
here and closed). Their text is below as it was. All four are the storage stack meeting a restart or a slow device: the
volume manager's restart and publish, `fsd`'s start, and the block driver's timeout and restart.

**Since then.** The block path moved to `virtio-blk-pci` behind the IOMMU (IOMMU10) and virtio-mmio left the allowlist (IOMMU12,
2026-11-27): T269's cascade ("map the window: InvalidArgs" after a dead driver) was on the virtio-mmio window, which is gone.
Its first failure (`blk_round_trip`: -12, TIMED_OUT) and the question behind the cascade (does a dead driver leave something
that the next driver cannot map?) apply to the PCI driver's BARs and DMA domain as well. T122's fix (`volmgr` publishes after
`fsd` reports ready) is in the code; the job it flaked in (`harness (fail-demo)`) runs only when the harness changes.

## The parts, as they were

### T209: volmgr_serves_volumes_by_the_table failed once in the phase 8 epic gate (OD140: a defect until its cause is known)

*(area kernel, horizon long, refs [OD140])*


**What.** In the epic gate of PR 383 (smoke a, 2026-11-21) `volmgr_serves_volumes_by_the_table` failed with "unexpected status -100" at the end of `open_volume` (the 15 s retry of a view open after the volume manager restart), and passed on the next run of the same code plus two small fixes. No cause is known.

**Why it is not just re-run.** TESTING.md rule 11: an intermittent kernel-test failure is a defect until its cause is known. It may be a real race in the restart path, or an effect of the EX1/EX2 changes (the thread park, the exception channel reaping on handle close).

**Proper fix.** Reproduce it from the smoke-a log (the harness prints the volmgr lines around it), find whether the restarted volmgr never published or the open retried against a dead channel, and fix that. Do it when the epic's smoke shows it again or in the first slack between items; it does not block phase 9.

**Second occurrence (2026-11-22).** The same test failed the same way (`unexpected status -100 at suite.rs:11217`) in a full local boot of the latency-trace kernel at four harts with `bench=full` (`make os-latency`, the whole suite, 264 user tests passed). It is a different binary and a far heavier run than the gate's smoke a, so the cause is not the gate's load alone; the `open_volume` retry of 15 s ran out both times. That boot's log has the volmgr lines around it.


### T44: Gaps in the block-driver tests (S6b)

*(area testing, horizon long, risk L)*


#### Shortcut

**Gaps in the block-driver tests (S6b).** (The harness now checks the whole image from the host after QEMU exits, `check_disk`: it catches an address bug the guest's read-back cannot; mutation-checked. Flush is still unverifiable: QEMU's raw file writes land in the host page cache either way.) ReadOnly, Timeout (the driver exits 10), IoError and a client that never reads replies are untested; the leak checks cover the driver's own job (processes, pages) but not the DMA VMO, channels or interrupt object; the in-flight-kill test kills a driver with a queued write but cannot know the device was mid-request; acceptance 8's `blk_bad_requests` is folded into `blk_round_trip`.

#### Why it was acceptable

The round trip, bad requests and restart all run on QEMU in both interrupt and polling mode.

#### Proper fix, and when

A read-only device and a stalled device in the harness.

### T122: A flaky volume test in the fail-demo build

*(area testing, horizon someday, risk M)*

#### Shortcut

**A flaky volume test in the fail-demo build** (2026-11-17): twice in two PRs the `harness (fail-demo)` job failed on a volume test (the volume manager test, then the symlink test after it) with status -7 (peer closed) on the first request to a freshly started volume server, and passed on rerun; three local runs of the same kernel were clean. Probable cause: `volmgr` published the names as soon as it started `fsd`, so a client could be connected to a server that then exited (the exit was silent). Changed: `fsd` says why it exits, `volmgr` publishes only after `fsd` reports ready (the `Ready` role) and retries failed starts, and the tests kill their services when they fail. **Not reproduced, so not proven fixed**: if the job flakes again the log now names the exit reason.

#### Why it was acceptable

Removes the one race found by reading the code.

#### Proper fix, and when

Watch the fail-demo job; if it recurs, read the `fsd: exit N` line.

(Migrated from the old TIDY-UP register, section "Concurrency and kernel structure", 2026-11-18.)

### T269: Soak at four harts on a hosted runner: blk_round_trip failed and seven device tests followed it (one occurrence)

*(area testing, horizon near, refs [T40, T44, T252])*

**What.** Soak run 45526124119 (2026-11-25, `main` at d518353), job `smp`, `OS_SMP=4 os_boot_test.py` on the normal kernel: `blk_round_trip` failed ("the reply carries the boot image: got (-12, 0), want (0, 1)"), then `blk_driver_restart`, `devmgr_starts_blkd_for_the_disk`, `interrupt_object_fires_and_masks`, `fsd_keeps_files_across_a_restart`, `volmgr_serves_volumes_by_the_table`, `symlinks_are_followed_by_the_client_not_the_server` and `init_runs_in_user_mode_and_passes` failed with "map the window: InvalidArgs" (AIA interrupts taken 0). The two-hart boot before it passed. Not reproduced: a local four-hart boot of the same kernel passed (391 tests), and the CI re-run's four-hart boots passed. The earlier soak of 2026-11-23 (run 45199049626) also failed in the `smp` job.

**Why acceptable.** Nothing else points at a kernel fault: T40 records that at four harts a boot sees stalls of 15 to 90 ms on hart 0 which timed out `blk_round_trip` before, and the seven later failures look like a cascade from the first (the driver was left in a state where its window could not be mapped again). Unproven.

**Risk.** If it is a real race in the block driver restart or the window map, it is hidden behind a load-dependent timeout.

**Proper fix.** On the next recurrence keep the failing-boot log (the job uploads it) and read what `blk_round_trip` saw first (-12 is the status to find in the driver) and whether the later `InvalidArgs` is a leaked window from the dead driver. If it never recurs in three soaks, close it as load noise.

## Stability epic (2026-11-27)

**Causes to name.** T209: was the volume never published within 15 s because the budgets do not nest (5 s per Busy device plus
15 s for `fsd` to mount, against the test's 15 s), or because a probe that failed once while the old driver wound down
ignores the device for good (`volmgr.rs`, T265's plan, row T209)? T269: what timed out first, and does a killed `blkd` leave a
BAR mapping, a domain or an interrupt the next one is refused? T122: does it recur at all on the current code (`fsd: exit N`
is printed now)?

**Scope (one PR).** The T209 plan's (a), (b), (c) (T265's plan, section 2 item 4: a bounded probe retry when the device was
Busy a moment before; the test's wait covering the server's own budgets; each `volmgr` stage logged with the clock), T44's
read-only and stalled devices in the harness, and the fix of whatever the evidence names.

**How to investigate.**
- Read the logs first. T209's first occurrence is PR 383's epic gate (smoke a, 2026-11-21): find the run (`gh run list
  --workflow ci.yml`) and read its `volmgr:` lines; T269's is soak run 45526124119, job `smp` (`gh run view --log`): read what
  `blk_round_trip` saw before the -12 and the driver's lines.
- Make the slow device deterministic instead of waiting for a loaded runner: QEMU's block throttling
  (`throttling.iops-total=`, `throttling.bps-total=` on the drive) and `blkdebug` error injection (`-drive driver=blkdebug,...`
  with a rules file: delay or fail the n-th request) give a disk that is slow or fails on cue. T44's read-only device is
  `readonly=on`. These are QEMU features (no OD); check `check-qemu.sh` still accepts the command line.
- Then the restart: a suite test that kills `blkd` mid-request with the throttled disk and starts the next one, and the volume
  manager test with the first probe failing on cue.
- Repeat to count, bounded: `make os-repeat TARGET=os-ktest-4 N=15` (the kernel-only shard has the PCI disks and `blkd`; about
  an hour) with and without throttling. Rule 11: five failed attempts at the same target before calling a sighting
  intermittent; keep the logs in `target/repeat/`.

**Acceptance (each run under two hours).** A host test of `volmgr`'s retry decision behind a pure function (Busy-then-probe-fails
is retried within its bound; a non-volume is not); the throttled-disk and failing-probe suite tests fail on today's code (or
show the budget overrun) and pass after; T44's read-only and stalled-device tests exist and pass (ReadOnly, Timeout, IoError
statuses each asserted); each part is struck on its named cause (OD160) or, if the cause is not shown, left open with the
record of what was run. Review by Opus.
