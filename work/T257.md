### T247: The scheduler core allocates on sleep, wake, spawn and migration (class N, with a reserve)

*(area kernel, horizon long, refs [KT9, T177, T246])*


**What.** `kcore::sched2` (`RunQueue`, `timers`, `hard_timers`, `demoted`, the per-hart `threads` maps) and `kernel/src/thread.rs` (`Kernel::threads`, the queues) grow with the infallible collections whenever a thread is spawned, sleeps, wakes or moves. They are class N (T177): inside `heap::nofail` or with a `TT`/`RQ` lock held, which the allocator's reserve (1 MiB plus 256 bytes per live kernel stack, `heap::reserve`) lets through when class R is refused.
**Why acceptable.** A thread that exists cannot be refused a wake, so the scheduler cannot report `NO_MEMORY`; the reserve keeps room for the allocations the population makes, and the population cannot grow once class R is refused (thread creation is an R point).
**Risk.** The reserve is an estimate. A fragmented free-list heap may not serve one large growth of a queue (one priority level with tens of thousands of threads) even with the reserve free.
**Proper fix.** Per-thread nodes made at spawn (intrusive run queues, a timer heap of slots), so that wake, sleep and migration allocate nothing. When: the next time `Sched2` is opened, or the FZ1 review.

### T248: Class N outside the scheduler: teardown and kill, exception delivery, the donation graph, PI futexes, pager waits

*(area kernel, horizon long, refs [KT9, T177, T246])*


**What.** Process teardown and kill (`request_kill`, the exit paths), exception delivery (`ksys/src/exception.rs`), the donation graph (`kcore::donate`), PI futexes (`kcore::pifutex`: four maps) and pager waits (`kcore::pager`) allocate with the infallible collections, inside `heap::nofail` (counted per file by `scripts/check_docs.py`, `NOFAIL`). None is in KT9's scenario list.
**Why acceptable.** Each runs for a thread or process that already exists and cannot be refused (a kill, a wake, a fault report); the allocator's reserve covers them (T247).
**Risk.** As T247: an estimate, defeated by fragmentation.
**Proper fix.** Prepay each from the thread record (`ksys::UThread`) or the process record at the R point that creates the thread, so that the later step allocates nothing; the `NOFAIL` row of the file then goes. When: with T247, or when one of them is opened.

##### 0. What the code says (corrections to "What" above)

The item says every site is inside `heap::nofail`. Reading the callers, **four are not**, and they are worse than class N: they use the
infallible collections as class R, so a refused allocation is a kernel panic (`handle_alloc_error`), in the single-failure sweep and under
real exhaustion once class R is refused below the reserve:

- **`futex_lock_pi` / `futex_unlock_pi`** (`kernel/src/user/waits.rs` 195, 272; dispatched bare at `trap.rs` 949-950). `PiFutexes::lock`
  does `recs.entry().or_insert_with`, `waiting.insert`, `owned.entry().or_default().insert`, and returns `Vec<Change>`; `unlock` does
  `outcomes.insert`, `owned.entry()`, a `rest: Vec<Tid>` copy. They run under `FUTEX` then `PI`; `is_class_n` (`heap.rs` 202) knows only
  `nofail_depth`, `Tt` and `Rq`.
- **A pager wait** (`waits.rs` 375 `pager_wait`, from the page-fault path `trap.rs` 821 and from two in-call paths): `ksys::pager::
  pager_wait_begin` -> `Pagers::wait` (`waits.insert`, `requested.insert`, `unsent.push_back`), `pager_flush`'s `msg` vector, the `woken`
  vectors, `pending_wake.extend`.
- **Fault delivery** (`trap.rs` 879 `raise_fault` -> `ksys::exception::deliver` -> `offer`): the object and handle creations are fallible and
  undone (the level "does not take it"), but `msg` (`exception.rs` 131, 40 bytes) is an infallible `Vec`.
- **`teardown_take`** on the exit path (`lifecycle.rs` 209, reached from `leave`, which is not under `nofail`): `Futexes::forget_process`
  collects a vector when a sleeper of the process is still queued (the backstop case only).

None has a guest scenario (which is why the sweep is green). They are the first things to fix; PR A starts with them.

Also read: `Changes` (`donate.rs` 40) is already a fixed array; every `.to_vec()` of it in `thread.rs` 1258-1303 exists only because
`pi_op` takes a `Vec<Change>`. `AsLocks::all` (`aslocks.rs` 90) allocates only when the boot scratch is out or `procs.len()` exceeds
`AS_HELD_MOST` (64, which `Backstops::processes` is clamped to, `limits.rs` 48).

##### 2. Data structures

**`kcore::donate::Donations`**: `nodes: FMap<Tid, Node>`, `Node { base, eff, out: Option<Tid>, first_in, next_in, prev_in: Option<Tid> }`,
`reserve_thread() -> Result<(), NoMem>`. `recompute` and `height` walk the list (both are order-free: a max). `audit` additionally checks
that every `out` edge is on exactly one list and the lists have no cycle.

**`kcore::pifutex::PiFutexes`** (one per futex bucket):
```
recs:    FMap<Key, Rec { owner: Tid, waiters: VecDeque<Tid> }>      (a record exists only while somebody waits)
waiting: FMap<Tid, Waiting { key: Key, outcome: Option<Outcome> }>  (`outcomes` folded in: a hand-over or a death is a field write)
to_wake: Vec<Tid>                                                   (capacity >= waiting.len(), kept across drains)
```
`owned: BTreeMap<Tid, BTreeSet<Key>>` goes: `owned_keys(owner)` is a scan of the bucket's `recs` (thread exit only, behind `PI_USED`),
exposed as `next_owned(owner, after: Option<Key>) -> Option<Key>`. `still_waiting(t)` is `outcome.is_none()` on a present record;
`take_outcome` removes it. Every count is bounded by the waiters (one `Waiting`, at most one `Rec` and one `VecDeque` slot per waiting
thread), so the one reservation in `lock` pays for the whole later life: hand-over, `cancel`, `dissolve`, `owner_died`, `forget_process`.
`VecDeque` and `FMap` removal never allocate. The `Vec<Change>` results become the sink of section 1; `drain_wake` becomes
`drain_wake(&mut self, f: impl FnMut(&[Tid]))`. `owner_died` handles one key per call (`owner_died_one(dead, key, word)`), so
`pi_thread_gone` is a loop of: next owned key, resolve its word, `owner_died_one`, poison, wake from `to_wake`; its four collections go.

**`kcore::pager::Pagers`**:
```
pagers:   FMap<u64, ()>                (existence; `create` is try_insert)
waits:    Vec<(Tid, Wait)>             capacity >= admitted; push at `wait`, swap_remove at `cancel`; lookups are linear in the current waits
unsent:   VecDeque<Request>            one queue for all pagers, capacity >= admitted (`unsent(pager)` is the first of that pager)
woken:    Vec<Tid>                     scratch, capacity >= admitted
admitted: usize
```
`requested: BTreeSet` goes: a page is requested exactly when a wait without a result names it, which is what `cancel` already computes
(`pager.rs` 181). `cancel` already drops the unsent request with the last waiter, so `unsent.len() <= waits.len() <= admitted` holds; the
audit asserts both. Rejected: the wait as a `UThread` field (zero bookkeeping, but `finish` would walk every thread of the system per
supply, and `pager_model` would lose its self-contained table). Linear lookup is acceptable while pager waits are few; if `pager_model` or a
benchmark says otherwise, index by `FMap<Tid, u32>` reserved in `admit`.

**`UserState`**: `job_exc: FMap<JobId, Handle>`, `pager_ends: FMap<u64, Handle>`; `pending_wake` reserved by `Pagers::admit`'s caller.
`reserve_thread` gains `self.pagers.admit()?`; `unregister_thread` gains `retire()`. No new field in `UThread` is needed: the per-thread
records of this item live in tables keyed by tid that are reserved at the thread's R point, which is what "prepaid from the thread record"
comes to.

##### 6. Blockers and decisions (nothing here is decided by this plan)

- **D1 (owner decision, `kind: decision` item to file with PR A).** A fault that cannot be delivered for want of memory (the exception
  object, the thread handle, the queued message) is today passed to the next level and finally ends the process. The alternative is to
  prepay one exception object and message per thread while a channel covers it, which a job channel makes unbounded to track. This plan
  keeps today's behaviour and writes it down in SYSCALLS.md. KERNEL-V1-SPEC 3.6 does not say; 4.2 says only "NO_MEMORY, never a panic",
  and a fault has no status.
- **D2 (spec text, not changed).** SCHED-SMP-SPEC (the `futex_lock_pi` entry at line 1330) lists `futex_lock_pi`'s errors without NO_MEMORY. SYSCALLS.md already
  lists more than the spec (NOT_SUPPORTED, SHOULD_WAIT), and `futex_wait` gained NO_MEMORY the same way in PR 3a, so PR A follows that
  precedent in SYSCALLS.md only. If the owner reads the spec's list as closed, PR A's lock path needs the per-thread prepay instead (an
  `admit` per bucket is not possible; it would need one `PiFutexes` wait record per thread in a global table): say so before PR A starts.
- **D3 (`job_kill` never reports NO_MEMORY).** This departs from T177's review note, which listed it as reportable. No spec text is
  involved; noted so the owner can object.
- Not a blocker: `kcore::jobsched::sync_budgets` (called by `job_set_sched`) was not read; if it allocates it needs a reserve at
  `job_create`.

### T163: Exited detached threads are freed inside finish_switch under the big lock, not from a per-hart dead list at a safe point

*(area sched, horizon near, risk L)*


#### Shortcut

L11c part 1 (PR 262) frees an exited detached thread in `finish_switch` (`reap_if_dead`), with interrupts off and the big kernel lock held, where SCHED-SMP-SPEC 3.6 has `finish_switch` move it to `PerHart.dead` and the hart reap at a safe point (`preempt_point()`, return to user, idle) with no lock held, plus `reap_quiesce()` for leak oracles. Review (Fable, 2026-11-19): the work (stack scan `note_stack_use`, map remove, heap and stack frees, two scheduler lock takes) is now charged to whichever thread resumes, possibly an RT thread, where the reaper thread paid it before. The safety argument depends on the big lock covering exit through `finish_switch`; `join` of a joined thread relies on the same.

#### Why acceptable

The lock follows the thread until L12, so no reap can race a switch; the leak tests pass. The work is the same as the reaper's.

#### Proper fix, and when

L12 (the scheduler leaves the big lock): per-hart `dead` list filled by `finish_switch`, drained at the safe points, `reap_quiesce()`, and `join` using the same hand-over; check B3 wake latency before and after. Do it with L12.

### T191: A process has no list of its own threads: finding them scans every thread in the system

*(area kernel, horizon long, refs [AB3])*


Found while debugging the phase 5 epic gate (2026-11-21). `wake_threads_of(pid)` (`kernel/src/user/wake.rs`) finds the threads of a process by walking `thread_pid`, the global map of every user thread in every process, and filtering by pid: O(all threads), not O(this process's threads). The process record has no complete list of its own threads: `Process::thread_objs` holds only threads that have a handle and an object, so a detached thread (`thread_spawn` with DETACHED) is in none. The caller was also quadratic (it ran on every thread exit; fixed in PR 331, which restricts it to whole-process exits), but the lookup is the wrong shape even for a kill. Proper fix: a per-process set of live tids (`BTreeSet<Tid>` or the like) kept in step at spawn, start and exit under the same lock, and used by `wake_threads_of`, the kill and suspend paths and `threads_alive` (which becomes its length, so the two cannot disagree); then look for other places that scan a global map by pid (`thread_pid`, `starts`, `stacks`, `interrupts`). A host test in `ksys` that a process's tid set equals the threads the scheduler has for it after random spawns, exits, kills and detaches. Why acceptable: after PR 331 the scan runs once per whole-process exit or kill, and the thread counts are bounded (`MAX_USER_THREADS` 4096). Risk: a kill of a small process while thousands of threads exist elsewhere costs a walk of all of them under the big lock.

Progress (2026-11-21): `Process::live_tids` is built and used: `wake_threads_of` and the teardown now walk the process's own set (no walk of `thread_pid`); the set is added to when a thread registers on its first run and removed at its exit. Still open: `threads_alive` could be the set's length (a thread that is created but has not yet run is counted by `threads_alive` and is not in the set), a host test that the set equals the scheduler's threads of the process across random spawns and kills, and the look for other global maps scanned by pid. Close with the epic.

### T192: Sweep the kernel, the servers and the libraries for quadratic-time (or worse) algorithms

*(area kernel, horizon long, refs [T191])*


The phase 5 epic gate failed at four harts because every thread exit woke every sibling and scanned every thread: O(n^2) for n threads, minutes for 2047 of them, and invisible at one hart (the test took under two seconds). It had been there since slice W and passed because the machine was fast enough. Nothing looked for it: the tests that exist check behaviour, not how cost grows. The sweep: (1) read every loop over a collection in `kernel/`, `kcore/`, `ksys/` and the servers (`init/src/bin/*`, `svc`, `pathres`, the net crates) for one that sits inside another loop or inside something called once per element (a scan per syscall, per wake, per exit, per packet, per directory entry, per handle); give each a verdict (bounded by a small constant, by a quota, or unbounded) and list the unbounded ones as items or fix them. Look at the global maps keyed by process or thread id first (`thread_pid`, `starts`, `procs`, `objs`, the wait table, the futex table, the port bindings, the job tree, the VMO store `find_gap`), the free-list and cursor searches, and `Vec::remove(0)`, `contains` on a `Vec`, `retain` and `sort` inside loops. (2) Add a scaling check to the suite: the cost of an operation at n = 64 and at n = 1024 (threads, handles, mappings, bindings, children, directory entries) must grow less than a set factor, using the guest's instruction counter (`os-count` already has it), so a quadratic path fails a gate instead of timing out one. (3) The tests that take more than 5 seconds of guest time (`thread_limit_and_slots_are_reused` and `two_thousand_threads_live` were 50 to 90 seconds at four harts) get progress marks so a stall report shows where. Why acceptable: the known case is fixed (PR 331) and the counts are bounded by the quotas. Risk: another path of this kind fails a gate on a slower runner, or a system with many objects is slow for no visible reason.

Progress (2026-11-21), a first pass by grep for loops over collections in `kernel/`, `ksys/` and `kcore/` (`retain`, `iter().filter`, `contains` on a `Vec`, sums over `procs`): the two unbounded ones found were the per-exit sibling wake and the pid scans of `thread_pid` (fixed: PR 331 and T191). What is left looked bounded by a constant or by a quota: `total_threads` (a sum over the live processes, at most a few dozen, on each thread creation), the run-queue and timer-queue `retain` in `sched2` and `sched` (one queue, at most the 4096 user threads), the wait table's `retain` over the waiters of one object (a mass wake of 2047 threads on one event is quadratic in the waiters but runs in about a second in the thread-limit test), `futex` and `ipc` bindings (bounded by the job's object quota). Not done: the pass over `init/src/bin/*`, `svc`, `pathres` and the net crates; the scaling check in the suite (part 2: instruction counts at n = 64 and n = 1024 live threads, handles, mappings and bindings); the progress marks for the slow tests (part 3). The grep cannot show a cost that grows through a path that looks constant (an operation that walks a list the caller made long), so part 2 is the real test.
