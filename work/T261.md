### T189: AB3 leftovers: no boot reaches the u64 end of the thread-id, koid or object-generation counters, and the ff= run is not self-verifying

*(area kernel, horizon near, refs [AB3, CNT1])*


Left from the Fable review of AB3 (2026-11-21). (1) The only counter boot is `ff=...:0xfffffff0` (the 2^32 crossing); the end of the u64 range (`ff=tid:0xffff_ffff_ffff_f000` and the like) is covered by host tests only, and there is no kernel test for the purpose (create threads and objects across the boundary, ids distinct, joins work, user thread creation refused with NO_MEMORY at the end). (2) `dtb::ff_value` returns `None` on any parse failure and nothing prints the applied values, so a typo or a dropped `OS_BOOT_ARGS` gives a green, vacuous run: print the applied values and have the harness require the line. (3) The VMO store's generation is 32 bits and retires a slot at `u32::MAX` (`kcore/src/aspace.rs`): correct, but untested and with no `ff=` name; a retired slot stays in `slots` for ever. Why acceptable: the host tests cover the counters and the boundary boot shows no 32-bit assumption is left. Risk: an end-of-range path that panics in the kernel (user thread creation is guarded by a headroom check, kernel threads are not).

Progress (2026-11-21): part (2) is done: the kernel prints `##FF <name>=<value> ...` (or `##FF ... error ...`) for the `ff=` boot argument in a test build, and `scripts/os_boot_test.py` fails a run whose `OS_BOOT_ARGS` carry `ff=` when the line is missing or has an error (checked by hand with a good list, an unknown name and an unreadable value). Still open: (1) the end-of-range boots and a kernel test for the purpose, (3) the VMO store's 32-bit generation.

Experiment (2026-11-24): `ff=tid:0xffffffffffffff00,...` (256 ids left) runs the k shard into `thread.rs:592 valid priority: Exhausted`: a kernel thread cannot be created once the id space ends (user thread creation is refused earlier by the headroom check, as designed). So the end-of-range boot needs a dedicated test that stops creating threads at the headroom and checks the refusal, not the whole shard; that test is still to be written.

### T190: AB3 leftovers: the process id is not the process object's koid, the ASID is derived from the pid, and three counters saturate

*(area kernel, horizon long, refs [AB3, CNT1, T66])*


Left from the Fable review of AB3 (2026-11-21). (1) KERNEL-V1-SPEC 3.3 says the process id is the process object's koid; the code keeps a separate `next_pid` counter and loader-started processes have no process object. (2) The ASID is still `(pid & 0xffff)`: two live processes 65,536 pids apart share an ASID (L18/T66 own the ASID allocator; spec 3.3 forbids deriving it from the pid). (3) The koid counter, the FP/vector tokens (`kcore::fp::Tokens`) and the legacy scheduler's `next_tid` (`kcore/src/sched.rs`) saturate or add unchecked at the end of u64; saturation would repeat a value (a token match would let a thread run on another's registers). Unreachable in 2^64 events but the comments say "stop": make them refuse. (4) SYSCALLS.md `futex_lock_pi` puts the owner's tid in bits 0-29 of a 32-bit word, which cannot hold a u64 tid: amend it when the call is built (decision item then). Why acceptable: none is reachable in a boot's lifetime; the test-only `ff=` can reach (3).

### T205: L18 leftovers: shootdowns are whole-TLB on every other hart (no `ran_on`, no ASID or range batching), a process can run under two ASIDs, and the ASID-reuse control is unobservable on QEMU

*(area kernel, horizon long, refs [L18, T64, SC2])*


L18 part b removed every flush at an address-space switch: installing a user space (`activate_current`, `enter_user`) and leaving one for the kernel table (`use_kernel_table_if_needed`) write `satp` and nothing else (translations are tagged by ASID; ASIDs are unique per generation and a hart flushes at a generation change). Teardown, the kernel-table installs at boot and secondary-hart start keep their flush. What it did not build:

1. **`ran_on` and batched shootdowns** (KERNEL-V1-SPEC 5.4, SCHED-SMP-SPEC 3.10): `smp::shootdown` still asks every other online hart for a whole-TLB `sfence.vma` (every ASID), where the spec has an unmap collect up to 64 page ranges and flush only the harts the address space ran on, by ASID and range. Why acceptable: a whole flush on every other hart is a safe superset, TLB2 holds, and at four harts the cost is small. Risk: the cost grows with the harts (SC2 measures it at 16 and 32).
2. **The negative control** `fault-asid-reuse-no-flush` (a feature of the kernel) skips a hart's flush at a generation change and counts the ASID field as one bit, but QEMU drops its translations whenever `satp` is written, so no boot can show a stale translation under a reused ASID: the host model (`kcore/tests/asid_model.rs`, mutation-checked) is the oracle, and the control is not run by a soak target. Correctness on hardware is by review only (PL7 is in the same position).

Proper fix: 1 with SC2 (the `ran_on` mask is the per-address-space hart set, cleared when a hart goes offline: PM1); 2 on a machine that implements ASIDs in its TLB (real hardware, or an emulator that does).
3. **A process can run under two ASIDs at once.** A thread on hart B keeps running under its old token through the lock-free returns (`lock_free_syscall`, the quiet tick and IPI: none call `activate_current`) after another hart refreshed the process's tag. It is harmless now because shootdowns flush every ASID and hart B flushes everything at its next full-path install (its `asid_seen` is behind); the fault path flushes with the ASID in `satp`, not the tag. Any future shootdown **by** `tag.asid` (item 1) must also reach harts still running under an older ASID of that process (flush the old ASID too, or keep a per-process list of the ASIDs it ran under in this generation).
4. **ASIDLEN 0 hardware** (`asid_bits` clamps to 1; `satp` reads back 0 so `aspace_current() != token` is always true and every return reinstalls) is correct but slow, and the width is probed on one hart only: harts with different widths are not handled.

### T236: The system library's data page is a snapshot (`harts_online`, the cache-block sizes); the kernel still answers the old call shapes

*(area kernel, horizon long, refs [AB7, AB8])*


**What.** AB7 fills the library's data page once, when the first process starts: `harts_online` is the count at that moment (it is not rewritten when PM1 takes harts offline or back), and
`cbom_block` and `cboz_block` are 64, the size on QEMU `virt` and on the RVA23 machines in sight, not read from the device tree's `riscv,cbom-block-size` and
`riscv,cboz-block-size`. The kernel also still answers `clock_get` and the other calls the library will replace (the spec lists `port_wait` and `clock_get`). **Why acceptable.**
Nothing in the tree reads these words yet (`rt` reads the page only in a test), and the old numbers are what the kernel's own tests and AB8's shuffling need until the
numbers go private. **Risk.** A program that trusts `harts_online` after a hart goes offline reads a stale count; a machine with other block sizes gets a wrong
`cbom_block`. **Proper fix.** Read the block sizes from the tree at boot, rewrite `harts_online` in `hart_set_online` (write the page again), and remove the
kernel's `clock_get` when AB8 makes the numbers private.

### T237: A program that starts without a system library cannot make a call; the process record keeps the library's range, nothing enforces it yet

*(area kernel, horizon long, refs [AB7, AB8])*


**What.** `rt` stops the program (`unimp`) when a call is made and no library was found (`a2` was 0 or not the library), and the kernel does not yet refuse an `ecall` from outside the library's text range, which `Process::libsys` records.
**Why acceptable.** Every process is started by `process_start` or the loader, both of which map the library; the enforcement is AB8, which has the kernel refuse an `ecall` whose `sepc` is outside `libsys.text`. **Risk.** Until AB8 a program written with its own `ecall` still works. **Proper fix.** AB8.
