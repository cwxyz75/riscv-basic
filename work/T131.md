## Shortcut

**`/proc` (UV6) shortcuts** (2026-11-17):

- (1) the view is the session's, not the reader's: every program in a session sees every program the session's shell started and has not yet waited for (UVI3 asks for the holder's own handles; a program holds none until it spawns its own children, so a per-program scope needs the process server to track parentage)
- (2) pids are the shell's own job numbers, not kernel ids, and `self` does not exist (procd cannot tell who is reading; a connection tagged with the reader's pid would give it)
- (3) `ps`, `free`, `nproc` and `/proc/<pid>/{status,stat,cmdline}` only: no `environ`, `fd/`, `task/`, `maps`, `ns`, `mounts`; `stat` is `pid (name) state`, not Linux's 52 fields; no start time or CPU time because the kernel does not keep them per process
- (4) `/proc/loadavg` averages are 0.00 (nothing measures load), `uptime` idle is 0.00, `meminfo` has the three fields `free` needs, in the session job's pages; `cpuinfo` is one bare `processor` stanza per online hart (`job_info` 7: there is no CPU affinity)
- (5) the shell tells `procd` about a program after the launcher returns, so a program that asks at once could in principle ask first: `procd` reads the control channel before every request, which makes the race a matter of microseconds against a program's start-up, not removed
- (6) confined shells get `/proc` read-only like `/dev` and `/tmp` (no grant is needed)
- (7) the `/proc` connection is a read-only tree, and the shell's own `>` redirections cannot reach it, so the write refusal is not exercised by a test.

## Why it was acceptable

Gives the corpus programs (`ps`, `free`, `nproc`, `top` later) what they read, scoped to what the session itself started.

## Proper fix, and when

- (1) and
- (2) with the process server of S11 (`fork`, pids, parentage)
- (3) as programs ask
- (5) by starting a program only after `procd` acknowledged it, which needs the launcher to take a start gate.
