### T180: The direct map reaches 64 GiB of physical space; the spec's target is 128 GiB of RAM, and QEMU puts the device tree at the top of RAM

*(area platform, horizon long, refs [PL4, KERNEL-V1-SPEC, SC1])*


PL4a (memory discovery) maps physical space through the direct map at `DIRECT_BASE`, and stops at `abi::layout::DIRECT_MAP_PHYS_LIMIT` (64 GiB, top-level slots 256 to 319) because slot 320 is the self-test region, 384 the kernel stacks, 416 the heap and 510 the image. RAM starts at 2 GiB on `virt`, so the most RAM it can use is about 62 GiB, against the spec's "up to 128 GiB of RAM" (KERNEL-V1-SPEC section 1). Two consequences, both loud and neither silent: RAM above the limit is left unused (the kernel prints `kernel: RAM above 64 GiB is not used`), and a machine whose firmware puts the device tree above the limit, as QEMU does at the top of RAM (`-m 80G`: the tree sits near 82 GiB), stops at boot with `a device tree below 64 GiB ...`, because the tree cannot be read before the kernel table exists. Why acceptable for now: the development and CI machines have a few GiB, and PL4a's acceptance sizes (128M to 8G) pass. Risk: a larger machine does not boot. Proper fix: move the self-test region (`LAZY_TEST_BASE`), the stack window and the heap window to slots above the direct map's 128 GiB span (they are layout constants with tests: `abi::layout`), raise `DIRECT_MAP_PHYS_LIMIT` to 128 GiB and the early table's loop with it, and for the device tree above the span either map its page through a small temporary window or move the early table's reach with the tree's address (the pointer is known in `a1`); add a boot test at the largest RAM the host can give. SC1 (64 harts) touches the same layout and is the natural place.

### T181: PL4's literals check misses frame-number and other spellings, rt, init and build.rs; the early boot code stops silently on an unmappable image

*(area platform, horizon long, refs [PL4])*


Left from the Fable review of PL4c (2026-11-20). (1) `scripts/check_docs.py check_ram_literals` matches `RAM_SIZE`, `RAM_BASE`, `KERNEL_PHYS`, `KERNEL_OFFSET`, `0x8000_0000` and `0x8020_0000` in `kernel/src`, `kcore/src`, `abi/src` and `ksys/src` outside test code. Not caught: frame-number forms (`0x80000`, `0x80200`), other spellings (`0x8_000_0000`, uppercase `0X`, decimal, `2 << 30`), `rt/`, `init/` and `kernel/build.rs`; `selftest.rs` and any file named `*_tests.rs` are exempt wholesale (the `low_half_is_empty` test still probes the old addresses on purpose). Device addresses (`0x1000_0000` in `console.rs` and `kmem.rs`) are PL5's. A shift pattern was left out because `abi` has `Rights(1 << 31)`. (2) `_start` stops in a `wfi` loop, with no console to say why, for an image that is not 2 MiB aligned, starts at 64 GiB or beyond, or is over 1022 MiB; `build.rs` now refuses a misaligned `KERNEL_LMA` at build time, but a loader that puts the image at an odd address still hangs silently. Proper fix: a one-character write to the UART at the stop (the 16550's data register at its fixed early address is the only device the early table maps anyway), once PL5 has the console address from the tree. Why acceptable: QEMU and OpenSBI load at 2 MiB multiples, and the build refuses the rest. Risk: a silent hang on a board with a different loader.

### T182: PL5b leftovers: a failing release kernel exits 0, the fallback console has no input, the early boot has no fault handler, the console's bus is not checked for translation

*(area platform, horizon long, refs [PL5, PL4])*


Left from the Fable review of PL5b (2026-11-20), after the findings that were fixed in the PR (the discovered addresses bounded, the tree read after `percpu::bind`, no alias table, a UART with a register shift or width or a disabled status refused, the legacy console call when the firmware lacks DBCN, the stop loop with interrupts off). (1) **A failing release kernel exits with status 0.** `finisher::exit` in a `release`-feature build ends through SBI SRST with the failure reason; from memory of OpenSBI and QEMU the reason does not become a nonzero exit status (QEMU exits 0 for a poweroff unless started with `-action panic=exit-failure`), so a harness that runs a release kernel sees success and has only the `##PANIC` line and the transcript (`scripts/release_smoke_test.py` checks `system halted`). The same holds for a test build whose tree has no test device. Proper fix: measure what SRST with a failure reason does on the QEMU and OpenSBI in use, and either start the release harness with `-action panic=exit-failure` or keep the test device for a failing release run when the tree has one. (2) **The fallback console has no input**: `console::try_read` returns `None` without a UART, so an interactive build on a machine without a 16550 has a mute shell; DBCN read (function 1) is the fix. (3) **No fault handler before `trap::init`**: nothing in `arch/riscv64` writes `stvec` earlier, so a fault in `dtb::locate` or the early walks (a firmware pointer inside 64 GiB that is not readable) is a silent hang; a minimal early vector that prints and stops would turn it into a `##PANIC`. (4) **The console's parent buses are not checked for address translation**, as `kcore::devwin` does for device windows: a UART behind a translating `ranges` would be driven at the wrong address. (5) **The wanted boot word cannot be tested without a UART on the machine**: `console=sbi` forces the fallback after the UART lines already went out; booting with `-dtb` of a tree with no `stdout-path` would start on the fallback from the first byte and also exercise the SRST exit if the test node is removed. Why acceptable for now: QEMU is the only machine, its tree names a 16550 with the plain registers, and a wrong choice is loud in a test build (the harness reads the lines). Risk: a hardware port finds these first.

### T183: PL5c leftovers: sources above 63 and unlisted harts are dropped quietly, no IMSIC groups, plain virt (no AIA) is not a tested target

*(area platform, horizon long, refs [PL5, PL6])*


Left from the Fable review of PL5c (2026-11-20), after the findings fixed in the PR (hart order from the IMSIC list, interrupt parent and nexus, irq cell 9, bounds on sources and base, `interrupt_create` order of errors). (1) `aim_and_unmask` returns silently for a hart id not in the IMSIC list (the call to `interrupt_create` still succeeds; the interrupt never arrives). (2) Device sources above 63 are dropped from the table without a boot line. (3) An IMSIC with group-index-bits above 0 (several groups) is refused whole, so the machine has no AIA. (4) `irq_objs.get_mut` for a missing slot is ignored. (5) The per-source allocations are sized by `riscv,num-sources` (at most 1023). (6) Whether plain `virt` without `aia=aplic-imsic` (a PLIC machine) boots and polls is not tested. Why acceptable: QEMU `virt` with AIA is the only target; each case fails loudly or not at all on it. Proper fix: a boot line for the dropped cases and the PL6 work that removes the PLIC remnants.

#### Note (2026-11-25): partly absorbed by the IOMMU epic (T42)

The owner chose MSI-X with MSI remapping for the IOMMU epic (Q-IOMMU-IRQ, answer B), which needs more than 64 interrupt identities per hart file. Points **1, 2, 4 and 5** above (a hart the IMSIC does not list, sources above 63, the ignored `irq_objs` slot, the per-source allocations) are now work of **IOMMU4** (the per-hart identity allocator, all `eie` registers, routes instead of a source-indexed table) and are **not to be done from this bundle**. Still here: point 3 (IMSIC groups) and point 6 (plain `virt` without AIA). Strike 1, 2, 4 and 5 when IOMMU4's epic smoke is green.

#### Note (2026-11-26): IOMMU4 built points 1, 2, 4 and 5

IOMMU4's feature PR (into `epic/iommu-kernel`) does them: (1) a hart the IMSIC does not list has no interrupt file, so `interrupt_create` on it
fails with NO_MEMORY instead of succeeding silently; (2) sources up to `riscv,num-sources` are admitted, and a source a device names past it gets a
boot line (`aia: source N ... not used`); (4) a missing `irq_objs` slot is INVALID_ARGS; (5) the per-source table is sized by the highest source
in use. Identities come from `kcore::msiid` per hart, every `eie` register up to `riscv,num-ids` is driven, and wired sources go through routes.
Nothing struck yet: strike 1, 2, 4 and 5 when the epic's smoke is green.

#### Note (2026-11-27): points 1, 2, 4 and 5 struck (IOMMU12's check)

`epic/iommu-kernel`'s smoke was green and the epic merged into `main` (#595), so the four points IOMMU4 built are **struck**: (1) a hart
the IMSIC does not list, (2) sources above 63, (4) the ignored `irq_objs` slot, (5) the per-source allocations. Nothing of the drivers
epic (IOMMU8 to IOMMU12) touched points 3 and 6. **Still here:** point 3 (IMSIC groups) and point 6 (plain `virt` without AIA).

### T184: PL6 leftovers: the optional interrupt in devmgr, the network driver and the block service's grant

*(area platform, horizon long, refs [PL6, PL5])*


PL6 made the AIA a requirement and removed the block driver's polling mode (`blkd` now exits with code 3 without its `BlkIrq` handle). What remains of the "no interrupt" shapes: `devmgr`'s `Block.irq`/`Net.irq` are `Option<u32>` (an `interrupt_create` that fails, for example a source taken already, leaves the device without one and `blkd` then refuses to start), the network driver's `irq: Option<u32>` and the `NET_FLAG_IRQ` protocol flag (the driver's own safety poll, NET8, stays: it is a different thing). Why acceptable: the AIA machine always gives the interrupt, so the options are never `None` on the one target; the failure is loud for the disk. Proper fix: make the interrupt mandatory in `devmgr` (a device whose interrupt cannot be created is not started and the manager reports it), drop the flag from the protocol with its tests. Also from the PL6 review: the IMSIC span is not checked against the other pages the kernel drives (a malformed tree would alias, not crash), `hart_order` is not capped at `MAX_HARTS`, and `a_wake_preempts_a_lower_priority_hart` does not itself assert zero SBI IPI calls (the counter is global and `ipi_reaches_every_hart` checks it); the 8-hart run is soak-only.

#### Note (2026-11-25): the driver side is absorbed by the IOMMU epic (T42)

With MSI-X in the epic (Q-IOMMU-IRQ, answer B), the "mandatory interrupt" fix is done for PCI claims in **IOMMU9** (a claim without its vectors fails; no `Option` in the reply), for the block driver in **IOMMU10** and for the network driver and `NET_FLAG_IRQ` in **IOMMU11**; the virtio-mmio shapes are deleted there, not repaired. Not to be done from this bundle. Still here: the three points "also from the PL6 review" (the IMSIC span check, `hart_order` against `MAX_HARTS`, the IPI assertion); the `hart_order` cap matters more once IOMMU4 sizes its tables by hart.

#### Note (2026-11-27): the driver side was built (IOMMU9 to IOMMU12)

The absorbed driver side is built on `epic/iommu-drivers`: a PCI claim without its vectors fails whole (IOMMU9, #598), `blkd` takes its
interrupt as a mandatory MSI-X vector from the claim (IOMMU10, #599), and `netdrv` likewise, with `NET_FLAG_IRQ` gone from the protocol
(IOMMU11, #601); IOMMU12 deleted what was left of the virtio-mmio shapes (the kernel admits no virtio-mmio device). It is struck in the
epic's closing commit, when its smoke is green. **Still here** (none of the epic touched them): the IMSIC span is not checked against
the other pages the kernel drives, `hart_order` is not capped at `MAX_HARTS`, and `a_wake_preempts_a_lower_priority_hart` does not
assert zero SBI IPI calls itself.

### T41: Device authority stand-ins (S6a)

*(area drivers, horizon long, risk M)*


#### Shortcut

**Device authority stand-ins (S6a).** The DMA budget is one system-wide constant (`MAX_DMA_TOTAL_PAGES`), not a per-job quota; ~~`DEVICE_WINDOWS` is a hard-coded QEMU `virt` constant~~ (done, PL5: `kcore/src/devwin.rs` builds the windows at boot from the device tree, from an allowlist of `compatible` strings); any number of physical VMOs may alias the same slot (no exclusivity, so two drivers could fight over a device); physical VMOs are pinned to the root job and counted as one object.

#### Why it was acceptable

Only the privileged boot process holds the resource, and the test suite and (S6c) the device manager are its only users.

#### Proper fix, and when

Per-job DMA quota; windows from the DTB; an exclusive-claim record per device slot.


#### Note (2026-11-24)

The windows now come from the device tree (PL5, work item D1). Still open: the one system-wide `MAX_DMA_TOTAL_PAGES` budget instead of a per-job quota, no exclusive-claim record per device slot, and the physical VMOs pinned to the root job.

#### Note (2026-11-25): narrowed by the IOMMU epic (T42)

Two of the three open points are now work of the IOMMU epic and are **not to be done from this bundle** (OD148, OD162, OD164; `docs/specs/IOMMU-SPEC.md` 3.2, 5.3). ~~The one system-wide DMA budget instead of a per-job quota~~: a DMA VMO's pages are charged to a job its creator names (`vmo_create_dma_in`), and two hierarchical per-job limits (I/O-mapped pages, interrupt vectors) are added, with `MAX_DMA_TOTAL_PAGES` kept only as a system backstop: **IOMMU3** (the model and the limit fields) and **IOMMU6** (the calls). ~~No exclusive-claim record per device~~, for DMA devices: at most one live domain per device id, a second `iodomain_create` is BAD_STATE: **IOMMU3** and **IOMMU6**. Still here: any number of physical VMOs may alias the same device window (the exclusive claim above covers a device's DMA and interrupts, not the mapping of its registers), and physical VMOs are pinned to the root job and counted as one object. Strike the two absorbed points for good when the kernel epic's smoke is green.

#### Note (2026-11-26): IOMMU6 built the two absorbed points

IOMMU6's feature PR (into `epic/iommu-kernel`) adds `vmo_create_dma_in(resource, pages, job)` (the pages charged to the named job),
`job_set_io_limits` with `job_info` 12 and 13 (the hierarchical I/O-mapped page and vector limits), and `iodomain_create`'s BAD_STATE
for a device id that has a live domain (the exclusive claim for DMA). They are struck for good when `epic/iommu-kernel`'s smoke is
green; the aliasing of physical VMOs and their root-job pinning stay here.

#### Note (2026-11-27): narrowed to physical-VMO aliasing and root-job pinning (IOMMU12)

The two absorbed points are **struck for good**: `epic/iommu-kernel`'s smoke was green and it merged into `main` (#595). IOMMU12 also
took `virtio,mmio` off the device-window allowlist and retired `vmo_create_dma` and `vmo_phys_addr` (library stubs, NOT_SUPPORTED), so
the old contiguous, physically addressed DMA VMO this part grew up around is gone. **This part is now only:** any number of physical
VMOs may alias the same device window (the exclusive claim covers a device's DMA and interrupts through its domain, not the mapping of
its registers), and physical VMOs are pinned to the root job and counted as one object.

### T59: The AIA path is minimal (slice I)

*(area drivers, horizon long, risk L)*


#### Shortcut

**The AIA path is minimal (slice I).** Interrupt objects run on the AIA (APLIC in MSI mode, one IMSIC supervisor file per hart); the PLIC path is gone, and a plain `virt` board has no interrupt controller the kernel drives (drivers poll). What is still a stand-in (the APLIC base, the IMSIC hart order and the source table now come from the device tree, PL5c; what was left from that is T183): the message id equals the source number; every source is level-high; a message still in flight to the old hart when an object is destroyed and re-created on another hart is taken there as a spurious interrupt (tolerated by drivers) and counts as misrouted, a possible flake of the boot-script check; only QEMU has run it, so a real APLIC's treatment of a still-asserted level after the message (the kernel re-pends with `setipnum` on unmask) and of a storm is unproven.

#### Why it was acceptable

Enough for virtio-blk on QEMU, with delivery to the hart that asked proven by counters (`debug_stat` 3-5).

#### Proper fix, and when

Map the APLIC from the device tree; map hart ids to IMSIC indices from the `interrupts-extended` order; sources and ids from `riscv,num-sources`/`riscv,num-ids`, edge sources, guest files and MSI-based devices (PCI) when a driver needs them.


#### Note (2026-11-24)

Narrowed: PL5c reads the APLIC base (`aia::info().aplic_base`), the hart order (from the IMSIC list) and the sources (`riscv,num-sources`) from the device tree. T183 holds that review's leftovers; this item keeps the message-id mapping, level-only sources, the in-flight message at re-creation, and the unproven real-APLIC behaviour.

#### Note (2026-11-25): partly absorbed by the IOMMU epic (T42)

Q-IOMMU-IRQ was answered B (MSI-X now). **The message-id mapping** (identity = source + 1) and **the in-flight message at re-creation** are now work of **IOMMU4**: identities are allocated per hart for every route, wired sources included, and an identity is reused only after its old hart retired it. "MSI-based devices (PCI)" from the proper fix is **IOMMU7** (the IOMMU's MSI translation and vector interrupt objects) and **IOMMU9** (MSI-X in `devmgr`). "Guest files" are deliberately **not** used (IOMMU7, the design table). Not to be done from this bundle. Still here: every wired source is level-high (no edge sources), and the unproven behaviour of a real APLIC. Strike the absorbed parts when the epic's smokes are green.

#### Note (2026-11-26): IOMMU4 built the message-id mapping and the in-flight message

IOMMU4's feature PR (into `epic/iommu-kernel`) replaces identity = source + 1 with identities the kernel allocates per hart (`kcore::msiid`,
next-fit, 0 and 1 never given), and an identity whose route moved (an acknowledgement on another hart, a hart going offline) or ended (the
object destroyed) is closed, its pending bit read and cleared and a message found there delivered, by its own hart, before it is reused (IO12).
A message in flight at re-creation is therefore not taken as misrouted any more. Nothing struck yet: strike those two parts when the epic's
smoke is green. Still here as before: level-only sources and the unproven behaviour of a real APLIC.

#### Note (2026-11-27): the absorbed parts struck (IOMMU4's check)

`epic/iommu-kernel`'s smoke was green and it merged into `main` (#595): **the message-id mapping** (identity = source + 1) and **the
in-flight message at re-creation** are struck. "MSI-based devices (PCI)" was built in the drivers epic (IOMMU7 in the kernel epic,
IOMMU9 in `devmgr`, used by `blkd`, `netdrv` and `rngd` in IOMMU10 and IOMMU11). **Still here:** every wired source is level-high (no
edge sources), and the unproven behaviour of a real APLIC (since IOMMU12 the only wired device is the RTC; the suite's wired-source
tests use its alarm).

### T84: The network device's DMA memory is charged to `devmgr`'s job, not to the driver's or supervisor's

*(area drivers, horizon long, risk L)*


#### Shortcut

**The network device's DMA memory is charged to `devmgr`'s job, not to the driver's or supervisor's** (`NET-SPEC.md` 4.3: only the root resource can create DMA VMOs, so `devmgr` creates the three net DMA VMOs, 130 pages, and `netsup` receives them through the `OP_CLAIM_NET` claim).

#### Why it was acceptable

The creator pays and only `devmgr` holds the root resource; a per-claimant charge needs a `devmgr` or kernel change that S8 does not otherwise need. Owner accepted it as a shortcut, 2026-11-14.

#### Proper fix, and when

The claimant's job should pay: either `devmgr` creates the VMO with the claimant's job as its charge target (a small `vmo_create_dma` variant that names a job, as `vmo_create` does under OD57), or the root resource can mint a DMA-capable resource limited to a budget that the claimant holds. Do it with the DM follow-ups (T41) or when a second DMA-using driver family exists. Also the blk driver's buffer is charged the same way today.

#### Note (2026-11-25): absorbed by the IOMMU epic (T42)

The whole of this part is now work of the IOMMU epic and is **not to be done from this bundle** (OD162 point 4; `docs/specs/IOMMU-SPEC.md` 4.7, 5.3). The first of the two fixes named above was chosen, as a new call rather than a change in place (OD166 point 9): `vmo_create_dma_in(resource, pages, job)`, built in **IOMMU6**. `devmgr` names the claimant's job for the network device's three VMOs in **IOMMU11** (its check: the 130 pages are on the claimant's job and return when the claim is dropped) and the driver's job for the block driver's buffer in **IOMMU10**. Nothing of this part stays here; strike it when the drivers epic's smoke is green.

#### Note (2026-11-26): the call exists (IOMMU6)

`vmo_create_dma_in` is built (IOMMU6, `epic/iommu-kernel`), so `devmgr` can now name the claimant's job; the use is IOMMU10 and IOMMU11.

#### Note (2026-11-27): built (IOMMU10, IOMMU11); nothing left here

`devmgr` makes the claim's DMA VMOs with `vmo_create_dma_in` charged to the claimant's driver job: the block driver's buffer and rings
(IOMMU10, #599) and the network device's pools (IOMMU11, #601; its check that the pages are on the claimant's job and come back when the
claim is dropped is the suite's). With IOMMU12 the old `vmo_create_dma`, which charged its caller, is a NOT_SUPPORTED stub, so no path
charges `devmgr` for a driver's memory any more. Nothing of this part is left; it is struck in the drivers epic's closing commit when
its smoke is green.

### T235: The shipped release kernel still embeds the suite and test programs; the build feature is `release`, not an inverted `test-kernel`

*(area testing, horizon long, refs [HD4])*


**What.** HD4 part 3 runs the `k` shard on a kernel with the release content (`release-suite`), but `kernel/build.rs` embeds every program, the suite and `crash` included, in the shipped `release` kernel too, and the switch that removes test code is still `release` (test code compiled when it is off) rather than a `test-kernel` feature that the release build never enables. **Why acceptable.** The deny-list symbol check (`release_symbols.py`) shows no test code in the release kernel, and the embedded suite ELF is data that nothing starts. **Risk.** Image size and a tidiness gap in the spec's wording (KERNEL-V1-SPEC 3.8). **Proper fix.** `build.rs` embeds the suite and `crash` only when a feature asks for them (`test-kernel`, `release-suite`); rename the cfgs when the next feature touches them.
