### T233: A kernel panic in the four-hart kernel-only boot: slice::get_unchecked range check (seen once, CI)

*(area kernel, horizon near, refs [T215, T232])*


**What.** CI, PR 478 (a test and harness change, so none of its code is in the kernel shard), job `kernel (ktest 4 harts)`, run 45215984804: after `bystander_cost_of_sleeping_bindings` PASS the kernel printed `##PANIC panicked at library/core/src/slice/index.rs:492:32: unsafe precondition(s) violated: slice::get_unchecked requires that the range is within the slice` and the boot ended. The next test is `a_dead_client_frees_everything` (stream queues, then `process_kill` of the client). The panic location is the standard library's, so the caller is not known; no `get_unchecked` exists in this repository, so the caller is a library function over a range that is not within its slice (an index computed from a length that changed between two steps is the likeliest: T215 made big stream and message copies run outside the object lock).
**Not reproduced:** four local boots of the same shard at four harts passed (macOS, debug build); the second soak's `smp` boots passed.
**Why acceptable.** One occurrence, development only; but it is a possible memory-safety fault, so it stays `near`.
**Risk.** A real out-of-range access on the stream or message copy path under a kill.
**Proper fix.** Find the caller: a panic handler that prints the return address chain (frame pointers), or the same boot repeated until it recurs (`make os-repeat TARGET=os-ktest-4 N=20`); read the staged and deferred copy paths in `kernel/src/user/trap.rs` and `ksys/src/lib.rs` for a range computed before the lock was dropped.

**How to catch it (plan).**
1. *Find the caller from the panic itself.* The panic location is the standard library's, so make the kernel's panic handler (`kernel/src/main.rs`, `fn panic`) print a frame-pointer backtrace (the kernel is built with frame pointers or can be: `-C force-frame-pointers=yes` on the kernel profile; print up to 16 return addresses as hex, and resolve them offline with `llvm-addr2line` against the ELF). That turns every future panic of this kind into a file and line, and is worth having whatever this one turns out to be.
2. *Reproduce it on purpose.* The suspects are the big stream and message copies that run outside the object lock (T215): a stream write or read of 1 KiB or more whose process is killed, or whose peer closes, between the check under the lock and the copy. Write a suite test (a kill storm): a child writes and reads 4 to 64 KiB on a socket and over a channel in a loop while the parent kills it at a random moment, 200 rounds, with the peer's end read concurrently; run it at four harts, release build and debug. A model test on the host (the staged and deferred paths in `ksys` against a model that kills the process at every step of the call) would find a range computed before the lock was dropped without a kernel at all: `ksys` already has the `Machine` seam for it.
3. *Count occurrences.* `make os-repeat TARGET=os-ktest-4 N=20` locally and in the overnight tier (it is in `OVERNIGHT_TARGETS` as the repeat-smp hunt); a failure rate would say whether it is rare (one in fifty) or tied to the runner's speed (it was seen once on a hosted runner, never in four local boots).
4. *Look at it the other way too:* the debug build's UB checks are what caught it. The same range would be a silent out-of-bounds read in the release build, so a release-checked boot (`os-boot-test-checked`, KT12) belongs in the repeat.
**Done when** the caller is named, the fix has a test that fails without it, and `os-repeat` of the four-hart boot passes 20 times.
5. *A reasoning pass (Fable review), later:* give a fresh reviewer the staged and deferred copy paths of T215 (`stage_in` and `dispatch` in `kernel/src/user/trap.rs`, `Staged`, `Deferred` and the socket and channel calls in `ksys/src/lib.rs`) and ask it to reason through every interleaving of a kill, a peer close and a second hart's call between the checks made under the object lock and the copy outside it, and to name any range or length that is computed in one critical section and used in another. Cheap, and it may name the bug before the repeat runs do.

**Step 1 is built** (the second soak's day, 2026-11-23): the panic handler appends `[stack 0x...]` (the kernel-stack words that point into the kernel's text) to the `##PANIC` line of a thread that entered from user mode, and `scripts/resolve_trace.py` names the symbols (`TEST-TOOLS.md`, "Where a panic came from"); checked by a temporary panic in a syscall, which resolved to `trap_epilogue`, `trap_handler`, `user_trap` and the syscall. The next occurrence of the panic names its caller; steps 2 to 5 stay open.

**Second symptom (2026-11-23, epic PR 485, `kernel (ktest release)`, a kernel with the release content at four harts):** the same test, `a_dead_client_frees_everything`, failed with `after the data: end of stream: got Some(InvalidArgs), want Some(PeerClosed)`: a `socket_read` of the queued data of a killed client returned INVALID_ARGS (a user buffer the copy-out refused) instead of draining and then PEER_CLOSED. Same test, same path (a big stream copy against a kill), so it is likely the same defect as the panic above; a rerun of the job passed. Whoever picks up step 2 of this item starts from these two.

**Step 2 is built** (2026-11-23): `a_kill_storm_on_a_stream_loses_no_range` (`init/src/stream_proto.rs`, in the kernel-only shard): 120 rounds of a client writing 4 to 64 KiB while the server reads in 4 KiB chunks and the client is killed at a random read; no read may return anything but Ok, ShouldWait or PeerClosed. It passes at four harts locally (debug); it did not reproduce the defect there, so it stays in the gate as the hunt. The channel variant and the host model are still open.

**Fable reasoning pass (step 5, 2026-11-24): no caller named in the T215 paths** (`stage_in`, `SOCKET_READ`, `finish_out`, `channel_call_send_staged`: no range or length is computed in one critical section and used in another). Candidates, ranked: (1) a `BTreeMap` node read mid-mutation or after free (`btree/node.rs keys()` is the main non-`mut` `get_unchecked(..len)` caller; `VecDeque` uses only the `_mut` variant): audit the kill path's removals from `kernel/src/thread.rs:107` (`threads`), `kernel/src/arch/riscv64/fp.rs:61-69`, `kcore/src/sched2.rs:147,604-617` and `sched_smp.rs:34` against their locks (shuttle/loom, not a `ksys` model); `state()` checks the object lock with `debug_assert!` only and `any_state` trusts `bkl::holds()`. (2) The second symptom: `kcore/src/usercopy.rs:34-39` `resolve` maps every `FaultError` (`NoMemory`, `VmoGone`, `MapFailed`) to `InvalidArgs`, and `finish_out` (`trap.rs:312`) uses the fault-capable `copy_to_user` after the bytes are dequeued: a page that needs a commit or copy-on-write there and fails for memory reports INVALID_ARGS with the data gone. Fix direction: map `NoMemory` to `NoMemory`; use the verified copy or re-queue on failure; host test with `defer_out`, a lazily backed destination and a failing frame allocator. (3) Pager-need slot cross-talk across harts (`pager_after_call`, low). (4) `SOCKET_WRITE`/`CHANNEL_WRITE` trust the staged length (hardening). The `[stack ...]` trace names the caller on the next occurrence.

**Built (2026-11-24):** `usercopy::resolve` maps a fault's `NoMemory` to `NoMemory` instead of `InvalidArgs` (candidate 2's first half). The rest of candidate 2 (`finish_out` after the bytes are dequeued) and the others stay open.

### T212: smoke b panicked once on a big-lock spin of 30 million iterations (phase 9 epic gate; passed on the re-run)

*(area kernel, horizon long, refs [OD140])*


**What.** In the phase 9 epic gate (PR 393, run 44982400526, head 6cff502) `kernel (smoke b)` panicked with "hart 3 has spun for the big kernel lock (last class asked for: 10) for 30 million iterations; the big kernel lock is owned by hart+1 = 2" during the network tests (the log ends in netd gate lines); on the re-run of the same head it passed. Earlier heads of the same epic had passed smoke b.

**Why it is not just re-run.** TESTING.md rule 11: an intermittent kernel-test failure is a defect until its cause is known. A hart that holds the big lock for 30 million iterations is a livelock or a very long section under it. The head in question had L25 (budgets enforced) and L8 and AB6: the candidates are a scheduler settle loop that does not terminate under the lock (pull and push with a throttled hart, `push_queue_from` after a pull), the new `charge_all`/`cpu_ns` reads, or a pre-existing network-test stall.

**Proper fix.** Reproduce with smoke b at four harts in a loop (`make os-repeat`), then print what hart 2 runs when the spin detector fires (the panic names the owner but not its site); fix the loop or the section. Do it in the first slack after phase 9's gate, or if it repeats.

**Update (same day).** A second smoke b failure on the next head was a 180 s stall (no output after `net_driver_attaches_and_exchanges_a_frame`, where `ten_thousand_threads_leak_nothing` runs, 68 s on a laptop). Thread exit had become dearer: `thread::charge_running` took every hart's run-queue lock for each exiting thread, under the big lock, which also lengthens the big lock's hold times (the spin of the first failure is the same cost seen from another hart). Thread exit now charges only its own hart (`charge_here`). If smoke b fails again, the stall is not this cost and the item stands.

### T197: Two failures seen once each on an overloaded host: a starvation-watchdog panic and `kill_a_process_that_is_creating_threads` (not reproduced)

*(area sched, horizon long, refs [T178])*


Seen once each during the first run of `make os-chaos` on 2026-11-21 (a Mac with ten cores, QEMU 11.1.3), when the machine was heavily oversubscribed: three chaos boots at a time at up to eight harts each (up to 24 emulated hart threads) beside builds and other boots. (1) seed 2 at eight harts: `##PANIC ... starved thread 2020: queued on hart 3 for more than 500 ms while hart 4 idles (per hart: ...)` (the starvation watchdog of L11d, `kernel/src/thread.rs`). (2) seed 4 at eight harts: `kill_a_process_that_is_creating_threads` failed with `the process ended: got -12, want 0`, which also failed `init_runs_in_user_mode_and_passes`. Neither reproduced: the same two seeds at eight harts passed four times (twice each, one run alongside ten repeat-smp boots), and the restarted chaos run (150 boots, seeds 1 to 50 at two, four and eight harts, two jobs) had no failure but the load-sensitive `realtime_thread_stays_responsive_under_load` (T178). The likely cause is host starvation of an emulated hart (a hart whose host thread is descheduled for over 500 ms cannot run the thread queued on it, and the watchdog sees an idle peer), but that is a reading, not a proof: TESTING.md rule 8 makes an intermittent kernel failure a defect. What to do: make the watchdog robust to a hart that did not run (compare against the hart's own `timer_ticks` or a progress counter, so a hart that made no progress is not blamed on the scheduler), or show the failure by a deliberate host stall in a run; read what `-12` is for the kill test (a status or an exit code) and whether a thread-creation failure under a kill can end the process with it; and run the chaos kernel at eight harts on a quiet machine for a few hundred seeds when the owner next runs the overnight tier. Why acceptable: not reproduced in 154 later boots. Risk: a real rare race in the starvation detector or the kill-while-creating path.

### 2. Design per part

**T233-a: prove the cause (mutation check, no product change).** Add a chaos point `Point::CopyOut` (`kernel/src/chaos.rs:11-22`) in `trap.rs` between `dispatch` and `finish_out` (`:1077-1078`); under `--features chaos` it delays and yields, so the reader is switched out with the message taken. Extend the kill storm to assert the *bytes* (the client writes a counter pattern; today only counts and statuses are checked, so a copy into the wrong space that happens to succeed passes). Then, once and by hand on a scratch branch, revert the one line of `current_space()` to `percpu.cur_as` and run one chaos boot at four harts (`make kquick` style, an experiment TESTING.md rule 4 allows): expected INVALID_ARGS, a pattern mismatch or the `get_unchecked` panic with a `[stack ...]` that resolves into `finish_out`. Record the outcome in this file. *Rejected:* waiting for a recurrence under `os-repeat` (owner-only tier, and it cannot recur if the fix is the cause); a `ksys` host model (the bug was in `kernel/src/user/trap.rs`, above the `Machine` seam, so no `ksys` model could have seen it).

**T233-b: the trace gap.** Give `Trace` the stack bounds of any thread: read the current thread's stack slot from `sp` itself (`sp / KSTACK_SLOT_BYTES` gives the slot, its top is the slot's top less the guard: `abi::layout`), and fall back to the per-hart idle and emergency stacks' bounds; keep the "same slot" rule (T240) so the walk never crosses a guard page. *Rejected:* frame-pointer unwinding (needs `force-frame-pointers` on every profile and a trusted chain in a panic; the scan works without it); looking the thread up in the TT table from the panic handler (takes a lock in a panic).

**T233-c: `finish_out` after the dequeue.** Minimal and recommended: (1) on a failed copy-out emit one structured debug line `##COPYOUT status=<s> va=<va> at=<offset> len=<n>` so a recurrence names itself; (2) map `VmoGone` and `MapFailed` deliberately (a comment per arm; the choice of status is owner question Q2); (3) a `ksys` host test for the `defer_out` contract: with `defer_out` set, a lazily backed destination and a frame allocator that fails on demand (`ksys/tests/allocfail.rs` has the harness), `verify_writable` fails *before* the dequeue with NO_MEMORY and the queue is intact; after a successful call every destination page is resident (so `finish_out` needs no commit unless the space changed). *Rejected:* re-queue at the front on failure (a second reader may have taken later bytes in between: stream reordering, and it needs the object lock a second time on an error path); pinning the destination frames under the object lock and writing to them afterwards (a snapshot taken in between would see or miss the write: it breaks MM8's copy-on-write rule); swapping to `copy_to_user_verified` (`usercopy.rs:213`: it fails where the fault-capable copy succeeds when a sibling snapshot makes the page copy-on-write in between, so it loses data in *more* cases). Whether the "lost with the error" contract stays is Q1.

**T233-d: the channel kill storm.** Same shape as the stream one over `channel_write`/`channel_read` and `channel_call` with 1 to 64 KiB messages plus two handles, pattern-checked; the handles' objects must be gone when the round ends (`job_use_settles`). Same file, same shard.

**T233-e: candidate 1 hardening.** Make the big-lock check of `user::state()` and `fp::state()` a real `assert!` in the `release-checked` profile as well (it is cheap: one per-hart load); leave plain release as is. *Rejected:* a shuttle model of the kernel's own tables (they are behind the big lock by construction; the model would test the model).

**T212: spin report.** Diagnostic only, threshold unchanged: at the first spin record the owner hart's `bkl_takes` (`percpu.rs:95`) and the clock; the panic adds `owner takes since: <n>, waited <ms> ms`. `n == 0` is one long section (the site is already named); `n > 0` is a starved waiter (fairness or host descheduling). *Rejected:* a time-based threshold (guest time is host wall time without icount: a descheduled owner would trip it sooner, not later); raising 30 million (hides a livelock for longer and changes nothing about cause).

**T197 (1): watchdog progress rule.** In `kcore`, a pure `starved_with_progress(now, limit, progress: &[u64], last: &mut [u64])` (or a small `WatchdogState` struct beside `starved`): a finding `(t, on, idle)` counts toward the three-in-a-row rule only if hart `on`'s progress counter advanced by at least 2 since the previous sample *and* the sampling hart's own advanced (else the sample is void, neither counted nor reset). Progress is `percpu.timer_ticks` plus scheduler passes (a hart with queued work arms an event every 100 ms, `thread.rs:980`, so a live hart always ticks; a hart whose host thread is descheduled does not). A hart that ticks, has `t` queued, and neither runs it nor pushes it to the idle hart is still reported: the lost-wake and lost-poke cases are kept. *Rejected:* a longer limit (masks real starvation); switching the watchdog off under `chaos` (that is where it earns its keep); SBI steal time (QEMU TCG reports none).

**T197 (2): the kill test.** Replace `wait_ended(p, 500)` at `suite.rs:6410` by `wait_ended_or_say(p, &[], 5000)`: a recurrence then prints the scheduler state and the process's signals, and 5 s is beyond host jitter while still failing a kill that never completes. The latency of a kill is T267's subject, not this test's.

### 5. Invariants, lock classes, and how this goes wrong

- **Lock order** (INVARIANTS.md "Lock order", K5; classes in `klock/src/lib.rs:35-50`): `finish_out` runs with **no** `Obj` lock, takes `As` (the caller's own cell) then the memory locks `Vmo`, `Jobs`, `Frame` (AS1: address space before memory locks, never after). The `##COPYOUT` line must be printed after those guards are dropped or it holds `As` across `Uart` for a formatted print (legal by order, but it lengthens an `As` hold and the print can take `Heap`). The chaos point goes outside every lock (after `irq::without` returns), or its yield sleeps with a lock held (AS1: no sleep with `As` held; K3: the big lock is released at a switch).
- **AS2 / the pager-need slot:** `finish_out` saves and restores it (`swap_need`); any early return added for diagnostics must keep the restore.
- **T10 / KT9** (nothing may fail for memory after a message is taken): the diagnostic line must not allocate on the success path, and `Deferred` construction must stay allocation-free (`ksys/src/lib.rs:402`).
- **K1, K3, RQ1/TR1:** the watchdog reads other harts' `timer_ticks` with `Relaxed` loads from a timer handler; it must take no `Rq` lock beyond what `starved` already takes (one at a time, ascending is not needed since never two), and must not read `percpu` of a hart index at or above `smp::started()`.
- **Watchdog false negatives (the real risk of T197):** a hart stuck in the kernel with interrupts off takes no tick, so the new rule would call it "no progress" and stay silent on a genuine hang of hart `on`. Bound it: if hart `on` shows no progress for a long absolute time (say 10 s of the sampler's clock, far beyond host jitter), report it as a *stalled hart* with a different message. The spin watchdog and CI's job timeout remain the backstops.
