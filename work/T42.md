## Shortcut

**DMA frames outlive a killed driver only by policy.** The kernel frees a DMA VMO like any other (`Vmos::release`,
`kcore/src/aspace.rs:1536`: it subtracts the DMA budget, credits the job and drops every frame, with no knowledge of a device); a
device mid-request could write into freed frames. S6b's answer is ownership: the *supervisor* keeps its own handle to the DMA
buffer and the MMIO slot across driver lifetimes, so killing a driver frees nothing, and resets the device (`STATUS = 0`) before
the buffer goes to the next driver. Implemented in `devmgr`, `netsup` and the suite's `BlkRig` (`blk_driver_restart`). Nothing in
the kernel enforces it, and it never contained a **malicious** driver: without an IOMMU a driver can point its device at any RAM
(OS-ARCHITECTURE 493).

## Why it was acceptable

Only trusted boot code supervises drivers; no IOMMU (OD14, then OD136).

## Decision

**OD148 (owner, 2026-11-24)**, amending OD136 and KERNEL-V1-SPEC 1's non-goal: the kernel gets a full IOMMU. A device reaches
only the frames mapped into its domain; frames are unmapped and the device's translations flushed before they are freed; no
quarantine is built in between; the profile requires the IOMMU (refuse to boot without it); the drivers move from virtio-mmio to
virtio-pci; every DMA device goes behind it with no pass-through; order: spec, host model, a boot with the IOMMU, the bus move,
block, network. FZ1 timing is free.

## Plan (2026-11-25)

### What was checked for this plan (2026-11-25; QEMU 11.1.3; no build, test or guest boot was run)

- The platform IOMMU (`-M virt,iommu-sys=on`) appears in the device tree as `riscv,iommu` at `0x301_0000` with four wired
  interrupts; the PCI host gets an `iommu-map` for all requester ids; **the virtio-mmio nodes get no `iommus` property**. So
  OD148's open check is answered as far as the tree shows: the IOMMU covers PCI only, and the bus move is needed in full.
- QEMU also has `riscv-iommu-pci` and `iommu-testdev` (a PCI device made for testing IOMMUs); a machine with the platform IOMMU,
  `virtio-blk-pci` and `virtio-rng-pci` (`iommu_platform=on,disable-legacy=on`) and the test device is accepted; all BARs start
  unassigned. The capability register reads `0x78_e2cf_4f10` (decoded in IOMMU0).
- The code: every DMA user is listed in IOMMU10 and IOMMU11 (`devmgr`, `blkd`, `netsup`, `netdrv`, `rngd`, the suite's rig and
  hand-driven tests; `netd` maps pools but never has the DMA right; the kernel itself drives no DMA device).
- For the MSI-X revision: QEMU's source at tag `v11.1.3` was read for the IOMMU's MSI translation (basic-translate forwards the
  device's data word; MRIF mode with a notice is implemented; MSI translations are not cached), the tree was dumped again
  (`riscv,num-ids = <0xff>` per hart file; `aia-guests` 0 to 7), and Linux's RISC-V IOMMU and IMSIC drivers were read. What
  follows from it, and what is still from memory, is in IOMMU7 ("The isolation design").
- Not verified, and each has an owner: everything in IOMMU0's "to establish" list (the test device's registers, the first-stage
  U-bit rule, QEMU's virtio bypass without `iommu_platform`, the debug translation interface, whether a stale cached translation
  is observable, record/replay and icount with these devices).

**Order.** IOMMU0 first (it needs nothing).
IOMMU2 can start as soon as IOMMU0 is in, beside the spec, because the hardware formats do not depend on the owner's answers. Then
IOMMU1 (the spec PR, which the owner merges); then IOMMU3 and IOMMU4 (independent of each other and of the IOMMU device: either order, or two sessions; IOMMU4 touches
only the interrupt controller and is worth landing early, since every later slice's interrupts ride on it), IOMMU5, IOMMU6,
IOMMU7, a smoke and merge of the kernel epic; then IOMMU8 to IOMMU12 strictly in order. Two epics, not one, so that `main` gets
the kernel half (required IOMMU, default deny, the calls, the vector mechanism) while the drivers are still on the old bus: `main`
boots in every intermediate state, and nothing is less safe than today at any point. The system is isolated only when IOMMU12
merges.

**The interrupt design in one paragraph** (IOMMU7 has it in full, with what was verified). A device's MSI is translated by a
per-domain MSI page table the kernel owns; every entry is in MRIF mode, so the device's message only sets a bit in a small
interrupt file in kernel memory and the IOMMU then sends a **notice** whose hart and identity the kernel chose. A driver gets
interrupt objects for the vectors its supervisor was granted and can cause no other interrupt, whatever it writes into its device
or its MSI-X table: an ungranted vector or a foreign address is a reported IOMMU fault, a wrong identity never leaves the file.
The limit: this needs the IOMMU's optional MRIF capability (QEMU has it); without it only the hart file would be confined, so
a machine without it does not boot (OD165).

  of any earlier T262 PR.
- **T14** (serial bridge): no DMA, no conflict. The owner chose a user-mode virtio-console server there (OD146), so T14 no longer
  builds a kernel-owned interrupt source: **IOMMU4 builds that hook alone**, for the IOMMU's own interrupts. The console server
  will be one more virtio-pci device with MSI-X vectors claimed through `devmgr`: it should start after IOMMU9, and it is a
  reason the four-line limit of option A would have bitten at once (two disks, network, entropy, console).
- **T263** (security bundle): OD159 splits `MANAGE` into separate rights; the domain object gets its own right bits from the
  start (IOMMU6), not `MANAGE`.
- **X-BUS**: IOMMU8 and IOMMU9 are its committed part (one ECAM host, bus 0, MSI-X). The older MSI capability, bridges, hotplug
  and USB stay there (the grouping of functions that share a requester id behind a bridge is T276).
- **OD149** (a lock per object) and SC2: IOMMU4's route table and IOMMU7's vector state are written under `OBJ` today; the split
  must give them a rule (noted in both slices).
- **X-DRIVER-MODEL**: gets its "shared virtio-queue crate" (IOMMU8) and loses "trust-based DMA with no IOMMU".
- **X-SANDBOX**, **OS-ARCHITECTURE 708**: an untrusted driver becomes possible only after IOMMU12.
- **Q-OS10** (revocation): destroying a domain is a revocation of a device's reach; nothing here decides Q-OS10.
- **T177**, **T271**: unmap and destroy never allocate (IOMMU2, IOMMU3); table frames come from the frame allocator inside the
  new lock, which the leaf allocator of T271 makes simpler but does not block.
- **FZ1**: the syscall fuzzer learns the domain calls in IOMMU6 and forgets `vmo_phys_addr` in IOMMU12; timing is free.
- **The home computer** (`home/`): untouched. It keeps virtio-mmio under its own kernel and plain `virt`.

### Risk register (what could go wrong, and how it is seen with no one watching)

| Risk | Seen as | Guard |
|---|---|---|
| The kernel writes a pass-through state (`ddtp` Bare, or a context with both stages Bare) | Nothing fails: DMA simply works everywhere | `iommucore` cannot construct it; negative-control kernel `fault-iommu-bare` must fail `iommu_is_on_and_denies_by_default`; the boot line prints the mode read back and the script checks it |
| A frame is freed while a cached translation still reaches it | Rare memory corruption in an unrelated process | Host model with a simulated device cache (IOMMU3); `fault-iommu-skip-inval` negative control and the late-write pattern test (IOMMU6, IOMMU12); a debug-build mark on device-mapped frames |
| The negative control cannot fail on QEMU (commands synchronous, cache not stale) | A control that passes when it should fail | IOMMU0 item 8 finds out first; if so the PR says plainly that the host model is the only proof |
| A virtio-pci device started without `iommu_platform=on` bypasses the IOMMU | Everything works, nothing is isolated | One helper builds every device option; `devmgr` refuses a device without `ACCESS_PLATFORM`; a per-machine negative test (`pci_virtio_outside_its_mapping_faults`) |
| Lock-order mistake with the new class | A `klock` checker panic in the first boot that takes the path | The pair table in `klock/tests/order.rs`; the spec lists every nesting (IOMMU1 section 11) |
| A fence that never completes | A hang in unmap with a lock held | A bounded poll; on expiry leak and count, one loud line; `debug_stat` selector; the leak oracle then fails the boot |
| A fault storm from a device left running | Console flooded, a hart starved | Bounded drain per interrupt, rate-limited line, a dropped counter, the quarantine context with reporting off |
| A boot script without `iommu-sys=on` after IOMMU5 | That boot stops with "no IOMMU" | Loud by design; `os-boot-test-iommu-neg` proves the text |
| A device raises an interrupt it was not granted (the MSI path left in basic-translate mode, or an entry pointing at a hart file) | Nothing fails: interrupts simply work, and a hostile driver can forge others' | `iommucore` has no constructor for a basic entry; negative-control kernel `fault-iommu-msi-basic` must fail `msi_forgery_faults`; the forgery rows of IOMMU7 and IOMMU12 |
| An interrupt identity is reused while a cached MSI entry or a message in flight still names it | A driver gets another device's interrupt, rarely | Host models with a simulated MSI-entry cache (IOMMU2, IOMMU7) and the retire step (IOMMU4). **No negative control in the machine**: QEMU caches no MSI entry (IOMMU7 says so plainly) |
| A lost device interrupt (mask and acknowledge race on the interrupt file; a vector left masked across a driver restart) | A request that completes only by the driver's safety poll: slow, not failed | Drivers count poll-found work and the suite asserts 0 (IOMMU10, IOMMU11); the model's exactly-once property (IOMMU7) |
| The trap path's identity handling regresses (IOMMU4 changes every device interrupt) | A hang of the block or network tests in the first boot | It lands early, alone, with the existing interrupt tests unchanged; the no-route counter |
| Identities run out (254 per hart file on QEMU) | A failed grant | Per-hart allocation; the per-job vector limit; a loud failed claim, never a shared vector (Q-IOMMU-MSI 2 and 4) |
| The IOMMU has no MRIF on some later machine | A boot refusal (OD165) | Stated in the spec as a profile requirement, like AIA |
| Firmware or an earlier kernel hands the IOMMU over in a mode other than Off | Devices may have had reach before the kernel ran; the kernel must not build on that state | The kernel writes Off first, reads it back and only then brings the IOMMU up; refusal only if it will not go Off (OD166 point 11; IOMMU5; IOMMU0 item 15 for what the hardware requires) |
| A driver job with no limit on I/O-mapped pages or vectors (the limits have no default) | One driver takes every interrupt identity of a hart or fills kernel memory with page tables | The limits are hierarchical; `devmgr` sets finite ones on every driver job; rows of the hostile-driver matrix (IOMMU12); the system backstops |
| MRIF mode's cost per interrupt (a memory update and a second message) | Lower interrupt rate than a direct file write would give | Accepted for isolation; nothing measures it in this epic (soak benches are the owner's to start) |
| Network restart regressions (generation counters, re-attach) | An intermittent `net_children_restart` | A driver restart is a re-claim: the function is reset, its domain destroyed and made anew, and the new driver maps the same pools afresh (IOMMU11); any intermittent failure gets an item and a cause (OD160) |
| `iommu-testdev` cannot do what the checks need | IOMMU5's first check cannot be written as planned | IOMMU0 item 1; the fallback is a virtio device with a descriptor outside its mapping |
| QEMU's IOMMU is the only implementation ever tested | A real device behaves differently (timing of fences, A/D updates) | Stated in the spec; a tidy item from IOMMU12 |
| Record/replay or icount stop working with PCI and the IOMMU | A debugging tool lost | Found in IOMMU8; recorded as an item, not dropped silently |
| The spec is bent to fit the easy path | Isolation with a hole nobody wrote down | CLAUDE.md's rule; the Fable reviews of IOMMU3, IOMMU4, IOMMU5, IOMMU6, IOMMU7 and IOMMU12 attack the spec's sections, not the code's comments |
