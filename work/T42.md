## Shortcut

**DMA frames outlive a killed driver only by policy.** The kernel frees a DMA VMO like any other; a device mid-request could write into freed frames. S6b's answer is ownership: the *supervisor* keeps its own handle to the DMA buffer and the MMIO slot across driver lifetimes, so killing a driver frees nothing, and resets the device (`STATUS = 0`) before the buffer goes to the next driver, which also clears the queue memory itself. Implemented and tested in the suite's `BlkRig` (`blk_driver_restart`); `blkd` zeroes the queue at start. Nothing in the kernel enforces it: a supervisor that closes its handle while a driver is alive, or that dies, can still lose the frames to the device.

## Why it was acceptable

Only trusted boot code supervises drivers; no IOMMU (OD14).

## Proper fix, and when

The S6c device manager follows the same rule and is the only holder of DMA VMOs; a kernel-side quarantine until a device-reset acknowledgement if drivers ever stop being trusted.

### 2. Design

What each trigger buys, stated plainly: without an IOMMU a hostile driver can point the device at any RAM, so **no kernel
quarantine contains a malicious driver** (OS-ARCHITECTURE 493). Quarantine (A) only closes "the supervisor closed early or died".
Containment needs B.

**A. No IOMMU: quarantine until a release (Q-T42 option 2).**
1. `Vmos` gets a quarantine list of `(first pfn, pages, job)`. Its entry is reserved in `create_dma` (class R: removal never
   allocates, T177), so `release` of a `VmoKind::Dma` VMO moves the run there and cannot fail. The index leaves are credited at
   that point as today; the frames are not `dec`ed, `dma_pages` is not reduced (the backstop bounds the leak), and the job keeps
   its page charge and its `retain` (J2: a record with usage is never freed).
2. New call `dma_release(resource, phys_addr)`: needs the root resource (D3); `phys_addr` is the first byte of a quarantined run,
   which the supervisor learned through its DMA-right handle (D2 unchanged). It frees the frames, credits pages, reduces
   `dma_pages`, releases the job. Errors in order: BAD_HANDLE, WRONG_TYPE, ACCESS_DENIED, INVALID_ARGS (unaligned), NOT_FOUND (no
   such quarantined run: a live VMO at that address is never touched, a second release finds nothing).
3. A `debug_stat` selector for quarantined pages (next to 124), so leak checks and a recovering supervisor can see them.
4. User space: `devmgr`, `netsup` and `BlkRig` call `dma_release` after `reset` and after closing their handle; the holder of the
   root resource that starts `devmgr` sweeps what a dead `devmgr` left (it needs the addresses: see question 3).

**B. With an IOMMU: unmap before free.** The kernel owns the IOMMU tables; a DMA VMO is bound to a device context at creation; a
driver gets I/O virtual addresses, never physical ones; `release` removes the I/O mapping and invalidates the IOTLB on the device
before any frame is `dec`ed (the shape of TLB2/SMP5). No quarantine, no new trust in the supervisor. This is an epic of its own
(spec amendment to KERNEL-V1-SPEC non-goals, a new profile requirement, QEMU `virt` IOMMU support to be verified first) and is
only sketched here.

| Rejected | Why |
|---|---|
| Reset on free (Q-T42 option 3) | Puts the virtio-mmio reset protocol and a bind call in the kernel; one device class only |
| Never free DMA frames | 1024-page backstop is gone after a few driver restarts with fresh buffers (the net claim makes 130 pages each time) |
| Key the release by VMO id or a creation tag | The VMO is gone when the release is needed; a tag changes `vmo_create_dma`'s ABI. The address is already the DMA-right secret |
| One "drain everything" call | Frees the run of a device that was not reset |
| Driver duplicates that do not keep the VMO alive | Does not cover a supervisor that dies; new handle semantics (M8) |

### 5. Invariants, locks, and how it goes wrong

- Rows touched: **D4** (becomes "freed exactly once, at `dma_release`"), **M8** and **H6** (a deliberate exception: frames outlive
  the VMO and the process), **M3** (baseline checks must include the quarantine), **J1/J2** (pages stay charged; leaves credited
  at the VMO's end; exactly one credit), **D2**, **D3**, **ML1** (unchanged: the VMO still goes with no mapping listed), new
  **D6** ("a DMA frame returns to the allocator only after its resource holder says the device is quiet").
- Locks: the list lives in the VMO store, so the call takes `OBJ` (resolve the resource handle), then `VMO`, `JOBS`, `FRAME` in
  that order (`kmem::get()`, K5, SCHED-SMP-SPEC 3.3 rows 1, 5, 6, 11). No new class. Nothing that takes `OBJ`, a thread call or
  `irq::without` runs while the three are held.
- Subtle failures: (1) the quarantine entry allocated in `release` instead of reserved at create (fails under `allocfail`, breaks
  T177's rule); (2) a job freed with quarantined usage (the `Jobs::release` debug assertion: a kernel panic); (3) double credit
  if the `<= RANGE_STEP` path and a future `stash_dying` path both handle DMA (raise `MAX_DMA_PAGES` and the batched path is
  live: handle `Dma` before the size test); (4) the J1 ledger formula (`leaf_count * LEAF_BYTES`) if leaves are credited at the
  wrong moment; (5) every leak test in the suite silently depending on free-at-close; (6) a restart loop that never releases
  exhausts the 1024-page backstop: a denial of service by a buggy supervisor, visible only as NO_MEMORY from `vmo_create_dma`;
  (7) the kernel cannot check that the reset happened: A moves the trust, it does not remove it; (8) kernel ASLR and shuffled
  syscall numbers (AB8) need the new number in every table (`abi`, `libsys`, `kfuzz-gen`).

### 6. Dependencies and owner questions

Depends on or overlaps: **T262** (its T41 part: per-job DMA quota and an exclusive-claim record per device slot; its T84 part: who
is charged for net DMA; both change `vmo_create_dma` and should land first or in PR 1), **X-SANDBOX** and **X-DRIVER-MODEL** (the

Questions for the owner (not decided here):

3. Who pays for quarantined pages: the creating job until release (proposed), or the root job? And how does the recovering
