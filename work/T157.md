## Shortcut

`OS_SMP=4 os_boot_test.py --rr` (the round-robin-class kernel, generic tests only) fails about one run in three, on `main` as well as on PR 250 (measured 2026-11-18: `main` 1 failure in 3 runs, the L11b branch 1 in 3). On CI it ended as "timed out after 600 s, no ##DONE line". The failing test, when the harness names one, is a network test against the host (`net_tcp_to_the_host_server`: the greeting from the harness's host server is not read in time); the soak `lossy relay` job's host download test fails the same way on slow runners. Not diagnosed: the cause may be the host side (the harness's Python servers and QEMU's user-mode network under load) or a timing assumption in the tests.

## Why it was acceptable

A re-run passes; the fixed-priority kernel runs of the same suite pass.

## Proper fix, and when

Run the failing test in a loop at `-smp 4` with the round-robin kernel and the host server's log kept, to see whether the stack or the host side stalls; give the host server and the tests the same generous deadline; or move the host-network tests out of the round-robin run (it only needs the generic scheduler tests).

## Note (2026-11-18, plan 4: the v1 kernel)

OD140 and `docs/reference/TESTING.md` rule 8: this is a defect until its cause is known, not a flake to re-run. Plan 4 phase 1 takes it with KT2's record and repeat tools: establish the pass rate over 20 runs, capture a failing run, find the cause, fix the code or the test, and show the rate after (20 of 20).
