title: The shootdown negative control passes on QEMU 11.1.3: it depends on how long QEMU keeps a stale TLB entry
refs: [T178]
---

Found by the first full soak (2026-11-21, run on a Mac with QEMU 11.1.3; CI installs 10.2.1 from Ubuntu). `make os-boot-test-smp-neg` ends in `negative control FAILED: ... os-fault-shootdown ... passed although it lacks the mechanism unmap_while_siblings_touch guards`, in the parallel run and again alone. The control (`fault-skip-shootdown`) skips the remote `sfence.vma`; the guard test (crash mode 40) has two readers on other harts read a page the main thread unmaps and remaps, and fails if one reads the previous round's data through a stale TLB entry. That only shows if the emulated hart's TLB keeps the entry; QEMU 11 evidently drops it (a trap, an interrupt or the ASID handling flushes it) often enough that the test never sees stale data. The mechanism itself is not shown to be broken: the control stopped being able to tell. Proper fix: first run the control on CI's QEMU (10.2.1) to see whether it still fails there; then make the guard independent of the emulator's TLB policy: for example give each reader a long run of reads between the unmap and its next trap, or check through the page-table walk and a reference model (the TLB1 and TLB2 invariants hold by construction in a model of the shootdown, which `kcore` could host), keeping the QEMU test as a smoke. Why acceptable: the shootdown is also exercised by every unmap in the suite and the churn tests at four harts; the control is soak-only. Risk: a real regression in the shootdown is not caught by this test on a recent QEMU. (The `earlyreap` control had the same decay and was made deterministic in the same pass: it now takes the freed stack slot and writes to it.)
