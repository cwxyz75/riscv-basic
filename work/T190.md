title: AB3 leftovers: the process id is not the process object's koid, the ASID is derived from the pid, and three counters saturate
refs: [AB3, CNT1, T66]
---

Left from the Fable review of AB3 (2026-11-21). (1) KERNEL-V1-SPEC 3.3 says the process id is the process object's koid; the code keeps a separate `next_pid` counter and loader-started processes have no process object. (2) The ASID is still `(pid & 0xffff)`: two live processes 65,536 pids apart share an ASID (L18/T66 own the ASID allocator; spec 3.3 forbids deriving it from the pid). (3) The koid counter, the FP/vector tokens (`kcore::fp::Tokens`) and the legacy scheduler's `next_tid` (`kcore/src/sched.rs`) saturate or add unchecked at the end of u64; saturation would repeat a value (a token match would let a thread run on another's registers). Unreachable in 2^64 events but the comments say "stop": make them refuse. (4) SYSCALLS.md `futex_lock_pi` puts the owner's tid in bits 0-29 of a 32-bit word, which cannot hold a u64 tid: amend it when the call is built (decision item then). Why acceptable: none is reachable in a boot's lifetime; the test-only `ff=` can reach (3).
