### T2: Ambient creation syscalls remain

*(area security, horizon long, risk M)*


#### Shortcut

**Ambient creation syscalls remain**: any process may `vmo_create`, `socket_create`, `channel_create`, `event_create` (bounded by its handle table and the global object cap) and `debug_write`; `process_create` is ambient but limited by the caller's job (a program's job allows no further process).

#### Why it was acceptable

Needed by every program; the dangerous ones (processes, threads, memory) are now job-limited.

#### Proper fix, and when

Gate object creation by the job's object quota (T1); restrict `debug_write` to a console capability.

### T3: Trusted programs (`ls`, `cat`) get a standing read-only root

*(area security, horizon long, risk M, fixed_by [S10-MANIFEST])*


#### Shortcut

**Trusted programs (`ls`, `cat`) get a standing read-only root** via `/etc/trusted` (S4 spec section 8). Contradicts least privilege in spirit, though allowed by OD20; and the list is baked into the read-only boot image at build time, so it is hardcoded in practice, not a user-editable config as OD20 intends (product owner accepted this for S4).

#### Why it was acceptable

Lets the S4 acceptance session use absolute paths without a powerbox protocol.

#### Proper fix, and when

**True powerbox**: the shell opens the path arguments itself and passes just those handles (argument syntax that references handles), no standing root; `/etc/trusted` goes away. With the manifest-driven shell (S10).

### T5: `MANAGE` is coarse

*(area security, horizon long, risk M)*


#### Shortcut

**`MANAGE` is coarse** (map, start, thread_create on a process). A kill-only right (`KILL`, S4a-1) now exists, but process rights are not otherwise split as OS-ARCHITECTURE section 9 wants (start, kill, read/write memory separate).

#### Why it was acceptable

Enough for S4.

#### Proper fix, and when

Split `MANAGE` (start / map / threads / debug-memory) when a second consumer needs it; at the latest before ported software.

### T29: `GetVmo` hands out the whole boot image

*(area security, horizon long, risk L)*


#### Shortcut

**`GetVmo` hands out the whole boot image** (read-only) plus the file's extent: any client allowed to read a boot-image file can read every other boot-image file.

#### Why it was acceptable

The image holds only public programs and fixtures.

#### Proper fix, and when

VMO slices/children (`vmo_create_child`) so a file's VMO is exactly that file.


#### Note (2026-11-24)

Checked against the code: `memfsd` still duplicates the whole boot image VMO for `GETVMO` (`init/src/bin/memfsd.rs`, "The whole boot image, read-only"). The proper fix is now buildable, because `vmo_create_child` exists (MM8), but nothing uses it for this yet.

### T58: The shared-memory rule of slice V is scoped to jobs (review of PR #102)

*(area security, horizon long, risk M)*


#### Shortcut

**The shared-memory rule of slice V is scoped to jobs (review of PR #102).**

- (1) A hostile peer in the *same* job, or a sibling job under a shared ancestor limit, can still hand over a lazily committed VMO whose touch kills the toucher, and the recipient has no COMMIT to defend itself
- (2) the page-table frames a first touch of a mapped committed VMO needs are taken at fault time (`process_map` charges the job for tables but reserves no frames), so a touch can still fail when frames run out
- (3) `vmo_write` commits pages with only WRITE, charging the creator, with no rollback on a partial failure
- (4) `rt::heap` now commits each 256 KiB chunk when it grows, so accounting moves from touched to mapped pages, and no test fails if the heap commit is removed
- (5) `COMMIT` is part of the default `Rights::VMO`, the wrong default (safe today only because every handle handed out is explicitly narrowed).

#### Why it was acceptable

Closes the cases the design review (D3) named: a client at its quota handing a server a VMO, and a server's VMO spent by a client, between different jobs.

#### Proper fix, and when

Build the tables and PTEs in `process_map` for foreign mappings; reject or commit-first in `vmo_write`'s partial failure; a QEMU test of an rt program in a tight job that must get a null from the heap, not a fault; take COMMIT out of the default VMO rights; move the V1 predicate into `kcore` so a host test can mutation-check it.

### T148: The independent review of the spawn, signal, terminal and attribute work (2026-11-17 night, fresh context): findings

*(area security, horizon long, risk M, blocked_by [Q-SIGINT])*


#### Shortcut

**The independent review of the spawn, signal, terminal and attribute work (2026-11-17 night, fresh context): findings.** *Fixed in PR 229:* `vfork` made every writable file of the parent append for good (now only the child's copy is, and the parent's offset moves past what the child wrote); an oversized or handle-carrying message on a program's signal channel kept the channel readable and the shell spinning, and the read loop was unbounded (now 8 per pass, 64 bytes and 8 handles, handles closed); `E2BIG` on a spawn leaked the three duplicated handles; `mmap` of a huge length wrapped; `memfsd` refused `chmod`/`chown`/`fsync` on a directory (now exempt from the file/directory gate as `fsd` is). *Open:*

- (1) **a program can hold Ctrl-C off for ever**: it sends `H,2,1` ("I handle SIGINT") and never waits, so `HoldForeground` leaves the console server nothing to kill and the signal is never delivered (the T31 guarantee and OD118's "Ctrl-C ends the chain" do not hold against a hostile program); a fix needs a policy (a second Ctrl-C within a second kills, or a deadline on the hold)
- (2) in non-canonical mode with ISIG `consoled` sends `Interrupt` but not `JobInterrupt` (both `kill` and `interrupt` are set), so a cbreak program with a SIGINT handler (`less`) never gets Ctrl-C
- (3) *fixed 2026-11-18 (OD120)*: the mount intersection with the asker was by mount *name*, not by volume: a policy mapping one name to different volumes for two programs, or a trust mount named `/tmp`, `/dev` or `/proc`, lets a child get what its asker did not hold (`parse_trust` bans only `/` and `.`)
- (4) the pipe-read, `poll_read` and write loops serve brokers but never the console control channel, so during a capture or pipe into the shell `JobInterrupt` is not read
- (5) SIGINT goes to the foreground roots only: a root that handles it (a shell waiting on a child) does not pass it down
- (6) a signal forwarded by an `exec` forwarder to a depth-5 program is dropped
- (7) a write-only connection's `FSTAT` now carries mode, owner and time, which `ATTR_GET` would need READ for (decided: POSIX `fstat` needs no access)
- (8) a message on a program's signal channel larger than 64 bytes or with more than 8 handles still cannot be read (the program is the only one hurt, but the shell polls it each pass); `memfsd` has no `ATTR_LIST`.

#### Why it was acceptable

The review found no kernel invariant broken; all of it is userland.

#### Proper fix, and when

The policy decisions (1),

- (3) and
- (5) are the owner's; the rest are small slices.

### T186: HD1 leftovers: the Zkr path is unexercised and its traps are unhandled; the original tree keeps the seeds; the key derivation leaves intermediates on the stack

*(area security, horizon long, refs [HD1])*


Left from the Fable review of HD1 (2026-11-20), after the fixes in the PR (the pool keyed in place and the key wiped, `seeded` needing 16 bytes of real seed, the hart matched by the last `reg` cell, `below` giving up when the source refuses, the seeds scrubbed in a heap copy before the single VMO write). (1) The `seed` CSR read is an illegal instruction in S-mode if M-mode has not set `mseccfg.SSEED` (or a virtual-instruction trap under a hypervisor), so a machine whose ISA string lists Zkr but whose firmware does not allow the read panics at boot instead of falling back; QEMU's `rva23s64` has no Zkr, so the path has never run. Proper fix: a trap-and-skip window around the read (the trap handler already decodes the faulting instruction) or a probe through SBI, and a pause in the retry loop. (2) The original device tree stays in memory with the seeds for the whole run (user space cannot reach it: RAM is cut from every device window, `kcore::devwin`); zero them in place once the kernel table maps the tree writable, or copy the tree. (3) `derive_key` leaves its SHA state and HKDF intermediates in dead stack; the generator's key is wiped, the intermediates are not. (4) The self-test `the_entropy_pool_is_seeded_as_the_tree_says` assumes a machine with no Zkr. Why acceptable: one target, QEMU, whose tree carries the seed and whose CPU has no Zkr; the stack is the boot stack of a kernel with no user code on it. Risk: a hardware port finds (1) first.

### T234: The runtime heap's base is derived from the randomised stack and image addresses, not drawn from the kernel's entropy

*(area security, horizon long, refs [HD2, HD1])*


**What.** `rt::heap::pick_base` hashes the stack and image addresses (both placed at random by the kernel) into a page of the 4 GiB window below the mapping arena. **Why acceptable.** A program has no entropy source before `rngd`, the kernel gives it no word at startup, and the hash makes the heap move on every launch (the acceptance asks for that). **Risk.** One leaked address (stack or image) plus the hash function determines the heap base: the heap is not an independent draw. **Proper fix.** The kernel puts one random 64-bit word in the first thread's startup registers (or a startup-message field the launcher cannot forge: the kernel-started process gets it in its bootstrap message), and `rt` seeds the heap base, the `thread_spawn` hint and any later placement from it. A syscall or startup ABI change: do it with the next flag day (see T213).

### T138: The boot image is held in several copies

*(area platform, horizon long, risk M)*


#### Shortcut

**The boot image is held in several copies** (2026-11-17): the kernel embeds it, and by the numbers about 3.7 copies of `/bin` sit in memory after boot (the memory file server keeps file data in its heap, T16, and other servers hold parts): with symbol tables the user programs were 24.6 MB on a laptop and 50.2 MB on CI's machine and the shell test's memory hog found 26 MiB of heap left on CI instead of 120. Stripping the symbol tables (`--strip-all`, was `--strip-debug`) took `/bin` to 5.3 MB and the copies to a size nobody notices, but a bigger image (a port such as `sqlite`, `tcc`) will bring the problem back.

#### Why it was acceptable

Found by running the shell test on CI for the first time.

#### Proper fix, and when

Serve `bin/` from VMOs shared with the loader (`GetVmo` for everything, T16) so a program is in memory once; show the boot "frames free" and the image size in every serial test's output (done).
