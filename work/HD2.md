**How.** KERNEL-V1-SPEC 3.7, 7.2. (1) `kcore::elf` accepts `ET_DYN` static-PIE images (no `PT_INTERP`, no `DT_NEEDED`; the dynamic section may hold `DT_RELA` with `R_RISCV_RELATIVE` only) as well as `ET_EXEC`, and reports the image's span. (2) Startup code relocates itself: `rt`'s entry and the C library's `crt0` walk their own `DT_RELA` before anything else (about 40 lines of position-independent assembly or carefully written Rust with no relocated references). (3) Builds: user Rust with `-C relocation-model=pie` and a static-pie link, C with `-fPIE -static-pie`. (4) Placement: the kernel's built-in loader (the first process) and `rt::spawn` map a PIE image's segments at a base obtained by one ANYWHERE reservation of the image's span (reserve, then map segments at fixed offsets inside it); the first thread's stack is mapped ANYWHERE instead of below `STACK_TOP`; `thread_spawn`'s stack arena hint starts at a random offset per process. `ET_EXEC` images and fixed addresses still work. Test builds honour `aslr=off`.

**Acceptance, written first.** `kcore/tests/elf_loader.rs`: PIE images accepted, a PIE with `PT_INTERP` or a non-relative relocation refused, the mutation fuzz extended to `ET_DYN`. QEMU: a program prints the addresses of its code, stack, a heap block and an ANYWHERE mapping; across ten launches each takes at least eight distinct values; with `aslr=off` they are constant. Every program in the image is PIE (a build check on `e_type`). The Lua, C, BusyBox and BASIC suites pass.

**Review.** Fable, soak.

## Progress (2026-11-22)

**Step (1) is built** (PR on `epic/phase-11`): `kcore::elf` accepts `ET_DYN` static-PIE images: link addresses are offsets from a base the loader chooses, the dynamic section may hold only the `DT_RELA` family (a tolerated few: empty symbol table and hash, flags, `DT_RELACOUNT`), every relocation must be `R_RISCV_RELATIVE` on an 8-byte word inside a writable segment, no `PT_INTERP`/`DT_NEEDED`, one `PT_DYNAMIC` and only in an `ET_DYN`; `Image` gains `pie` and `span`; host tests (`kcore/tests/elf_loader.rs`: acceptance, every rejection, a mutation fuzz over a static-PIE, one mutant checked). Until step (4) places them, the kernel's loader and `rt::spawn` refuse a static-PIE (BAD_TYPE / BAD_ELF). **Open:** (2) the self-relocating startup of `rt` and the C library, (3) the PIE builds of every program, (4) placement by an ANYWHERE reservation, the ANYWHERE stack and the random `thread_spawn` arena hint, `aslr=off`, and the QEMU acceptance (ten launches, eight distinct values).

**What a build spike found (2026-11-22), for steps (2) and (3):** `hello` with `-C relocation-model=pic -C link-arg=-pie -C link-arg=--no-dynamic-linker` and a linker script based at 0 (text, rodata, `.data.rel.ro`, `.rela.dyn`, `.dynamic` and the data segment) fails at link time: the prebuilt `libcore` of `riscv64gc-unknown-none-elf` is not position independent, so its read-only data holds absolute words (`R_RISCV_64` against local symbols, switch tables, vtables), and lld may emit a dynamic relocation only into a writable section unless it is told `-z notext`. Because the kernel maps rodata read-only, the program's own startup cannot write those words. The way through is the usual RELRO: put `.rodata` (and `.data.rel.ro`) in the writable segment, let the startup apply every `R_RISCV_RELATIVE` and then `process_protect` that range read-only (the call exists: MM7), which also means the self-relocating startup must run before anything reads those words and cannot use them itself (no `core::fmt`, no tables, no vtables: assembly or a very small `#[no_mangle]` function that touches only registers and the `.dynamic` it finds from `_DYNAMIC`/a PC-relative address). Alternatives to weigh before building it: build `core` and `alloc` with `-Zbuild-std` and PIC (nightly, a build change for every user crate), or have the loader (the kernel's and `rt::spawn`) apply the relocations while it maps (it already holds the bytes), which keeps rodata read-only and the startup trivial but makes the loader do the writing: the spec's choice (startup code relocates itself, KERNEL-V1-SPEC 3.7) would then change by an amendment. The C programs (Lua, SQLite, gzip, BusyBox, `ctest`) need `-fPIE` and the same link. Nothing of this is started beyond the spike.


## Progress (2026-11-23)

**Steps (2) to (4) are built** (one PR on `epic/phase-11b`), with the loader relocating instead of the startup (decision in `WORK-PLAN.md`, spec amendment 2026-11-23): `Image::relocate`; `rt::spawn::map_image` (shared with the suite's hand-built children); every program linked with `link-pie.ld`, `-pie -z notext` and compiled with `-C relocation-model=pic` (`init/.cargo/config.toml`) or `-fPIE` (C); `scripts/check_pie.py` (every program is `ET_DYN`, run by `os-ktest-release-content`); kernel loader: random base in the mapping arena, random stack in the stack arena, random `thread_spawn` hint (`random_stack_hint`, also for `process_create`); `rt::heap` base hashed from the stack and image addresses (T234 for an independent draw); `aslr=off` (`entropy::placement_below`, `debug_stat` 128; the AB3 boot of `os-ktest-small` runs with it); the placement test `programs_are_placed_at_random` (ten launches: at least eight distinct code, stack and ANYWHERE addresses; one each under `aslr=off`). The suite's own fixed addresses for child stacks became ANYWHERE maps. What remains: the Fable review, the soak, and the heap-base entropy (T234).
