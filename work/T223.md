## Shortcut

The counts job (`make` target of KT5: a `kfast` k-shard boot at one hart under `OS_ICOUNT=shift=0,sleep=off`, `OS_BENCH_FULL=1`) compares seven instruction counts with `bench/counts.tsv` at 5%. The numbers are not stable. Evidence of 2026-11-22: the same code (merge commit `a3f4e1a` of phase 6e and the head of `epic/phase-11`, which differ only in code that does not touch these paths) gives, on one machine, the identical set (`channel_write_read_64` 30236, `channel_call_round_trip` 167200, `futex_wake_no_waiter` 942), so a single machine is steady; but CI gave `channel_write_read_64` 26302 (the baseline), 30648, 27142 and 31701 in four runs over two days, `handle_dup_close` 17747, 18777, 17616 and 19265, `futex_wake_no_waiter` 795, 840, 856 and 907. The spread is up to 20%, so the check fails on noise and a re-baseline records noise.

## Why it is open

Phases 6e and 11 each lost two or three counts-job runs to it (a re-run, a re-baseline that the next run exceeded). The cause is not found. Candidates: the seeded entropy (HD1: the firmware's seed differs per boot and per CI runner, so an `ANYWHERE` placement or a hash seed changes what the loop touches), the interrupt phase (even with `shift=0` a tick lands on a different iteration), `n` (5 or 200 iterations by `debug_stat(7)`) amortising a cold first iteration differently, the host's QEMU version.

## Proper fix, and when

Find which of those moves the count: run the job's command a few times on one machine with different seeds (`-seed`, the device tree seed) and look at the spread; then pin the cause (a fixed seed under `bench=full`, more iterations, or reading the counts from a user-only counter), and restore the 5% rule's meaning with a re-baseline of the stable numbers. Until then a counts failure that is not a regression of an order of 20% or more is a re-run, not a re-baseline.
