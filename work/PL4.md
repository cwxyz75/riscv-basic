**How.** KERNEL-V1-SPEC 2.3. (1) Early boot (`boot.rs`) is position independent: it computes where the image was loaded and builds the early table from that, not from `KERNEL_PHYS`. (2) `kmain` parses the tree at the pointer from `a1` (`kcore::fdt`, extended as needed): `/memory` ranges, `/reserved-memory`, the memory reservation block, the tree's own extent, the initial ramdisk if any. The frame allocator (MM2) is given exactly the usable ranges. `RAM_BASE`, `RAM_SIZE` and "the top 2 MiB" leave `abi` and `kmem.rs`. (3) `timebase-frequency` feeds one `Timebase { mult, shift }` used by the clock, the timer and the latency trace; `TICK_CYCLES` goes. (4) Hosts tests of `kcore::fdt` with synthetic trees: RAM at `0x4000_0000`, two memory ranges, a reserved range in the middle, a tree placed low in RAM, a 24 MHz timebase.

**Acceptance, written first.** (From MM3, which could not do it with RAM a constant:) at `-m 4G` the page-table frames of the direct map are under 16 (a suite or selftest count of the kernel table's frames; the host test `large_pages.rs` proves the bound at 4 GiB), and the time to the first `##TEST` line at `-m 4G` is recorded with large pages and, for the before, with a kernel built with `plan_range(..., 0)` (4 KiB direct map) once, by hand. QEMU boots of the `k` shard with `-m 128M`, `-m 1G`, `-m 4G` and `-m 8G` report the right frame count each (a suite test compares `debug_stat` total frames with the size the harness passed). The host tests above. No `RAM_SIZE` or `0x8000_0000` literal remains outside tests (grep in the docs check).

**Not verifiable here, said plainly.** QEMU `virt` always puts RAM at `0x8000_0000` and the timebase at 10 MHz, so a different base and frequency are tested only on the host parser and by review.

**Review.** Fable, soak.

## Progress (2026-11-20): PL4a, memory discovery

Part (2) of the item, built on `epic/phase-4` as the named part PL4a. `kcore::fdt` reads every `reg` pair (`Node::regs`), the `memory` ranges, `/reserved-memory`, the memory reservation block and the timebase frequency (`memory_ranges`, `reserved_ranges`, `reservation_block`, `timebase_frequency`); `kcore::memmap::usable_frames` subtracts the reservations (widened outward to whole frames) from the RAM (cut inward to whole frames) and merges. `kmem::init` asks the tree (`dtb::memory_map`), adds the kernel image, and gives the frame allocator exactly the usable ranges (several ranges, MM2's `with_ranges`): the metadata is carved from the first range that can hold it, the direct map covers every usable range with large pages (MM3), and the tree's own frames are mapped read-only. `dtb::locate` reads the tree's extent from the pointer in `a1` through the early table, whose direct map now reaches every gigabyte of physical space up to 128 GiB (`boot.rs`), so page tables can be written into frames wherever RAM is. `abi::layout::RAM_BASE` and `RAM_SIZE` and the "top 2 MiB" are gone. New: `kmem::stats()`, `debug_stat` 24 to 27 (RAM start and end, frames described, frames managed), the harness's `OS_RAM`, the kernel test `ram_matches_the_machine`. The two selftests that assumed a fixed RAM now use what `init` found. Host: `kcore/tests/memmap.rs` (the item's scenarios on synthetic trees: RAM at `0x4000_0000`, two banks, a reserved range in the middle, a tree low in RAM, a 24 MHz timebase; a property test of the range arithmetic against a frame bitmap; the real QEMU tree). Verified: the host tests of `kcore`; the kernel-only boot at four harts with `-m 128M` and `-m 1G` (before the final assertion change), and at the default `256M`, `-m 4G` and `-m 8G` (the final code): 238 tests each, the frame count matching the machine every time. The final code was not re-run at 128M and 1G. Note: QEMU's own tree (what `dumpdtb` shows) has no `/reserved-memory`; OpenSBI adds its footprint to the tree it passes on, so the real boot reserves less than 2 MiB below the image and the rest is ordinary RAM now. **Left in PL4:** (3) the timebase (`Timebase { mult, shift }` from `timebase_frequency`, replacing `TICK_CYCLES` and the 10 MHz assumption in the clock, the timer and the latency trace), PL4b; (1) the position-independent early boot (`KERNEL_PHYS`, the early table's fixed gigabyte slots), PL4c; and the docs-check rule that no `RAM_SIZE` or `0x8000_0000` literal remains outside tests, which waits for PL4c (the early table and the linker script still carry the load address).

## Progress (2026-11-20): PL4b, the timebase

Part (3) of the item. `kcore::timebase::Timebase` (a frequency and a 32.32 fixed-point multiplier; `cycles_to_ns` is one multiplication and one shift, within a nanosecond and a relative 2^-32 of the exact value and exact for rates that divide 10^9; `ns_to_cycles` is the exact ceiling, so a timer is never armed early; both saturate; rates 1 Hz to 4 GHz). The kernel's timer (`arch/riscv64/timer.rs`) keeps the frequency and multiplier in two atomics, 0 until `dtb::init_timebase` sets them from `/cpus/timebase-frequency` right after the tree is located (a tree without one stops the boot); `now_ns` no longer divides; `program` and every deadline in boot code use `cycles_from_ns`; the 10 MHz literals in `smp.rs`, `main.rs`, `smp_tests.rs`, `user_tests.rs` and `latency.rs` are gone; `debug_stat` 105 gives the rate to the suite, whose benchmark conversion no longer assumes 100 ns a cycle. (`TICK_CYCLES` had already gone with L13.) Host: `kcore/tests/timebase.rs` (exactness where the rate divides 10^9, the error bound at ten rates from 1 Hz to 4 GHz including 24 MHz and 32.768 kHz, the ceiling property, monotonicity, saturation; one mutation check: a floor instead of the ceiling fails two tests). Verified: the host tests; the kernel-only boot at four harts (238 tests, exit 0). **Not verifiable here, said plainly:** QEMU `virt` always runs the counter at 10 MHz, so another rate is tested only on the host and by review. Not run: smoke (instruction counts: `now_ns` now has no division, so it should fall), soak. **Left in PL4:** PL4c, the position-independent early boot and the docs check that no `RAM_SIZE` or `0x8000_0000` literal remains outside tests.

## Progress (2026-11-20): PL4c, the load address; PL4 complete

Part (1) of the item. The image is linked at a fixed upper-half address (`abi::layout::KERNEL_VIRT_BASE`, replacing `KERNEL_PHYS` and `KERNEL_OFFSET`) and loaded wherever the loader puts it, at a multiple of 2 MiB. `_start` works out where it is (`la` is PC-relative with paging off), stores `KERNEL_DELTA` (linked minus loaded) and builds the early table from that: a 1 GiB identity page for the gigabyte it runs in, the direct map of the first 64 GiB, and 2 MiB pages over the image (`root[510]` points at `EARLY_L1`); the jump to the upper half and the secondary harts' entry (`sbi.rs`) add the delta; `kmem::init` and the self-tests convert image addresses with `arch::kernel_delta()`. The linker script is a template whose load address `build.rs` fills in (0x80200000, the default QEMU's firmware jumps to, or `$KERNEL_LMA`): defining it with `--defsym` does not work because lld evaluates the script's `AT()` addresses first, which an earlier version of this change found by passing a vacuous test (the binary still said 0x80200000). New: `make os-boot-test-loadaddr` (soak) builds for 0x80600000 and boots the kernel-only shard, with `OS_LOAD`, the kernel-line word `load=` and the kernel test `the_image_is_where_the_loader_put_it`, which fails unless the image's measured start is where the harness said; the docs check refuses `RAM_SIZE`, `RAM_BASE`, `KERNEL_PHYS`, `KERNEL_OFFSET`, `0x8000_0000` and `0x8020_0000` in the kernel, `kcore`, `abi` and `ksys` outside test code (a planted literal in `kcore` was flagged). Verified: the kernel-only boot at four harts, 239 tests, at the default address and at 0x80600000. Not run: smoke, soak, an image at an address that is not a multiple of 2 MiB (the early code stops there on purpose, with no console to say why). **PL4 is done**: PL4a (PR 310), PL4b (PR 311) and this part cover its four parts and the acceptance (the frame counts at 128M, 1G, 4G and 8G; the literals check). The `-m 4G` page-table-frame count and boot-time measurements from MM3 are in this item's acceptance: the host test `large_pages.rs` proves the bound at 4 GiB and the 4G boot passes; the boot-time comparison with and without large pages was not taken.
