**Where and when.** The epic smoke of `epic/iommu-kernel` at `abb97a7` (GitHub Actions run 45913768540, 2026-11-26, job
`kernel (smoke a)`, `make os-boot-test-smoke-a`, four harts, QEMU 11.1.3 built from source on the hosted runner). Every user test
passed (`init: 0 of 315 user tests failed`; no `##TEST ... FAIL` line from the suite), init exited 0, and then four of the kernel's
checks after init failed:

```
process_teardown_returns_every_frame FAIL free frames 59108 -> 56403 (database, caches, stacks, heap: (56799, 43, 66, 2199) ->
  (42837, 88, 8225, 5250); a dying VMO still to drain: false; after one more drain: 56403)
no_process_or_vmo_survives_init FAIL 3 processes and 242 VMOs left (wanted 0 and 2), 0 futex sleepers, 0 pager waiters or pagers;
  (jobs, processes, threads) (1, 5, 1, 10, 128, 3288), wanted (1, 0, 0, 0, 0, 0); device domains, I/O-mapped pages, leaked holds
  [0, 0, 0]; vectors live and leaked [0, 0]
no_kernel_thread_survives_init FAIL kernel threads 5 -> 6
process_exit_releases_all_objects FAIL 10 kernel objects left alive after init exited
```

The checks had already waited 200 ticks for the processes and 200 more for the frames, so this is not a slow teardown. What the
numbers say: one user thread is alive (kernel threads 5 -> 6, and the root job charges one thread); three processes are in the
process table but the root job is charged for five, so two more are between `teardown_take` (out of the table) and
`teardown_memory` (the job credited), or their credit was lost; 128 IPC bytes are queued; the IOMMU and vector counters are zero, so
no device domain or vector was left. A plausible shape (not shown): a live thread of one surviving process is inside a teardown it
started (a `handle_close` or `process_kill` of a never-started process tears it down in the caller, `request_kill`), stuck or very
slow there, with that teardown's victim and a nested one uncredited; candidates for a long stay are the IOMMU drain at the end of
`teardown` (`settle_moves` can retry a route that does not open 4096 times, each bounded by the 100 ms fence bound) and the sliced
handle drain. Which processes they were is not in the log: a process has no name, and the failing check printed only counts.

**What was tried.** Nine local runs of `make os-boot-test-smoke-a` at `abb97a7` (plus the diagnostics below, which change no
behaviour) at four harts with QEMU 11.1.3 (Homebrew, macOS arm64): six one after another on a quiet host, then three at the same
time (host overload). All nine passed the four checks. The three overloaded runs failed only
`a_real_time_thread_stays_responsive_while_hogs_run_and_a_normal_one_does_not` (the host-pause latency of T267/T219), twice. Not
reproduced, so this is rule 11's item. The previous smoke of the epic (run 45906519497 at `84421c9`) did not show it.

**Diagnostics added (the PR that wrote this item).** When `no_process_or_vmo_survives_init` or `no_kernel_thread_survives_init`
fails, the kernel now prints, before the summary:

- `leak: live objects [...]`: every live kernel object by kind, and each process object with its pid and whether it ended;
- `leak: proc <pid>: ...`: every process left: state, detached, privileged, killed and exit codes, stopped, threads alive and their
  ids, its handles by kind (a fingerprint of which program it is), its VMOs, job, object, bootstrap end, exception channel and entry;
- `leak: thread <tid> ...`: every thread that was not there before init started: name, pid, scheduler state, whether it is on a
  hart, its saved return address and the kernel-text words on its stack (`[stack ...]`, link addresses: KASLR's slide is taken off,
  so `python3 scripts/resolve_trace.py <kernel ELF> <addr>...` or `llvm-addr2line -e <kernel ELF>` names where it waits).

**How to reproduce and trace.** `make os-repeat TARGET=os-boot-test-smoke-a N=20` (OD160 permits it), also with two or three boots
at once; the harness prints the serial output of a failing run, and `OS_SHOW=leak:` prints the report lines of a passing one. On the
next occurrence: resolve the `[stack ...]` of the surviving thread; if it is in `teardown`, `iommu::drain` or a settle loop, the
thread is the cause and the fix goes there; if it is in user mode on a hart, a lost kill (the kick IPI) is the suspect; the
`handles` fingerprint names the test whose child it was.

**Closes** only on a named cause or a demonstrated test race (OD160), never on a count of green runs.
