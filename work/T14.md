## Shortcut

**Serial access through a kernel bridge thread** (S4 spec, OD52), not a user-mode driver with MMIO and interrupt capabilities. The bridge **polls** the UART every tick (no receive interrupt), drops input bytes when the process is not reading (counted), and a kernel `##` line can still split a forwarded chunk only between chunks.

## Why it was acceptable

No device-capability objects until S6.

## Proper fix, and when

S6: interrupt object + MMIO VMO; `consoled` drives the UART directly; delete the bridge.

(Migrated from the old TIDY-UP register, section "Services and userland", 2026-11-18.)

## Plan (2026-11-24)

**Premise check first.** The item's "why acceptable" is stale: device capabilities exist (S6a; `devmgr` mints MMIO VMOs and interrupt objects, `init/src/bin/devmgr.rs:107,518`). But the item's "proper fix" as written (**`consoled` maps the UART, the bridge is deleted**) is now **blocked by two later decisions, not by missing mechanism**, and must not be built without an owner answer (Q1 below):

- OD52 / S4-SPEC section 3: every byte to the UART goes through one `kcore::linestate::LineState` in the kernel, so no program can forge or swallow a `##` verdict line. A user process holding the UART page writes THR directly: the guarantee is gone, and it races the kernel's own `put` on the same registers.
- KERNEL-V1-SPEC 2.3 and its amendment of 2026-11-20 (PL5a): the console is a device the kernel drives; its page is cut from every device window and `ns16550a` is not on the allowlist.

What this plan therefore details is the part that is safe under every answer except "move the terminal off the UART": **the kernel keeps the UART, receive becomes interrupt-driven, and the bridge thread blocks instead of polling.** The user-driver end state is sketched as option B and left to the owner.

### 2. Design

**Proposed (option A): kernel-owned receive interrupt, blocking bridge.**

1. `kcore::fdt`: a `console_irq(blob) -> Option<u32>` next to `console_base` (`kcore/src/fdt.rs:243`): the first `interrupts` cell of the same node, only when its interrupt parent is the supervisor APLIC (reuse `aiatree::inherited`). `kcore::aiatree::Aia` gets `console_source: Option<u32>`, bounded like `sources` (1 to 62), and **never** a member of `sources` (a process must not be able to `interrupt_create` it; `irq_allowed` stays as it is).
2. `kcore::rxring` (new, pure, `forbid(unsafe_code)`): a fixed single-producer single-consumer byte ring over atomics (4096 bytes, the size of today's `PENDING_MAX`), `push -> bool`, `pop -> Option<u8>`, `is_empty`, and an overflow counter.
3. `console.rs`: `rx_enable()` / `rx_disable()` write IER bit 0 (offset 1) and enable the FIFO with trigger level 1 (FCR, offset 2); `rx_interrupt()` drains RBR while LSR bit 0 is set into the ring (a full ring still drains the device: drop and count, plus count LSR overrun bit 1), then wakes the bridge thread. No print, no allocation, no UART lock in it.
4. `aia::deliver` (`aia.rs:309`): before the `irq_allowed` test, `if Some(source) == console_source { disable; console::rx_interrupt(); reenable; any = true; continue }`. `reenable` is the existing `aim_and_unmask`, whose set-pending write re-fires a level that is still high, exactly as for user drivers.
5. `interactive.rs`: the loop becomes `wait(ring not empty | socket READABLE or PEER_CLOSED | (pending not empty and socket WRITABLE) | STOP)`, then the same two copies as today. Give `KernelSocket` a `wait(mask, extra_ready, deadline)` built like `KernelEnd::wait_readable`. `run` enables receive before spawning the bridge, and after `STOP` wakes it and disables receive (so `interactive_no_kernel_thread_survives` and a later boot stage see the device quiet). `DROPPED` becomes ring overflow plus overrun.
6. A backstop deadline of 1 s on the wait, with a counter of backstop expiries that found work; the report asserts it is 0. This turns a lost wake into a failing test, not a silent 1 s stall.
7. No UART or `console=sbi`: no input, as today (`console.rs:21-23`). Input through the firmware console stays T262 (T182 part 2).

**Rejected.**

### 5. Invariants, lock order, and how this goes wrong

Rows: **K5** and the lock table in INVARIANTS.md (classes `OBJ` 1, `TT` 8, `RQ` 9, `HEAP` 12, `UART` 14), **X3** (no lock across a switch), **X7** (a wake never switches), S4-SPEC section 3 / OD52 (verdict lines), KERNEL-V1-SPEC 2.3 (the console is the kernel's), and the fail-closed rule of `aiatree` (interrupt objects only for admitted sources).

1. **Lost wake.** `wait_deadline_registered` tests `ready()` before `prepare_block_on` (`thread.rs:1552-1564`). That is safe only because the handler runs under `OBJ` (`trap.rs:717`) and the wait runs inside `bkl::ensure`. Set `STOP` and wake under `OBJ` too. If the external-interrupt path ever stops taking `OBJ` for this source (the `OBJ` split, SC2), the ring check must move after `prepare_block`. Say so in a comment and in the INVARIANTS note; the backstop counter is the tripwire.
2. **Level interrupt stall.** If the handler returns with the FIFO not empty (a full ring, an early `break`), the line stays high, the APLIC sees no new edge and input stops for good. Always drain to empty; keep the set-pending-then-enable order of `aim_and_unmask`.
3. **Handler discipline.** Under `OBJ` with interrupts off: taking `TT`/`RQ` for the wake is in order; taking `HEAP` (a `Vec` push) or printing is legal by class number but must not happen (allocation failure in a trap, recursion through the console). The ring is a static.
4. **The source must stay kernel-only.** If `console_source` leaks into `Aia.sources`, a holder of the root resource can `interrupt_create` it and mask the console's input, and `irq_objs` gets a kernel source. Test it (PR 1) and assert it at boot.
5. **Message id bound.** Source + 1 must be below 64 (`aia.rs:300-302`); a tree with the UART on a high source means no receive interrupt: print one boot line and keep input off, do not fall back to polling silently.
6. **Hart offline and suspend.** `retarget_from` (`aia.rs:259`) moves aimed sources when a hart goes offline: the console source must be in `AIMED`. Verify what the suspend-to-RAM resume path (PM3) restores; IER and FCR are device state the kernel must write again after resume. Not verified in this plan.
7. **Non-interactive builds.** Receive is enabled only between bridge start and stop; with IER set and no consumer every key would be an interrupt that fills a ring nobody reads.
8. **`unsafe` audit.** `try_read`'s SAFETY comment names its callers ("the serial bridge's own thread", `console.rs:27-28`); the caller becomes the interrupt handler. Rewrite it, and keep the T256 (T241 part 3) caveat about the unchecked firmware address.
9. **Reader and writer on one device.** The handler reads LSR while another hart is in `put` under the UART lock. LSR bits 1 to 4 clear on read on real hardware: `put` only looks at bit 5, the handler must latch the error bits it reads. Harmless in QEMU, a real board finds it.
10. **Single hart under icount (T21).** The handler and the bridge share the boot hart; the wake must lead to a reschedule (`deliver` returns true), or echo waits for the next tick and the wake-count test hides it.

**Questions for the owner (not decided here).**

1. **What is the end state of the terminal's device?** (A) the kernel keeps the UART for good and the interrupt-driven bridge is the answer: T14 closes after PR 2 and S4-SPEC, OS-ARCHITECTURE and X-DRIVER-MODEL are amended to say so; (B) the terminal moves to a user-driven device (virtio-console) and the UART becomes kernel-log only: PR 2 is then a stopgap of doubtful value, since under B nobody reads the UART; (C) `consoled` gets the UART as the item says, and OD52's guarantee is retired or kept for test builds only.
2. If B: should PR 2 be built at all in the meantime, or should T14 wait for the X-DRIVER-MODEL spec?
3. May the kernel own a device interrupt of its own (the first source that is neither an interrupt object nor the inter-hart message)? KERNEL-V1-SPEC 2.4 would need an amendment and section 9's "a kernel change needs a reason recorded as a decision" applies once the kernel is frozen.
4. Is a counted drop still the wanted behaviour when a process does not read for more than 8 KiB of input (ring plus pending), or should the bridge stop reading the device and let the sender's flow control (none on this UART) decide?

## Decision (2026-11-24, OD146)

The owner chose option B: the terminal becomes a user-mode virtio-console server and the UART is kernel-log only. Consequences for the plan above: the interrupt-driven kernel bridge (its PR 2) is **not built**, and neither is the kernel-owned UART interrupt or the KERNEL-V1-SPEC 2.4 amendment; the polling bridge stays until the server exists. What is left of this item is the server itself (its own spec first), the harness change, and then deleting the bridge. The plan's PR 1 (the host-only `rxring`) is useful to the server too, but nothing else in it applies. Timing against FZ1: either side is allowed.
