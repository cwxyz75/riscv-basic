title: A sweep still collects its roots whole, and runs its slices under the big lock
refs: [MM10, L19, T76]

MM10 (`Registry::sweep_begin`, `sweep_step`, `shade`) makes the reachability sweep a state machine run in slices of 256 marked objects or slots: a creating syscall starts one when garbage cycles have piled up (`needs_sweep`), runs up to four slices, and the next creating call carries on; near the object cap it finishes the sweep at once, so a creation is never refused while garbage that the sweep is about to free fills the registry. What is not sliced: `UserState::roots()` gathers every handle of every table at the start (O(handles), a vector the size of the root set), and all slices of a call run inside one syscall under the big lock, so the interrupts-off span of a creating call is four slices plus the root scan, not one slice. The spec's version drops the object lock between slices and runs `preempt_point()`; that needs the object lock (L19, `OBJ`) to be a real lock.

Why acceptable: the worst span fell from the whole object graph (16,384 objects at most) to about 1,000 objects plus the roots; the roots are bounded by the handle limits. Proper fix: with L19, take `OBJ` per slice and preempt between slices; slice the root scan by table (a sweep's roots are marked table by table, with the same barrier). The latency trace's worst interrupts-off section with 16,000 live objects (the item's second acceptance check) is a soak measurement and not taken here.

Also not sliced (found in the review of PR 366): **a process's teardown** (`kernel/src/user/lifecycle.rs`) still calls `Registry::sweep`, which finishes a sweep in progress and then runs a whole fresh one with the roots collected whole, inside one `irq::without`: up to two whole-graph passes on every process exit; and the **near-the-cap rule** of the creating calls (`kernel/src/user/trap.rs`) runs a whole sweep in one call, as the old code always did. KERNEL-V1-SPEC 4.6 ("no single section is proportional to the number of live objects") is not met at those two places, so **T76 stays open** until they are sliced too (with L19: teardown's sweep as a series of slices between preempt points). A started sweep also advances only on the five object-creating calls: with none of them it stalls, and cycles closed meanwhile float until the next sweep (a delay only).

**2026-11-23:** a process's teardown now closes its handles and runs its sweep in slices, one critical section per slice (`HandleTable::drain_some`, `teardown_objects`; amendment of the same date). Left: the near-the-cap rule of the creating calls (`kernel/src/user/trap.rs`) runs a whole sweep in one call; `UserState::roots()` is still collected whole at the start of each sweep; and the slices still run under the big lock (`teardown` releases it completely around the two long steps, so each slice is its own hold with a switch point between; each slice is still serialised with every syscall). T76 stays open for the first of these.

**2026-11-23 (L20):** the near-the-cap rule and the sweep a creating call runs are slices too: `sweep_before_create` (before the object section of `dispatch`) starts, steps and finishes the sweep one slice per critical section, with the roots taken in the section that begins it; the creating call itself is its own section afterwards. **Left:** `UserState::roots()` is still collected whole at the start of each sweep (O(handles of every table)), and T76 closes with that.


**2026-11-23 (L20 leftovers):** the root scan is sliced: a sweep starts with `sweep_begin_pending` and `UserState::sweep_slice` shades one process's handle table per slice, the kernel's table last, then `sweep_roots_done` lets it free. A slice of the kernel is never proportional to the whole set of handles now. This needed a second barrier: `remove_for_transfer` shades the object it takes out of a table (a handle moving from a table not yet scanned into the queue of a channel already scanned would otherwise vanish; `kcore/tests/sweep_slices.rs` found it). What is left of the item: the slices still run under `OBJ` (that is its own lock now, and each slice its own section). T76's acceptance (the latency trace with 16,000 live objects) is a soak measurement.

**Precondition (2026-11-24, owner's decision):** before building the rest of this item, have Fable write a design plan and append it here (a section "Plan (Fable, date)"): the root scan marked table by table under the sweep barrier, teardown's sweep and the near-the-cap rule as slices with preempt points, `OBJ` taken per slice, and `channel_call`'s copies outside the object lock (T215's remainder). How reachability is kept (a live object must never be freed) is the first thing the plan must show.

### 1. Reachability: why a live object is never freed

Facts the argument rests on. Roots are the handles of every table in `procs` plus `ktable`. The only strong edge between objects is a handle in a
queued message (`KObj::held`: channels only); peers, watchers, wait registrations, `Process.obj` and thread objects are weak ids, checked by
generation at use. White = `mark != epoch`; grey = on `mark_work`; black = marked and scanned.

Invariant while a sweep is active: (a) no black channel queues a handle to a white object; (b) every handle in a table slot the root scan has
passed names a non-white object; (c) nothing is freed while `roots_pending`, `mark_work` is non-empty or `mark_incomplete`.

1. An object made during a sweep is born marked (`object.rs` create). Keeps (a), (b).
2. A handle enters a table only through `HandleTable::insert`, which shades (create, duplicate, replace, read from a queue, bootstrap). Keeps (b)
   for any slot, scanned or not, so the scan's position in a table does not matter.
3. A handle enters a queue only through `remove_for_transfer`, which shades. Keeps (a) when the source table is unscanned and the channel black.
4. Removing an edge (close, dequeue, drain, destroy) makes no new path. A dequeued handle reaches a table by 2 in the same section.
5. No object reference lives outside `OBJ` across a yield. `Staged` is bytes and raw handle words; `Deferred` is bytes and `Handle` values already
   inserted (2) in the section that took the message; `Call` holds a `Handle`. Sweep state between slices is all in `Registry` and `UserState`
   (`root_scan`, `cursor`, `mark_work`), none on a stack. **Rule for new code: deferred state holds no `ObjId`.**
6. A dying process's table is out of `procs` from `teardown_take`, so its undrained handles are not roots. Safe: no call can name that table, so
   an object reachable only through it dies at the drain anyway; if the sweep dooms it first, the drain's `release` of the stale id is skipped
   (generation). An object also reachable elsewhere is marked through that path. Only the order of PEER_CLOSED differs.
7. When marking ends with (a) to (c), white means unreachable, and an unreachable object cannot gain a handle (nothing to read it from). During
   freeing, mutators only touch non-white or new objects; `sweep_step` drains `mark_work` before it frees.
8. A weak id of a doomed object fails its generation check (BAD_HANDLE or a no-op), never names another object.
9. A yield between slices adds no new kind of mutator: `OBJ` is already let go between slices, so other harts run 1 to 4 today. A switch or an
   interrupt on this hart is one more such mutator (an interrupt object's signal makes no handle).

Not covered by `kcore/tests/sweep_slices.rs` today: 6 (a half-drained table that is not a root), kernel-made messages (`ipc.rs` 524, exception and
bootstrap messages: I did not trace that each carried handle passes 2 or 3), and 5.

### 2. Built, and left

**Built:** the slice machine; roots shaded a table per slice (`sweep_start`, `sweep_slice`); both barriers; teardown's drain and sweep, and a
creating call's sweep and the near-the-cap rule, as one `irq::without` (= `OBJ`, ending in `preempt_point`) per slice; `channel_call`'s big
request staged in and big reply deferred out (`stage_call_in`, `channel_call_reply_deferred`, PR 493). **T215's "Left: `channel_call`'s copies"
is stale.**

**Left:**

- **L1, a bug.** `sweep_before_create` (`kernel/src/user/trap.rs` 1119, 1122, 1124) calls `with_state`, not `locked_state`, outside any section:
  the near-the-cap slices run **without `OBJ`** (`state()`'s debug assert should fire; in release it is a race on the registry).
- **L2, interrupts stay off.** A trap runs with interrupts off from entry to return (`trap_handler`); `preempt_point` switches only if another
  hart set `need_resched`. So the lock hold is one slice (B2) but the interrupts-off span (B1, what T76 measures) is still the whole sweep near
  the cap, and the whole drain, sweep and memory teardown at exit.
- **L3, slices not bounded by 256.** A root slice is one whole table (holes included; `ktable`'s limit is the object backstop). `Registry::release`
  runs its whole cascade in the section: one close can free a chain up to the cap (a channel queues 128 x 64 handles), in `drain_some`, `close`
  and the freeing slice's `dropped_refs` alike.
- **L4, copies.** Big copies are one `AS` hold of up to 64 KiB, not chunks of 16 KiB (3.10). Copies under 1 KiB, the 56-byte record and
  `verify_writable` stay inside `OBJ` (bounded; keep).
- A sweep advances only on creating calls and teardown (a delay only; unchanged).

### 3. Targets and measurement

One unit = one slot looked at, one object scanned, one reference released or one handle closed. **Every `OBJ` section and every interrupts-off
span of the sweep, drain and release: at most 256 units** (4 x 256 for a creating call far from the cap). **Every `AS` hold of a copy: 16 KiB.**
Tooling (`latency-trace`): `latency::irq_off_max` (`debug_stat` 8) and its site, `HOLD_MAX` per syscall, `report()`'s `##BENCH` lines. Smoke
asserts the loose bound of 3.12 (B1 under 20 ms); the 100 us figure with 16,000 objects is the owner's soak (OD142). kcore gets a unit counter
so host tests assert the 256 exactly.

### 4. Design

**A. `irq::window()`**: with no lock held (depth 0, empty held-stack): close the trace span, enable and disable interrupts, start a span, then
`preempt_point()`. Called between slices in the near-the-cap loop, `teardown_objects`, `teardown_memory` and copy chunks. Barrier: item 9.

**B. Bounded release.** `release` stops after 256 units and leaves the rest on the registry's persistent `work` list as owed releases;
`release_step(budget)` drains it. A closing call and teardown loop `release_step` (a section each, a window between) until empty before they
return or mark the process terminated, so what a caller sees at return is as today. Argument: an owed entry is a counted reference of a destroyed
holder, so its target only lives longer; a sweep that dooms the target first makes the owed release a skipped stale id (6, 8). The freeing slice
puts `dropped_refs` on the same list.

**C. Root scan by slot.** `root_scan` keeps (pid, slot cursor); `HandleTable::objects_from(cursor, 256)`. Argument: item 2 holds for any slot; a
process made mid-scan gets every handle by 2; one that exits is item 6.

**D. Chunked copies.** `stage_in`, `stage_call_in`, `finish_out`: reserve the whole buffer first, then per 16 KiB: `AS`, memory locks, copy,
unlock, window. Any failure still returns `None` and the section copies for itself, so **errors and their order are unchanged** (the section
re-reads the record and makes every check; staged bytes are used only if the lengths match). The reply: checked and taken in the section, held as
`Deferred`, copied after; a failed copy loses the message and leaves its handles in the table (the rule `channel_read` has). An interrupt is
taken only inside the two sections, before the send or after the wait, so a retry never sends twice. A kill is acted on at the wait or the
return to user mode.

**Allocation (T177).** R: the staged buffer (`try_reserve`; failure falls back and reports NO_MEMORY as now), `root_scan` (failure: no sweep).
P: `mark_work` (at most one push per live object per epoch; `reserve_for` holds capacity >= live). Skip, never fail: owed releases beyond
`work`'s room leak to the next sweep, as now. N: teardown, unchanged. The window and the cursors allocate nothing.

**PRs 3 and 4 are blocked on the audit the plan's section 7 names, and nothing was built (2026-11-24).** An interrupts-on window inside a syscall means a timer tick or an IPI taken in S-mode **on a user thread's kernel stack with its outer trap frame below it**. The code reads as if only kernel threads and idle ever take such a nested trap: `trap_handler_inner` treats `from_user == false` as "interrupted kernel code (an idle hart, a kernel thread)", takes the big lock for a switch, and calls `activate_current(frame)` with the nested frame; whether `activate_current`, `switch_if_designated` and the FP claim (`light_save` is called only `from_user`) are right for a nested frame whose outer frame belongs to a user thread mid-syscall, and the stack budget of KT13 with a second frame on a syscall's stack, were not audited. A switch inside the nested handler also leaves the thread's kernel stack with two frames across a context switch (as a kernel thread does, but a user thread has an `ecall` frame the return to user mode expects on top). Until that is audited (a Fable review of exactly this, against FP1 to FP3, K4, X4 and KT13) the interrupts-off span stays the whole teardown or near-the-cap sweep, T76 cannot close, and the chunked copies (D) gain nothing. Owner: this is the one item of T206 where the answer decides whether L2 is closable.
