title: A sweep still collects its roots whole, and runs its slices under the big lock
refs: [MM10, L19, T76]
---

MM10 (`Registry::sweep_begin`, `sweep_step`, `shade`) makes the reachability sweep a state machine run in slices of 256 marked objects or slots: a creating syscall starts one when garbage cycles have piled up (`needs_sweep`), runs up to four slices, and the next creating call carries on; near the object cap it finishes the sweep at once, so a creation is never refused while garbage that the sweep is about to free fills the registry. What is not sliced: `UserState::roots()` gathers every handle of every table at the start (O(handles), a vector the size of the root set), and all slices of a call run inside one syscall under the big lock, so the interrupts-off span of a creating call is four slices plus the root scan, not one slice. The spec's version drops the object lock between slices and runs `preempt_point()`; that needs the object lock (L19, `OBJ`) to be a real lock.

Why acceptable: the worst span fell from the whole object graph (16,384 objects at most) to about 1,000 objects plus the roots; the roots are bounded by the handle limits. Proper fix: with L19, take `OBJ` per slice and preempt between slices; slice the root scan by table (a sweep's roots are marked table by table, with the same barrier). The latency trace's worst interrupts-off section with 16,000 live objects (the item's second acceptance check) is a soak measurement and not taken here.

Also not sliced (found in the review of PR 366): **a process's teardown** (`kernel/src/user/lifecycle.rs`) still calls `Registry::sweep`, which finishes a sweep in progress and then runs a whole fresh one with the roots collected whole, inside one `irq::without`: up to two whole-graph passes on every process exit; and the **near-the-cap rule** of the creating calls (`kernel/src/user/trap.rs`) runs a whole sweep in one call, as the old code always did. KERNEL-V1-SPEC 4.6 ("no single section is proportional to the number of live objects") is not met at those two places, so **T76 stays open** until they are sliced too (with L19: teardown's sweep as a series of slices between preempt points). A started sweep also advances only on the five object-creating calls: with none of them it stalls, and cycles closed meanwhile float until the next sweep (a delay only).

**2026-11-23:** a process's teardown now closes its handles and runs its sweep in slices, one critical section per slice (`HandleTable::drain_some`, `teardown_objects`; amendment of the same date). Left: the near-the-cap rule of the creating calls (`kernel/src/user/trap.rs`) runs a whole sweep in one call; `UserState::roots()` is still collected whole at the start of each sweep; and the slices still run under the big lock (`teardown` releases it completely around the two long steps, so each slice is its own hold with a switch point between; each slice is still serialised with every syscall). T76 stays open for the first of these.

**2026-11-23 (L20):** the near-the-cap rule and the sweep a creating call runs are slices too: `sweep_before_create` (before the object section of `dispatch`) starts, steps and finishes the sweep one slice per critical section, with the roots taken in the section that begins it; the creating call itself is its own section afterwards. **Left:** `UserState::roots()` is still collected whole at the start of each sweep (O(handles of every table)), and T76 closes with that.


**2026-11-23 (L20 leftovers):** the root scan is sliced: a sweep starts with `sweep_begin_pending` and `UserState::sweep_slice` shades one process's handle table per slice, the kernel's table last, then `sweep_roots_done` lets it free. A slice of the kernel is never proportional to the whole set of handles now. This needed a second barrier: `remove_for_transfer` shades the object it takes out of a table (a handle moving from a table not yet scanned into the queue of a channel already scanned would otherwise vanish; `kcore/tests/sweep_slices.rs` found it). What is left of the item: the slices still run under `OBJ` (that is its own lock now, and each slice its own section). T76's acceptance (the latency trace with 16,000 live objects) is a soak measurement.
