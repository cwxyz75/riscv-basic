Part of the stability epic (`STAB0`). Moved here on 2026-11-27: T219 and T178 from T267, T21 and T40 from T264 (their text below,
as it was). They are one problem: a bound on host time fails when the host does not run an emulated hart, and nothing in the
boot says whether that happened, so every such failure is argued from load ("a loaded runner") and never shown.

## The parts, as they were

### T219: a_real_time_thread_stays_responsive_while_hogs_run_and_a_normal_one_does_not woke 4299 us late once (bound 4 ms) in smoke a of the phase 9b epic gate

*(area sched, horizon near, refs [L8, OD140, T178])*


**What.** In the epic gate of PR 410 (run 45034672496, head after the L23 test fix) `kernel (smoke a)` failed this test: "a real-time thread woke 4299 us late with a hog on every hart (bound 4 ms)". The same suite on the previous head of the same epic (run 45033938295, smoke a) measured **515 us**, the phase 6c epic's smoke passed it, and the kernel's own probe in the failing run reported `rt_latency_p99` 205 us. The failing head differs from the passing one only in the PI futex tests' change.

**Why it is not just re-run.** TESTING.md rule 11: an intermittent kernel-test failure is a defect until its cause is known. The candidates, none shown: a pause of the shared CI runner (steal time: a vCPU thread not run for 4 ms delays the timer interrupt it should have taken; the bound's own comment says a loaded host delivers one "up to a few ms late"); a real scheduler delay (the wake of a prepared RT thread behind the throttle's `rt_blocked`/`normal_has_work` logic of L25, or the new `PI` lock on the base-priority path (`thread_set_sched` of this test's probe and hogs now takes it)); a regression from the phase 6c locks (`AS`, futex buckets) on the timer path. The test takes the worst of 30 samples, which is the most exposed statistic to a single pause.

**Related.** T178 records the same bound failing on a loaded development machine (seen up to 9.2 ms), for the kernel-thread version of the probe; this is the first time on CI.

**Proper fix.** Reproduce at four harts in a loop (`make os-repeat` over the one test, a soak-sized run: only if the owner asks, or on a repeat in the gate); until then watch `rt_user_latency_max_us` in every smoke a log (515 us, 4299 us so far). If it repeats, print the per-sample lateness and what each hart ran, find the delayed wake, and fix that; if the cause is runner jitter, make the bound a percentile of the samples (the 95th of 30) with the worst case reported, so that a pause cannot fail it while a scheduler that delays every wake still does.

Progress (2026-11-24): the user-mode test now bounds the second-worst of its 30 samples at 4 ms and the worst at 30 ms (a pause of the host delays one wake); the negative control still uses the worst. Kept open until it has passed several gate runs.

~~Cause to name~~ **(2026-11-27, T284: host pause, shown by the injector and excluded by the detector.)** With `OS_HOST_STALL=20:200`
the unchanged epic kernel failed this test in two of three kernel-only boots at four harts (worst 31193 and 32097 us, second worst
about 2.6 ms: the shape of the 2026-11-26 observation), and the T284 kernel, which takes a window again when the pause detector saw a
pause inside it, passed it in every injected boot (see the Stability epic section). The CI sighting itself (4299 us, run 45034672496)
predates the detector and its log holds only the worst sample, so it cannot be classified after the fact; a recurrence now says
`host pause` (or prints `##PAUSE` lines) when it is one, and fails on the bound when it is not.

Observation (2026-11-26, IOMMU7, development machine): a kernel-only boot (`OS_SHARD=k`, two harts, debug kernel) failed it with the
worst sample 21269 us and the second worst 16129 us (`rt_user_latency_max_us` 21269). The host was heavily loaded: a four-hart boot
and a cargo build of a second kernel ran at the same time. The same kernel passed at one, two and four harts when the boots ran one
after another on an otherwise idle host. This fits the host-pause candidate (two samples above 16 ms, both above the second-worst
bound). No kernel cause was shown.


### T178: realtime_thread_stays_responsive_under_load fails on a loaded development machine (bound 4 ms, seen up to 9.2 ms)

*(area testing, horizon near, refs [OD140, T174, L13])*


The kernel test `realtime_thread_stays_responsive_under_load` (`kernel/src/sched_tests.rs`) asserts a wall-clock bound: a real-time thread woken by a timer while three hogs run must be at most 4 ms late. On the development machine, whenever it is busy with other builds or QEMU runs, the emulator delivers the timer interrupt late: 12 of the 180 failing-boot logs kept under `target/fail-logs/` hold this failure, with lateness from 1.7 ms to 9.2 ms (today's, 6.4 ms, was one failure in a `make kquick` run that was never reproduced in eleven reruns). The bound's own comment records that 2.2 ms was seen. It is not a defect of the kernel's wake path (the idle and tickless work of L13 measure it in instructions elsewhere) but of measuring a latency in host time on a shared host; it is the same class as T174 and is closed the same way. Why acceptable for now: a rerun passes and CI runners have not shown it. Risk: a flaky gate (OD140). Proper fix: measure the same wake with no hogs in the same boot and bound the loaded lateness by a multiple of it plus a floor, or run the test under `-icount` where the guest clock is the instruction count, then tighten.

Seen again 2026-11-21 (the overnight soak, three boots at a time, and later two chaos jobs beside other builds and boots): `realtime_thread_stays_responsive_under_load` failed on every loaded boot (woke 5 to 31 ms late against the 4 ms bound), and once `wait_is_woken_by_the_peer_closing` ("the close came after about 3 ticks (waited 0)") failed in a one-hart boot beside two chaos jobs and passed in the next two runs: the same cause (host load), a second timing test with a tight bound to review in the same pass.

Progress (2026-11-24): the bound is now on the 99th sample (the next to worst of 50) with the worst held to 30 ms, so one pause of the host cannot fail it; the negative control still uses the worst. Kept open until it has passed several gate runs; the second timing test named above (`wait_is_woken_by_the_peer_closing`) is still to be reviewed.

~~Cause to name~~ **(2026-11-27, T284: host pause, shown by the injector and excluded by the detector.)** Two findings. (1) The
"99th" of 2026-11-24 was the worst: `late[len * 99 / 100]` of 50 samples is index 49, so one pause still failed the test; with
`OS_HOST_STALL=20:200` the unchanged kernel failed it in three of three boots ("woke 31728000 ns late (99th 31728000 ns)", 28.4 and
27.5 ms), the 5 to 31 ms of the 2026-11-21 soak. It is now the next to worst. (2) The development machine's own host lateness, measured
by the detector: the emulator takes a timer interrupt programmed T ahead about T / 2 late (a 3 ms sleep about 1.6 ms, a 10 ms slice end
5.04 to 5.09 ms, an 8 ms timer 4.05 ms), with the hart running and interrupts on. That is why the probe's lateness here is 1.6 ms when the
same test measures 36 us under `-icount` (guest time), and why a loaded machine reaches several milliseconds. The old logs under
`target/fail-logs/` hold only the worst sample (34 of 438 logs there hold this failure, 1.7 to 84 ms), so they cannot be reclassified;
the next failure names a pause itself. `wait_is_woken_by_the_peer_closing` uses the detector too (below); its 100 ms stall after a
send is T167's (T287), not this item's.

Progress (2026-11-26, IOMMU5): `wait_is_woken_by_the_peer_closing` reviewed and fixed. On the IOMMU machine (`iommu-sys=on`) at two harts it failed with "waited 0" in most kernel-only boots: 5 of 7 with the IOMMU5 kernel, and 1 of 3 with the unchanged epic kernel on the same machine, against 0 of 4 on the old machine. The test's `tt:` time was 83 to 123 ms although its wait returned at once, so the suite thread was held off about 100 ms around its `channel_write`, after the send. The helper's three ticks ran out meanwhile. The test now reads its clock before the send, so the close can never look early (lower bound 2 ticks). The stall itself, a user thread on a two-hart machine not running for about 100 ms right after a send that wakes a kernel thread, is the latency of T167 above: not diagnosed, and still open.


### T21: Timing-based tests follow the host clock

*(area testing, horizon long, risk M)*


#### Shortcut

**Timing-based tests follow the host clock** (and the SMP suites are not run under icount at all: with several vCPUs QEMU runs them in fixed turns and a spin lock needs the other CPU's turn for every handoff, which made `-smp 2` time out) (QEMU tick = host millisecond), so windows have slack and fail on loaded machines (the round-robin kernel on CI flaked twice).

#### Why it was acceptable

Simple and independent of the code under test.

#### Proper fix, and when

A virtual-time/icount mode for the timing tests (also needed by S5), with strict windows.

~~**Timing-based tests follow the host clock**~~ **(2026-11-27, T284: host pause, shown by the injector and excluded by the detector.)**
A timing test now tells a pause of the host from a kernel delay (the pause detector, `debug_stat` 216 and 217): the windows a pause
covered are taken again. The guest-time half, where it was cheap: the counts boot (`make os-count`, one hart, `-icount
shift=0,sleep=off`) already ran `realtime_thread_stays_responsive_under_load`; the harness now puts `guesttime` on its kernel line and
the test holds every one of its 50 wakes to 1 ms of guest time there (measured 36 us; the planted-delay kernel fails it with 5217 us).
No boot was added and the job's length is unchanged (70 s locally). The SMP suites under icount stay out (the fixed turns of the
vCPUs, above).


### T40: S5 test gaps

*(area testing, horizon long, risk L)*


#### Shortcut

**S5 test gaps.** (The clock part, reproduced 2026-11-14 and **not fixed**: counting timer interrupts loses time when an interrupt is late, but deriving ticks from the `time` counter makes every deadline in the suite follow real stalls, and at four harts a boot sees about 70 stalls of 15 to 90 ms on hart 0, which timed out `blk_round_trip` and woke the real-time probe late; the fix waits for deadline-robust tests, the benchmark baseline (task 1) and the nanosecond clock of OD91.) The churn stress has no process or job churn (it churns channels, VMO mappings, sockets, events, ports, threads and yields) and the unmap test uses a different-contents VMO rather than a refilled canary; the SMP suites run in debug builds only for K1; only hart 0 advances the scheduler's tick time, so tick-based bounds loosen when hart 0 spins on the lock. (The frame oracles are now exact, no slack.)

#### Why it was acceptable

Adequate to catch the bugs the negative controls target.

#### Proper fix, and when

Process/job churn and a wake-protocol shuttle model with T38. **SMP review fix (2026-11-14): advance the tick count to `(time - t0) / TICK_CYCLES` instead of counting handler runs, so lock contention cannot stretch deadlines.** Plan: resolved by SCHED-SMP-SPEC task 3.

(2026-11-27, T284) Struck or moved, part by part:

  so a stall of the host moves it; the timing tests now take a window a pause covered again. Under `OS_HOST_STALL=20:200` at four
  harts (about 480 stalls of 20 ms per boot) `blk_round_trip` and the other tick-based bounds of the kernel-only boot passed in every
  boot, before and after T284; the one other bound the injector broke was `a_runaway_rt_thread_does_not_hang_the_system` (one boot of

- ~~Only hart 0 advances the scheduler's tick time~~ (stale since L13): every hart takes its own one-shot timer and brings its own

- ~~The churn stress without process or job churn~~: built by T265 (2026-11-27): `crash` churn operation 6 (jobs of never-started

## Stability epic (2026-11-27)

**The cause to name.** For each sighting class (the real-time probe late, `wait_is_woken_by_the_peer_closing`, the tick-based
bounds of T40), show which of two causes it is: (a) the host did not run the hart's thread (a pause), or (b) the kernel delayed
the wake. Today (a) is a reading in every one of these items; the 2026-11-26 observation in T219 (21 ms worst, heavy host load)
fits (a) and proves nothing.

**Scope (one PR).**
1. **A host-stall injector** in the harness: `OS_HOST_STALL=<ms>[:<period ms>[:<seed>]]` stops the QEMU process (SIGSTOP) for
   the given time at seeded random moments, then continues it (SIGCONT), and prints each stall as `##HOSTSTALL <t> <ms>` on the
   harness side. It is the deliberate host stall that T266 (T197 Q4 of its plan) and T287 need as well. A harness self-test
   shows the stall lands (the guest's `time` jumps by at least the stall).
2. **A pause detector in the guest** that the timing tests read: per hart, the lateness of the hart's own timer interrupts
   against the deadline it programmed (Sstc `stimecmp`), kept as a small ring of the last samples and readable through a
   `debug_stat` selector (test kernels only, documented in `SYSCALLS.md` as such). A test window in which any hart shows a timer
   interrupt later than its bound by more than the test's own bound is reported as `host pause` with the hart and the size,
   in the failure message and on a `##PAUSE` line.
3. **The tests use it.** `realtime_thread_stays_responsive_under_load`, the user-mode real-time test of T219,
   `wait_is_woken_by_the_peer_closing` and the tick bounds named in T40 keep their bounds; a window that a pause covers is
   re-sampled (bounded: three windows), and a test fails if three windows in a row are covered (a host that never runs the hart
   is still a failure) or if a window without a pause is late. The negative controls (the latency negative control that uses
   the worst sample) must still fail.
4. T40's other parts: the churn stress without process or job churn is built by T265 as its reproduction stressor (strike it
   there); "only hart 0 advances the tick time" is stale since L13 (per-hart one-shot timers): check and strike.
5. T21's other half, where it is cheap: a timing test whose bound only makes sense in guest time runs under `-icount` at one
   hart in the counts boot (`os-count`) instead, if it fits that job's budget (measure; do not grow tier 1, rule 2).

**How to investigate.**
- Start from the logs that still exist: `target/fail-logs/` on the development machine (T178 counted 12 of 180 there) and the
  CI logs of the runs named in T219 (`gh run view 45034672496 --log`). Print, for each failure, the per-sample lateness.
- Reproduce (a) on purpose: one kernel-only boot at four harts with `OS_HOST_STALL=20:200` must fail the latency tests today
  (that is the injector's own acceptance), and pass with the detector.
- Reproduce (b) on purpose: a kernel with a planted delay in the real-time wake path (a `fault-` feature, as the other negative
  controls) must fail with and without the injector.

**Tools.** The injector and detector built here; `-icount` (no OD: QEMU's own); record and replay does not help (record mode
runs every hart in one TCG thread, so a host pause of one hart cannot happen there: use that as a second discriminator, a
failure that also shows under `OS_RECORD` is not a host pause).

**Acceptance (runnable, each under two hours).** (1) the injector self-test; (2) `OS_HOST_STALL=20:200` makes today's kernel fail
`realtime_thread_stays_responsive_under_load` in one boot and the new kernel pass it in five of five boots (`make os-repeat
TARGET=os-ktest-4 N=5` with the variable set: about 30 minutes); (3) the planted-delay kernel fails in five of five; (4) the
existing latency negative control still fails; (5) the parts close only on the cause shown by (2) and (3) (OD160): T219, T178
and T21 are struck naming "host pause, shown by the injector and excluded by the detector", T40's clock part likewise, and any
sighting that the detector does not cover stays open with its log.

## Results (2026-11-27, PR 617)

**Built.** The host-stall injector (`scripts/host_stall.py`, `OS_HOST_STALL`, `##HOSTSTALL`, its `--self-test` in the docs check and the
guest's `a_host_stall_is_seen_by_the_guest`). The pause detector (`kernel/src/pause.rs`, rule `kcore::pause`, host tests
`kcore/tests/pause_rule.rs`, `debug_stat` 216 to 218, `##PAUSE`). A window counts as covered only when two harts took a timer interrupt
later than the test's bound inside it (a pause of the emulator stops every vCPU; a kernel delay is on one hart). A sentinel 1 ms ahead
after each taken interrupt, and a 1 ms heartbeat while a test watches, close two blind spots that the first version had (stalls were seen
to land between a taken interrupt and the re-arm, unseen, three times in one boot). The tests of scope point 3 use it; so does
`a_runaway_rt_thread_does_not_hang_the_system`, the one other bound the injector broke. Two planted-delay controls
(`fault-rt-wake-late`, `fault-rt-wake-late-irqoff`) and the injected boot are in `os-boot-test-sched-neg` (soak).

**Runs** (development machine, debug kernel, kernel-only shard at four harts unless said; one at a time; each boot about 2 minutes):
- The injector self-test (host): passes; its control (no injector) sees no gap.
- (2) Today's kernel (`epic/stability` at ab83c95f) under `OS_HOST_STALL=20:200`, seeds 1 to 3: fails
  `realtime_thread_stays_responsive_under_load` in three of three boots (31.7, 28.4, 27.5 ms); the user-mode test failed in two
  (31.2, 32.1 ms worst), the runaway test in one (254 ms billed in one 100 ms window).
- (3) `fault-rt-wake-late`: fails on its bound in five of five boots with `OS_HOST_STALL=20:200` (seeds 1 to 5: 99th 8.9 to 10.1 ms,
  two to four windows retaken for 30 ms pauses) and two of two without (99th 8.9 ms). `fault-rt-wake-late-irqoff`: fails on its bound
  in three of three with the injector and one of one without, each naming "a timer interrupt 4 to 5 ms late on hart 0 alone (not a
  pause of the host)". Under `-icount` (one hart, `guesttime`) the first fails the 1 ms guest-time bound with 5218 us; the normal kernel
  passes there (36 us).
- (4) The latency controls (`the_latency_test_can_fail`, the user test's equal-priority probe) passed (that is, the load was seen to
  load) in every boot above of the normal kernel.
- (2) The new kernel under `OS_HOST_STALL=20:200` (`make os-repeat TARGET=os-ktest-4 N=5`, 603 s): 5/5. The first repeat (with the
  kernel before the last fix, 609 s) was 4/5: the fifth boot failed `harts_go_offline_and_come_back` ("the sleepers made 5 wakes in
  10 ms ... (baseline 26); window 25148 us"), a fourth sighting class the injector showed: a 20 ms stall inside its 10 ms window. Its
  windows are now taken again when a pause covers them (two harts more than 2 ms late; no heartbeat there, which would wake the
  offline hart it counts). The same kernel passed the kernel-only boot without the injector (107 s).
- Mutation checks (host test `pause_rule`): the covering rule taking any one hart, `covers` ignoring the late span, the resampler's
  `>=` for `>`, its give-up count off by one, and `rearm` dropping the cancelled interrupt each fail the test; restored, it passes.

**Struck** (above): T219's and T178's causes, T21's shortcut and T40's clock part, on the cause shown by (2) and (3): host pause,
shown by the injector and excluded by the detector. **Not covered by the detector, open:** the CI sighting of T219 (run 45034672496,
4299 us) and the old development-machine logs, which hold only the worst sample (a recurrence now names a pause itself); the 100 ms
stall of a user thread after a send in `wait_is_woken_by_the_peer_closing` is T167's (T287). What the two-hart rule still cannot tell
from a pause is a kernel delay shown on two harts at once (a lock held with interrupts off while another hart spins for it); only the
three-in-a-row rule catches that, and `make os-latency` measures such spans (TEST-TOOLS.md).
