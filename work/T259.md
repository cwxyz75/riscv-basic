### T83: Task 9 leftovers

*(area sched, horizon long, risk M)*


#### Shortcut

**Task 9 leftovers** (`thread_spawn`):

- (1) `MAX_THREADS_PER_PROCESS` (2048) still exists beside the job's thread limit; SCHED-SMP-SPEC 5.3 removes it once launched programs get their quota (done: 128) and the `thread_limit_and_slots_are_reused` test is rewritten around a job limit.
- (2) Every stack release costs a full shootdown (an IPI to every hart) and `unmap_region` walks every page of the stack: OD93's ranged shootdowns and a pending-set of harts that ran the process would cut it.
- (3) The thread object limit is the handle table: a thread handle per thread, so a 4096-handle process cannot hold more than about 4000 joinable threads (detached threads have none).
- (4) `a1` = tid is set only for `thread_spawn`; `thread_create` and the first thread still start with `a1` = 0.
- (6) the stack arena is not protected from `process_map`/`process_unmap`: a program can map into it or unmap a spawned stack (self-harm only; `free_spawn_stack` unmaps by address, accounting balances)
- (7) `pthread_create`'s handle hand-off (`handle_of`) spins on `thread_yield`, which can livelock under strict priorities if the creator is lower priority than the thread: have the kernel store the handle before the thread runs, or wait on a futex
- (8) guards: the guard above a stack is at least the stack's own guard size, not the neighbour's, when sizes differ
- (9) no test for the other start registers being zero, a cross-process successful spawn, or a stale-TLB negative control (Fable review of task 9, findings 3, 6, 9); (5) `ROUND_ROBIN` is recorded (`thread_get_sched` shows it) but the scheduler has no round-robin class yet.

#### Why it was acceptable

None is a safety problem

#### Proper fix, and when

- (1) with T79's limit review
- (2) with OD93
- (3) with the handle-table work
- (5) with the scheduler class work

### T168: AB2 leftovers: ns-grain tests for futex, port and channel_call, the ticks_to_ns shims, hart 0's first clock step, a mixed-clock watchdog

*(area sched, horizon near, risk L)*


#### Shortcut

AB2 (PR 270) moved the ABI to nanoseconds. Left, from the Fable review (2026-11-19): (1) the acceptance asked for 1000 sleeps and checks at nanosecond grain for every wait; the suite has 300 `object_wait_ns` waits of at most 3 ms and a 5 ms check, none for `futex_wait_ns`, `port_wait_ns`, `channel_call_ns` or a `u64::MAX` deadline; (2) `ticks_to_ns` and `sleep_ticks` remain in `thread.rs`; (3) hart 0's scheduler clock stays 0 until its first tick, which then advances by all the time since (`BOOT_COUNT` is set by the first secondary): harmless now, inflates the boot thread's `cpu`, matters once RT budgets are enforced (`set_clock(0, now_ns())` once the timer is running, while never ahead of the real clock); (4) the starvation watchdog samples every 100 ticks (tick count, which lags) but its limit is 500 ms of real time; (5) the C transcript's `clock_gettime` check against a host oracle; (6) the many millisecond bounds in the suite are real time now and about 2.6 times tighter under load than when ticks dilated: the soak run (owed) shows the margin.

#### Why acceptable

The ABI is right and `make smoke` is green; these are test breadth and precision.

#### Proper fix, and when

Do (1) to (3) with L13, which replaces the tick; (4) falls with it. (5) with the next libc work. (6) from the soak result.

### 2. Design, per PR

**2.A PR 1: the scheduler core (kcore, plus two kernel lines). Kernel slice: its own feature PR and a Fable review.**

1. **T169 (1), balance without a tick.** Keep the rule (a hart takes one equal thread from a queue at least two longer) and its mover (the destination, under `lq2`). Add the trigger: in `tick_on`, after the settle, the ticking hart `g` looks at the `queued_len` hints; if an online hart `x` has `len(x) + 2 <= len(g)` and `view_cur(x)` is not above `g`'s best movable queued thread, `mark(x)`. Move the `balance(h)` call from `tick_on` into `settle_with` (after the pull loop), so a marked hart balances when it serves the mark. A hart with a queue of equals always has a slice event, so the offer repeats every slice until the gap is below two. *Rejected:* `g` moving the thread itself (the first move where a hart changes another's queue for a thread it does not outrank; today only the destination moves, which keeps RQ1/TR1 reasoning one-sided); a periodic balance timer on short harts (a tick again, KERNEL-V1-SPEC 5.1); the fair class (T72, `someday`).
2. **T170 (1).** Add `fn slice_event_for(cand: Prio, cur_eff: Prio) -> bool` to `Class` as an associated function (no `self`: `after_enqueue` holds no lock and reads hints), default `cand >= cur_eff`, `RoundRobin`: `true`. `after_enqueue` (`sched_smp.rs:1138-1142`) asks the band's class instead of comparing. *Rejected:* marking on every remote enqueue (an IPI per wake in the default build).
3. **T170 (4).** `spawn_on`: `self.charge_now(target)` before `self.lq(target)` in the loop (the pattern of `wake_inner`; `charge_now` takes and releases the lock itself, so no nesting). Check `adopt_current_on` and every other `fresh_as` caller the same way.
4. **T170 (5).** In `HartRq::charge`: when `slice_left` reaches 0 and the thread's class reports no `next_event` for it (no equal or better peer), refill to the class's slice, as `account` does. *Rejected:* routing `charge` through `account` (it returns "rotate now", which `charge`'s callers do not act on).
5. **T211.** Narrow the excuse at the three sites to `held && band(eff) == Band::Rt`, run the two recorded seeds (904 step 331; 964 step 67) and read the state dump `audit` prints. Hypotheses, most likely first: (H1) `pull_work` computes `mine = cur_eff.max(queued_top())` (`sched_smp.rs:917`), and `queued_top` counts the destination's own held-back RT threads, so a throttled hart running priority 15 with a queued RT 40 refuses a normal 19: use the best queued thread that `dst.would_run`; (H2) `push_marks_with` reads `would_run_hint(x)` for `x != g` (`sched_smp.rs:855-859`), published before `x` entered the throttle; (H3) `balance`'s `p < cur` test has the same blind spot as H1. Fix what the dump shows, keep the narrow excuse. If two days do not find it, put the wide excuse back and add the dump to this section.
6. **T107 (4).** `debug_assert!` in `pull_work` that the destination's level `p` is empty at `attach`; strike the sub-item.
7. **Hart 0's clock.** `sched.set_clock(0, now_ns())` in `thread::init` before `adopt_current_on`. The timer must be up first: check the order of `timer::set_frequency` and `thread::init` in `kernel/src/main.rs`; `now_ns` before `MULT` is set returns 0 and the call is then harmless but useless.

### 5. Invariants, locks, and how this goes wrong

- **Rows:** GP1 (PR 1 changes both what satisfies it and what excuses it), TR1 and RQ1 (`balance` moves to `settle_with`: it must keep skipping threads in transit and re-check under `lq2`, as now), ID1 and the poke contract (every new `mark` needs its poke bit: `sched2_kernel_walk.rs` checks it, extend the walk to the balance offer), NM1 (the T211 fix must not let an RT thread run on a spent hart: `sched2_rt_budget.rs`), AC1 (the hart 0 clock and the `spawn_on` charge change who is charged), PK1 and PK2 (untouched, but the walks check them on every step), X7 (a mark never switches: the offer is a mark, nothing more), AF1 (balance respects `allowed`), PR1-PR2 (PR 2 and PR 4), HT1 (no mark for an offline hart: `mark` and `balance` already test `is_online`).
- **Locks:** `RQ` (class 9, per hart; two at once only in ascending hart index through `lq2`), `TT` (8, before `RQ`), `PI` (7, held by `set_priority_held` around the scheduler call: `set_attr_on` keeps that order), `OBJ` (1, the syscall section in PR 2), `JOBS` (6, the `max_prio` read). No new class and no new nesting. `charge_now(target)` in `spawn_on` must not be called with any `RQ` lock held.
- **Subtle failures to look for:**
  1. *Ping-pong.* The offer and the mover read hints; if the offer uses "2 longer" and the mover re-checks "2 longer" under the locks, a thread cannot bounce, but an offer on stale lengths costs an IPI per slice for nothing. Count offers in the convergence test and bound them.
  2. *Balance inside `settle`* runs on every look at the queues, not once per tick: it must stay O(harts) on hints with at most one `lq2`, and must not loop (one thread per settle, as now one per tick). Re-check `pair_scaling` at the epic smoke, since T267 watches the same path.
  3. *A user-mode lone runner now takes an IPI* when a neighbour's queue is two longer. That is the point, but `user_mode_ticks_take_no_big_lock` and the lone-runner interrupt counts (`smp_tests.rs:805-880`) have tight allowances.
  4. *The T211 fix widens what a throttled hart pulls.* If `mine` ignores held-back RT threads, check the moment the window ends: the hart then holds a normal thread it pulled and an RT thread it should run at once; `restore_demoted` and the window-end event must mark it.
  5. *The slice refill in `charge`* must not refill a thread whose equal peer is queued (it would never rotate): the condition is the class's `next_event`, not `slice_left == 0` alone. `tick_starvation.rs` is the guard.
  6. *The watchdog change removes a repair.* Any lost arm or lost poke the 100 ms `tick_on` has been hiding in debug builds becomes a `starved thread` panic at the next smoke. That is a real defect each time (TESTING.md rule 11): expect it, do not put the tick back; this is why PR 3 follows PR 1.
  7. *`rr` on a donated thread:* the class reads `cur.base.rr` with the effective priority; a normal-band thread boosted into the RT band has `rr` false and runs FIFO there. Decide in the PR whether that is right and say so in SYSCALLS.md (4.5 is silent).
  8. *`SUSPENDED` in `pthread_create`:* a thread killed or a process exiting between spawn and resume must not leak the TCB or hang `exit`; a detached create must not take this path.
  9. *Strict `Held::release`* can turn a harmless double release on a panic path into a second panic: keep `Uart` lenient.

## Stability epic (2026-11-27)

**Why it is in the epic.** Three of what OD157 kept are failure sources, not features: T83 (7) `handle_of` spins on
`thread_yield` and can livelock under strict priorities (a hang); T83 (8) a later stack with a small guard can sit inside an
earlier stack's larger lower guard (an overflow that the guard does not catch); T83 (6), OD157 (1): the stack arena refuses
`process_map` and `process_unmap`, which turns the class of T272 and T251 (a fixed address that a randomised stack lands on) from
a rare refusal into a deterministic one. T168 (3), hart 0's clock, books the whole boot to the boot thread under enforced RT
budgets (the plan's second finding). The rest (T83 (9) tests, T168 (1) the nanosecond-grain waits, (2) the shims, (5) the C
transcript's clock) are the checks that would catch a regression of the same paths.

**Scope (one PR, kernel and libc).** The plan's 2.B items 3 and 4 (`pthread_create` through `SUSPENDED` plus `thread_resume`; the
guard spacing), 2.B item 5 with OD157 (1) and (2) (the arena refusal; `SYSCALLS.md` states the handle-table bound), 2.A item 7
(hart 0's clock) and 2.C items 3 and 5 and 2.D's T168 (5). Not the scheduler-algorithm parts (T268, OD150).

**How to investigate.** The livelock first, on the host: the C transcript test of the plan (a creator that lowered its priority
below the new thread's creates and joins 100 threads inside a deadline) hangs today; a shuttle model of the hand-off is cheap if
the transcript cannot show it at one hart. The guard overlap: the `ksys` address-arithmetic test of the plan (spawn A with a 64 KiB
guard, B with a 4 KiB guard until it lands next to A). The arena refusal: a suite test that maps into the arena at a fixed address
and expects INVALID_ARGS, and a sweep of `init/src/bin/*.rs` for literals in the arenas (T272 moved them; confirm none is left).

**Acceptance (each run under two hours).** The plan's section 4 rows for 2.B items 3 to 5, 2.A item 7 (hart 0: `the_boot_thread_is_not_charged_for_boot`)
and 2.C items 3 and 5, each written first and seen to fail; one targeted kernel-only boot at four harts. Review by Opus.
