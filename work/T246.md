title: The syscall epilogue allocates infallibly, so the guest allocation-failure sweep does not count it
area: kernel
horizon: long
refs: [KT9, T177]
---

**What.** `notify_held` (the cleanup of dead objects, the pager's closed-channel reap, the wake commit with `WaitTable::commit`'s `fired` and `keep` vectors and its watch maps, the heap service) and `cow_sync` run after every call and must not fail: a failed allocation there would leave a waiter asleep or a copy-on-write translation stale. They allocate with the infallible collections, and a guest sweep that failed them ends in a panic on the first scenario (`WaitTable::commit` at N=3 of the channel scenario). The `fault-alloc` kernel therefore leaves them out of the count (`heap::epilogue`).
**Why acceptable.** The kernel heap grows from the frame database at safe points and a creating call reserves room first, so an epilogue allocation meets a heap with headroom in every run the suite makes; a kernel with no frames left is the one place it would panic.
**Proper fix.** Make the commit allocation-free (the woken list into a per-hart buffer sized by the thread count; the `fired` set as a mark on the registration) or, when it cannot get memory, release every registration so each waiter re-checks (the `overflow` path already does that without allocating if the list is a cursor over `regs`); the same for `cleanup_dead`'s vectors. Then remove `heap::epilogue` and let the sweep count them.

Also: when `cow_sync` finds no memory for its list of address spaces, the caller's own space is still synced (translations dropped on every hart) and the rest of the log stays pending until the next call or fault; other spaces may hold a stale entry for that long. The proper fix is the same: no allocation there. `AsLocks::all` returning `NO_MEMORY` is also new for `process_start`, `thread_spawn`, `pager_supply` and the process-table calls (SYSCALLS.md lists NO_MEMORY for each).
