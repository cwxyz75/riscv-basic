title: KT14: aliased `&mut` through nested `with_state` and the FP tables' `state()` (undefined behaviour by the language rules; no machine-level corruption found)
area: kernel
horizon: long
refs: [KT14, L20]
---

**What.** The KT14 audit (`docs/records/reviews/2026-11-23-kt14-unsafe-audit.md`) found that `user::state()` hands out a `&'static mut UserState` and that a closure of `with_state` can call a function that opens `with_state` again while the outer `s` is live: `lifecycle.rs` `leave()` -> `pi_thread_gone`; `calls.rs` `thread_write_state` -> `state_write` -> `fp::write_fp`/`write_vec` -> `charge_state` -> `job_of_thread`; `waits.rs` (`killed_now`/`interrupted_now` inside a closure); `lifecycle.rs` `suspend_blocks` (`commit_wake` inside the closure). Likewise `arch/riscv64/fp.rs` `write_fp`/`write_vec` take `state()` and call `drop_claim`, which takes it again. Two live `&mut` to one object is UB and a miscompilation hazard where the outer one is used after the nested call. The lock half holds (no cross-hart race; no closure reaches a context switch). User mode reaches all of them (`thread_write_state`, PI futexes).
**Why acceptable.** No corruption path was found; development only.
**Proper fix.** Pass `s` (or the pieces) down instead of re-opening; make the nested helpers take `&mut UserState`; the FP tables get `drop_claim(s, ..)`. This is T225's accessor work. Test: Miri cannot run the kernel, so a debug build counter of nested `with_state` depth that asserts 1.
