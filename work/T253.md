title: KT14 second review: the weak points that stay (kernel stack slice, firmware window fallback, public guard fields, a release check of the FP lock)

**What.** The second independent review of KT14 (2026-11-24, `docs/records/reviews/2026-11-24-kt14-second-review.md`) found no memory-safety path reachable from user mode. What it left, with the change that fixes each: (1) `kstack.rs` `Deref` forms a slice over a kernel stack a thread may be running on (a read of guard and dead words, aliasing by the letter of the rules): use volatile or atomic reads in `guard_intact` and `stack_used`; (2) `aia.rs` `reg()` falls back to base 0 when `info()` is none (every caller is gated by `irq_allowed` today): a `debug_assert!(info().is_some())`; (3) the `kmem` guard structs (`Kmem`, `KmemAs`, `Mem`, `Frames`, `JobsRef`) have public reference fields, so safe code could move one past the guard's drop: make the fields private and expose methods; (4) the FP tables' `state()` and `user::state()` assert the lock in debug builds only: a hard assert at the first `state()` call or the claim in the comment kept honest; (5) `calls.rs` `general_of` can read a thread's frame while the thread writes its reply on another hart (T241 holds the race; diagnostic only); (6) not traced by the reviewers: whether `cow_sync_held` is ever reached with an `AsLocks` live (a nested take of the same address-space locks), whether the entry-frame jump is always at big-lock depth 1, whether `heap::service` can run on a parked hart through a device interrupt, whether thread ids are never reused (`light_save` relies on it).
**Why acceptable.** Each is a debug-checked or caller-held condition that holds on every path found; none is reachable from user mode.
**Risk.** A future caller breaks one of the conditions and a release build does not notice.
**Proper fix.** The six changes above, in one pass, then audit the changed blocks again (the hash check lists them).
