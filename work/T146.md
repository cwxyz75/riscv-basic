## Shortcut

**File names are UTF-8: enforced at the file protocol since 2026-11-17 (step 0b, the `names` crate), the layers around it are not done** (owner, 2026-11-17). *Done:* one rule in `names`, used by `proto::file::valid_name`, `memfs` and `doofs` (names and attribute names), refused with `EILSEQ`, tested (goldens, a property test against `std`, the `memfs`/`doofs` differential, the `ctest mount` QEMU checks). *Left, and the rest of this entry:* `fsck` has no finding for a name on an old volume that breaks the rule (test volumes are regenerated); the symlink-target components use the rule only where `check_link_target` is called. The text below describes the state before step 0b and the items that still apply. Before it, `proto::file::valid_name` accepted any bytes except NUL and `/` (and `.`/`..`, over 255 bytes), so every server and client treated names as bytes: `memfs`, `doofs` and `fsd` store whatever arrives; the libc passes bytes through; the shell's `ish` lists names with `from_utf8_lossy` (a name that is not UTF-8 shows as U+FFFD and cannot be typed back); BusyBox and `ls` print raw bytes to the terminal; no test makes a non-ASCII or an invalid name (the one place that keeps bytes on purpose is the shell's start path for `xargs` and `find -exec`). When step 0b lands (the roadmap's F section), a name must be valid UTF-8 without control characters, and the rest of this entry is what has to follow it:

- (1) every layer agrees on one rule, a single function in `proto::file`, used by `memfs`, `doofs`, `fsd`, `memfsd`, `rt::fs` and the libc (`EILSEQ` for a refused name)
- (2) goldens and the `memfs`/`doofs` differential gain non-ASCII and invalid-byte cases
- (3) the libc test corpus gains a non-ASCII name through `open`, `readdir`, `rename`, `symlink` and `glob`
- (4) the shell and the terminal show and accept names as text (`ish` completion and quoting, `ls` column widths with wide characters: needs `wcwidth`, the libc's wide-character batch in WORK-PLAN plan 2)
- (5) archives and the ported programs that carry raw bytes (`tar`, `gzip -N`, `unzip`) have a defined behaviour for a name that is not UTF-8 (decided 2026-11-17: the file system refuses it with `EILSEQ`, silent replacement is not used because it makes distinct names collide, and the program reports the error and goes on; if extracting such archives ever matters, patch `tar` with a special mode that escapes invalid bytes reversibly, outside the file system). Names are stored as given, not normalised: look-alike names stay possible (T141). Normalisation and look-alike names stay in T141.

## Why it was acceptable

The rule was decided before the disk format was frozen so that nothing stored ever has to be repaired; until step 0b the system is byte-transparent, which is harmless for ASCII.

## Proper fix, and when

Step 0b (mechanical, specified in `FS-SPEC.md` F6), then items 2 to 5 as their own small slices; do 0b before more programs that create names are ported.
