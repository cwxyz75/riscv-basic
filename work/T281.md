title: The IOMMU has run only on QEMU virt's riscv-iommu-sys; no second machine type or real hardware
area: platform
horizon: someday
risk: M
complexity: H
change_risk: L
refs: [IOMMU-SPEC, OD148, T42, X-DRIVER-MODEL, IOMMU5, IOMMU12]

**What.** Everything the IOMMU epic proved in a guest (IOMMU5 to IOMMU12: default deny, the domain calls, MSI translation,
the hostile-driver matrix) ran on one implementation: QEMU's `riscv-iommu-sys` on `virt` with `iommu-sys=on` and one ECAM
host. The kernel reads the IOMMU's capabilities and the device tree's `iommu-map` and refuses what it does not support, so a
different implementation fails loudly rather than silently, but nothing has exercised: an IOMMU as a PCI function
(`riscv-iommu-pci`, which QEMU also has), several IOMMUs, a capability set other than QEMU's (no MSI flat or MRIF mode, other
page-table modes, a fault queue of another size), wired-interrupt rather than MSI signalling of the IOMMU's own queues, real
hardware's timing for the bounded fence (T274), or a real APLIC (T262's T59 part).

**Why acceptable.** QEMU `virt` with `-cpu rva23s64` is the only target (OD47, OD127); no RISC-V board with an IOMMU is in
reach of the project, and the kernel fails closed on anything it does not recognise.

**Risk.** The first real board, or a QEMU change of defaults, finds a path no test covered: the most likely are a capability
the kernel refuses (the machine does not boot, loudly) and a fence that takes longer than its bound (counted, leaked, IO8).

**Proper fix, and when.** A second QEMU configuration in the soak tier first (`riscv-iommu-pci` in place of the platform
device, and one with a reduced capability set if QEMU can be told to offer one), then one real board as a periodic hardware
gate (X-DRIVER-MODEL). Do it when a board with a RISC-V IOMMU is a target, or before the kernel's IOMMU code is frozen.
