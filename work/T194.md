title: QEMU prints "virtio: zero sized buffers are not allowed" during full-suite boots
refs: []
---

Found by the first full soak (2026-11-21, QEMU 11.1.3): QEMU's stderr carries `virtio: zero sized buffers are not allowed` several times at the start of boots that run the network and disk tests (five times at the start of one four-hart `os-boot-test` run, and again in the serial `lossy` and `smp` runs, which pass). It means a guest queued a descriptor of length 0 on some virtio queue; QEMU 11 refuses the request and may mark the device broken. In the parallel soak the same boots also showed `net_tcp_to_the_host_server` failing (the failures did not reproduce when each target ran alone, so they were load or a shared host port, see T195), so it is not shown that this message causes a failure. Not found by reading `netdrv`, `blkd` and `rngd`: the net transmit descriptor is `HDR_LEN + len` (never 0), the receive ones are filled at start, `blkd` handles a zero data length, `rngd` asks for `CHUNK`. Next step: run one boot with QEMU's `-trace virtio_*` (or a debug print in the three drivers' queue code) to see which device and queue, and whether it comes from a driver restart test (`net_faults_are_survived`) where a stale available-ring entry points at a descriptor the new driver zeroed. Why acceptable: every boot with it passes. Risk: a latent driver bug that a stricter QEMU turns into a lost connection.
