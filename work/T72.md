## Shortcut

**The normal band has no fairness**: fixed priority and round robin; a high-priority spinner starves lower ones, a program gets a share per thread

## Why it was acceptable

Today's behaviour, kept on purpose

## Proper fix, and when

The hierarchical fair class (SCHED-SMP-SPEC 4.7), deferred

(Migrated from the old TIDY-UP register, section "Concurrency and kernel structure", 2026-11-18.)

## Plan (2026-11-24)

**Status of the premise.** Not overtaken: the shortcut is real and the fix is still deferred on purpose. KERNEL-V1-SPEC 1 (line 33) lists "a fair scheduling class" as a v1 non-goal and `WORK-PLAN.md` ("Not in this plan") names T72; no OD entry decides the open points of SCHED-SMP-SPEC 4.7. So this plan is for *after* the v1 freeze and must not be started inside a v1 phase without the owner saying so.

**Evidence that would justify starting** (any one): (a) the owner asks for per-program CPU shares or a per-job CPU quota; (b) a real workload shows the starvation (an interactive session stalls behind a higher-priority or many-threaded job; `os-bench` or the suite records it); (c) PR 1's fluid-model report, which is cheap and host-only, shows a share error above the tolerance on a scenario that occurs in the system (not only on a synthetic one); (d) three or more parts of T259/T258 that say "fix: the fair class" are otherwise ready to close. PR 1 alone may be done at any time as measurement; it changes no kernel behaviour.

### 2. Proposed design

A third normal-band class `Fair` in a new pure file `kcore/src/fair.rs`, selected by a new feature `sched-fair` beside `sched-round-robin` (OD32's mechanism, unchanged). RT band, idle band, precedence, NM1 and the RT budget code are not touched.

1. **Per hart, EEVDF over threads.** `class_words` = `[vruntime, vdeadline, lag, weight]`. Weight from `eff` by a 31-entry constant table (`1024 * 1.25^(prio-16)`, integers, generated once and checked by a test against the formula). A hart keeps the weighted average virtual time `V` and the weight sum. Eligible: `vruntime <= V`; pick: earliest `vdeadline` among the eligible; `vdeadline = vruntime + slice * 1024 / weight`. `account` advances `vruntime` by `ran * 1024 / weight` and reports "slice over" when the deadline is passed and anything is queued; `next_event` is `None` for a lone runner (OD131: no event without a competitor).
2. **Priority stops being an order inside the band.** `displaces` returns false for normal against normal (as `RoundRobin` does, `sched2.rs:407`); wake preemption is `preempts(cur, now)` (the woken thread is eligible and has the earlier deadline). `would_run`'s early `cand <= cur` test must move behind the class for the normal band. The class still reports one priority to the other bands and harts through `top()`; for `Fair` that is a constant band level, so pull and push move normal work only to idle harts or by load (3).
3. **Across harts: virtual time is per hart; lag travels.** On `Deq::Migrate`/`Enq::Migrated` and on block/wake the class stores `lag = V - vruntime` (clamped to one slice either way) and re-bases on enqueue (`vruntime = V_dst - lag`). Load is a per-hart atomic weight sum in the hint record (next to `queued_len`); `select_hart` for the normal band picks the least-loaded allowed hart unless the last hart is within a margin; `balance` compares weight sums, not queue lengths, and runs at the slice end and on a mark (T169 (1)'s fix).
4. **Hierarchy, depth one, by weight division (second PR set).** A thread's weight is `prio_weight * job_weight / runnable_threads_of_the_job`, with `cpu_weight` and a runnable count kept as atomics in `JobSchedTable` and the weight re-read lazily at `enqueue` and `account` (the idiom the RT demotion already uses: nothing walks a job's threads, no lock under `RQ`). `ThreadSched.group` gets the job slot.
5. **Donation inside the band:** a boosted thread takes the larger of its own and its donor's weight while boosted (`Enq::AttrChanged` keeps lag, never resets it). Charging the donor's entity (T77) stays out.

Rejected:

| Alternative | Why not |
|---|---|
| Full per-hart entity tree per job (the letter of 4.7, Linux group scheduling) | needs group shares recomputed across harts and per-group per-hart queues: the hardest part of CFS, for a system with tens of jobs. Keep as the fallback if (4) misses the fluid tolerance |
| One global virtual time / a shared fair queue | a global lock or a contended atomic on every switch; contradicts 4.4's rejection of a shared queue |
| Decay-usage priority adjustment on top of `FixedPrio` (BSD style) | small, but gives no weights, no per-job share and no bound to test against |
| Stride/lottery or plain weighted round robin | no latency control for sleepers (no lag), which the interactive session needs |
| Changing the ABI priority range or adding a "nice" call | 4.7 says the ABI does not change |

### 5. Invariants, locks, and how this goes wrong

- **Lock classes.** All class state is per hart under `RQ` (9), at most two `RQ` locks, ascending hart index. Job weight and counts are read as atomics; `JOBS` (6) is before `RQ` in the order, so it must never be taken from the class (the ledger writes the mirror while it holds `JOBS`, as `set_budget` does). `TT`, `PI` and `OBJ` are not touched. No new lock class.
- **Rows.** GP2/C4, AF1, AC1, NM1, TR1/RQ1, X7 and DN1 to DN3 must hold unchanged. **GP1 changes**: for the normal band under `Fair` it reduces to work conservation (no idle hart while an allowed normal thread is queued); new rows are needed (names to be allotted): bounded lag per thread on a hart, weight-sum hint equals the queued weights at quiescence, lag is preserved by migration and by `AttrChanged`. PR1/PR2 (limits never exceed the parent's) extend to `cpu_weight` semantics once it is live.
- **Subtle failures.** (1) sleeper gaming: a thread that sleeps briefly, or calls `thread_set_sched` on itself, must not gain lag (clamp, never reset on `AttrChanged`); (2) fixed-point rounding makes the lags not sum to zero and `V` drift: use wrapping comparisons relative to `V` and test long runs (weight ratio 31 to 1 is about 800:1); (3) migration ping-pong between harts of near-equal load (the margin in design 3); (4) a remotely queued normal thread that arms no slice timer on a lone-runner hart (T170 (1) again: every queued `Fair` thread is a slice event, so `after_enqueue` must mark); (5) the T211 excuse in the audit widens silently if the normal clause is rewritten carelessly; (6) a demoted RT thread arrives at `DEMOTED_PRIO` 31, the heaviest weight (Q6); (7) kernel threads pinned to hart 0 skew load placement; (8) tests that rely on "higher normal priority runs first" (suite, libc, `pthread_create`'s `handle_of` spin, T83 (7)) change meaning; (9) any allocation added to enqueue or wake worsens T257 (use the existing queue storage or a fixed structure); (10) the debug watchdog's 500 ms limit can fire for a priority-1 thread legitimately held to 0.1%.
