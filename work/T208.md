title: MM7 left out: the C library's mmap/munmap/mprotect, the protect-versus-sibling-write negative control, per-job region counts

MM7 (KERNEL-V1-SPEC 3.5, 4.5) was built in 2026-11-21 except:

1. **The C library**: `mmap`, `munmap` and `mprotect` for anonymous memory are not mapped onto `process_map` (ANYWHERE), `process_unmap` (ranges) and `process_protect` yet (`libc/`, `oslibc`): that is user-space glue over calls that now exist and are tested; the allocator idiom (map twice the size, trim) is tested directly in the suite (`process_protect_and_range_unmap_from_user_mode`).
2. **The negative control** `fault-protect-no-shootdown` and the QEMU test "protect to read-only while a sibling thread writes": the shootdown after a downgrade is in place (`proc_call` asks for it when `ProtectStats::downgraded`) and tested on the host (`ksys/tests/proc_calls.rs`: counts), but no boot shows a stale writable translation on another hart (QEMU's timing, as for T193).
3. **The region count per job** (PL8): `MAX_REGIONS` (65,536) is still the per-address-space limit; the spec has a per-job `regions` level.
4. **ANYWHERE's choice** takes a uniformly random start and the first gap from there, wrapping once, not the spec's "8 random positions then first fit": a start just below a large occupied range is likelier than one in a wide gap's middle, so the placement is not uniform over gaps. Why acceptable: the address is unpredictable to a process that cannot read the pool; the bias is slight. `aslr=off` (first fit) is not built: the pool gives 0 only when unseeded.
5. **The page-table charge of a split mapping**: `table_charge` is kept per original region start; after a range unmap or a protect splits a mapping, the credit comes back when the piece at the original start goes (or at teardown), not piece by piece. No leak; the credit can be early or late by the part that is left.
6. **`process_map_info`'s VMO field** is the VMO store id, not a kernel object id (a region does not know its VMO object); stable for a VMO's life.
