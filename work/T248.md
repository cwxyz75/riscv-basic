**What.** Process teardown and kill (`request_kill`, the exit paths), exception delivery (`ksys/src/exception.rs`), the donation graph (`kcore::donate`), PI futexes (`kcore::pifutex`: four maps) and pager waits (`kcore::pager`) allocate with the infallible collections, inside `heap::nofail` (counted per file by `scripts/check_docs.py`, `NOFAIL`). None is in KT9's scenario list.
**Why acceptable.** Each runs for a thread or process that already exists and cannot be refused (a kill, a wake, a fault report); the allocator's reserve covers them (T247).
**Risk.** As T247: an estimate, defeated by fragmentation.
**Proper fix.** Prepay each from the thread record (`ksys::UThread`) or the process record at the R point that creates the thread, so that the later step allocates nothing; the `NOFAIL` row of the file then goes. When: with T247, or when one of them is opened.

## Plan (Fable, 2026-11-24)

A plan from a reading of the code on `bundle13` (nothing was built or run for it). Four feature PRs into the epic. No lock class is added or
moved; every new structure is data under the lock that protects its predecessor.

### 0. What the code says (corrections to "What" above)

The item says every site is inside `heap::nofail`. Reading the callers, **four are not**, and they are worse than class N: they use the
infallible collections as class R, so a refused allocation is a kernel panic (`handle_alloc_error`), in the single-failure sweep and under
real exhaustion once class R is refused below the reserve:

- **`futex_lock_pi` / `futex_unlock_pi`** (`kernel/src/user/waits.rs` 195, 272; dispatched bare at `trap.rs` 949-950). `PiFutexes::lock`
  does `recs.entry().or_insert_with`, `waiting.insert`, `owned.entry().or_default().insert`, and returns `Vec<Change>`; `unlock` does
  `outcomes.insert`, `owned.entry()`, a `rest: Vec<Tid>` copy. They run under `FUTEX` then `PI`; `is_class_n` (`heap.rs` 202) knows only
  `nofail_depth`, `Tt` and `Rq`.
- **A pager wait** (`waits.rs` 375 `pager_wait`, from the page-fault path `trap.rs` 821 and from two in-call paths): `ksys::pager::
  pager_wait_begin` -> `Pagers::wait` (`waits.insert`, `requested.insert`, `unsent.push_back`), `pager_flush`'s `msg` vector, the `woken`
  vectors, `pending_wake.extend`.
- **Fault delivery** (`trap.rs` 879 `raise_fault` -> `ksys::exception::deliver` -> `offer`): the object and handle creations are fallible and
  undone (the level "does not take it"), but `msg` (`exception.rs` 131, 40 bytes) is an infallible `Vec`.
- **`teardown_take`** on the exit path (`lifecycle.rs` 209, reached from `leave`, which is not under `nofail`): `Futexes::forget_process`
  collects a vector when a sleeper of the process is still queued (the backstop case only).

None has a guest scenario (which is why the sweep is green). They are the first things to fix; PR A starts with them.

Also read: `Changes` (`donate.rs` 40) is already a fixed array; every `.to_vec()` of it in `thread.rs` 1258-1303 exists only because
`pi_op` takes a `Vec<Change>`. `AsLocks::all` (`aslocks.rs` 90) allocates only when the boot scratch is out or `procs.len()` exceeds
`AS_HELD_MOST` (64, which `Backstops::processes` is clamped to, `limits.rs` 48).

### 2. Data structures

**`kcore::donate::Donations`**: `nodes: FMap<Tid, Node>`, `Node { base, eff, out: Option<Tid>, first_in, next_in, prev_in: Option<Tid> }`,
`reserve_thread() -> Result<(), NoMem>`. `recompute` and `height` walk the list (both are order-free: a max). `audit` additionally checks
that every `out` edge is on exactly one list and the lists have no cycle.

**`kcore::pifutex::PiFutexes`** (one per futex bucket):
```
recs:    FMap<Key, Rec { owner: Tid, waiters: VecDeque<Tid> }>      (a record exists only while somebody waits)
waiting: FMap<Tid, Waiting { key: Key, outcome: Option<Outcome> }>  (`outcomes` folded in: a hand-over or a death is a field write)
to_wake: Vec<Tid>                                                   (capacity >= waiting.len(), kept across drains)
```
`owned: BTreeMap<Tid, BTreeSet<Key>>` goes: `owned_keys(owner)` is a scan of the bucket's `recs` (thread exit only, behind `PI_USED`),
exposed as `next_owned(owner, after: Option<Key>) -> Option<Key>`. `still_waiting(t)` is `outcome.is_none()` on a present record;
`take_outcome` removes it. Every count is bounded by the waiters (one `Waiting`, at most one `Rec` and one `VecDeque` slot per waiting
thread), so the one reservation in `lock` pays for the whole later life: hand-over, `cancel`, `dissolve`, `owner_died`, `forget_process`.
`VecDeque` and `FMap` removal never allocate. The `Vec<Change>` results become the sink of section 1; `drain_wake` becomes
`drain_wake(&mut self, f: impl FnMut(&[Tid]))`. `owner_died` handles one key per call (`owner_died_one(dead, key, word)`), so
`pi_thread_gone` is a loop of: next owned key, resolve its word, `owner_died_one`, poison, wake from `to_wake`; its four collections go.

**`kcore::pager::Pagers`**:
```
pagers:   FMap<u64, ()>                (existence; `create` is try_insert)
waits:    Vec<(Tid, Wait)>             capacity >= admitted; push at `wait`, swap_remove at `cancel`; lookups are linear in the current waits
unsent:   VecDeque<Request>            one queue for all pagers, capacity >= admitted (`unsent(pager)` is the first of that pager)
woken:    Vec<Tid>                     scratch, capacity >= admitted
admitted: usize
```
`requested: BTreeSet` goes: a page is requested exactly when a wait without a result names it, which is what `cancel` already computes
(`pager.rs` 181). `cancel` already drops the unsent request with the last waiter, so `unsent.len() <= waits.len() <= admitted` holds; the
audit asserts both. Rejected: the wait as a `UThread` field (zero bookkeeping, but `finish` would walk every thread of the system per
supply, and `pager_model` would lose its self-contained table). Linear lookup is acceptable while pager waits are few; if `pager_model` or a
benchmark says otherwise, index by `FMap<Tid, u32>` reserved in `admit`.

**`UserState`**: `job_exc: FMap<JobId, Handle>`, `pager_ends: FMap<u64, Handle>`; `pending_wake` reserved by `Pagers::admit`'s caller.
`reserve_thread` gains `self.pagers.admit()?`; `unregister_thread` gains `retire()`. No new field in `UThread` is needed: the per-thread
records of this item live in tables keyed by tid that are reserved at the thread's R point, which is what "prepaid from the thread record"
comes to.

### 6. Blockers and decisions (nothing here is decided by this plan)

- **D1 (owner decision, `kind: decision` item to file with PR A).** A fault that cannot be delivered for want of memory (the exception
  object, the thread handle, the queued message) is today passed to the next level and finally ends the process. The alternative is to
  prepay one exception object and message per thread while a channel covers it, which a job channel makes unbounded to track. This plan
  keeps today's behaviour and writes it down in SYSCALLS.md. KERNEL-V1-SPEC 3.6 does not say; 4.2 says only "NO_MEMORY, never a panic",
  and a fault has no status.
- **D2 (spec text, not changed).** SCHED-SMP-SPEC (the `futex_lock_pi` entry at line 1330) lists `futex_lock_pi`'s errors without NO_MEMORY. SYSCALLS.md already
  lists more than the spec (NOT_SUPPORTED, SHOULD_WAIT), and `futex_wait` gained NO_MEMORY the same way in PR 3a, so PR A follows that
  precedent in SYSCALLS.md only. If the owner reads the spec's list as closed, PR A's lock path needs the per-thread prepay instead (an
  `admit` per bucket is not possible; it would need one `PiFutexes` wait record per thread in a global table): say so before PR A starts.
- **D3 (`job_kill` never reports NO_MEMORY).** This departs from T177's review note, which listed it as reportable. No spec text is
  involved; noted so the owner can object.
- Not a blocker: `kcore::jobsched::sync_budgets` (called by `job_set_sched`) was not read; if it allocates it needs a reserve at
  `job_create`.
