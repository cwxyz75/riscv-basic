### T216: PI futex: the WAITERS bit is not cleared when the last waiter gives up, and a thread id above 2^30 cannot use a PI futex

*(area sched, horizon long, refs [L23])*


**What.** (1) SCHED-SMP-SPEC 4.8 says the kernel clears `WAITERS` in the lock word when the last waiter leaves the queue (a timeout, a kill, an interrupt). The kernel does not touch the word on that path (L23): the page may be gone by the time the waiter wakes, and the kernel's own physical address of the word is only good under the big lock and the address-space lock held at the call. The bit stays set; the owner's next unlock (user mode: the compare-and-swap of its tid to 0 fails because of the bit) falls to the kernel once, which finds no queue and writes 0. (2) The lock word holds 30 bits of owner id and thread ids are 64 bits (AB3), so a thread whose id is 2^30 or more gets NOT_SUPPORTED from both PI calls.

**Why acceptable.** (1) Costs one system call per give-up, never a wrong answer. (2) A billion threads created by one boot; the ids are assigned in order, so a normal system never reaches it.

**Proper fix.** (1) Re-resolve the word under the `AS` lock when a waiter gives up and clear the bit with a compare-and-swap if the queue is empty (a failed resolve is fine: the word is gone). (2) A second word format, or ids that wrap within a process (a thread's id as the process sees it), if a program ever needs more.

### T217: a PI futex lets one confined program lend a real-time priority to a normal-band thread without being charged for it

*(area sched, horizon long, refs [L23, L25, T77])*


**What.** A process with a real-time-base thread W and a normal-base thread L: L takes a PI futex and spins, W blocks on it with no deadline. L then runs at W's real-time priority. The job's real-time budget (L25) charges only threads whose **base** is real-time (`charge_job`), so L's time in the real-time band is not billed and L is never demoted; only the per-hart cap of 80 ms in 100 ms (NM1, when the normal band has work) applies. The donation graph also ignores demotion: a demoted donor still lends the priority it had before it was demoted.

**Why acceptable.** The program can only do this to itself and its own job's threads, so it gains nothing a program with a real-time thread did not have; the per-hart cap keeps the normal band alive. T77 records the same for `channel_call` across processes. The budget's purpose, bounding a runaway real-time thread, is met for the threads that are real-time by their own priority.

**Proper fix.** Charge the real-time band by **effective** priority (a thread running in the band on a donation is billed to its own job, and demoted like one), and have a demoted donor lend its demoted priority. It needs the accounting to know why a thread is in the band; do it with L22 (donation through `channel_call`), which has the same question.

### T218: PI futex work done with interrupts off is quadratic in the waiters, and a thread's exit scans every bucket once any PI futex has had a waiter

*(area sched, horizon long, refs [L23])*


**What.** (1) `futex_unlock_pi` retargets every remaining waiter to the new owner; each retarget recomputes the owner's effective priority over its growing set of donors, so n waiters cost O(n^2) in one interrupts-off, big-lock region (a process may have thousands of threads). (2) After the first PI wait (`PI_USED`) every thread exit takes all 64 futex bucket locks and the donation graph's to look for PI futexes it owns. (3) The compare-and-swap loops in the lock, unlock and poison paths have no bound against another hart changing the word without end.

**Why acceptable.** A PI futex with thousands of waiters is the case the user-level mutex is not for; the exit scan is 64 uncontended locks; the retries are geometric in practice. None is a wrong answer.

**Proper fix.** Keep the donors of an owner as a count and a maximum instead of a set (the donation graph's `recompute`), and retarget in one step; index the PI owners (a counter of owners per bucket, scanned only when non-zero); bound the retries and return BAD_STATE for a word that will not settle.

### T221: no donation between a call's request being queued and the server reading it (the provisional edge of SCHED-SMP-SPEC 4.8 at wake)

*(area sched, horizon long, refs [L22, L24, T77])*


**What.** L22 lends the caller's priority to the thread that **reads** the request; L24 places the woken server on the caller's hart (direct hand-off). Between the wake and the read the woken server runs at its own priority: a low-priority server that was woken but not yet scheduled (the harts busy with higher-priority work) is not boosted until it reads. SCHED-SMP-SPEC 4.8 wants a provisional edge at wake, confirmed or dropped when the thread reads.

**Why acceptable.** The common case, a server blocked in receive, is placed on the caller's hart by the hand-off and runs as soon as the caller blocks. A server that waits on a **port** (the service runtime) is registered on the port, not on the channel end, so the commit cannot tell which woken thread serves this call without more bookkeeping.

**Proper fix.** Have the wait table report which object each released registration was on (and, for a port poller, which bound object's touch released it), match it to the call's peer end, and `retarget` the caller's edge from the provisional waiter to the thread that reads (`pi_lend` of `lend_to_reader` already would have to retarget instead of refusing a second donation).

### T77: Donation gaps

*(area sched, horizon long, risk L)*


#### Shortcut

**Donation gaps**: CPU time and RT budget are not donated; a chain longer than 8 or a cycle gets no boost (the boost between a request being queued and a server reading it was built in L22 and L24; its provisional edge at wake is T221)

#### Why it was acceptable

The common case (a server blocked in receive) is covered by hand-off

#### Proper fix, and when

The donation at the queueing of a request and the hand-off are built (L22, L24); what remains is CPU time and RT budget donation (with the fair class) and chains longer than 8 (T221 for the provisional donation at wake).
