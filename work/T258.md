### T216: PI futex: the WAITERS bit is not cleared when the last waiter gives up, and a thread id above 2^30 cannot use a PI futex

*(area sched, horizon long, refs [L23])*


**What.** (1) SCHED-SMP-SPEC 4.8 says the kernel clears `WAITERS` in the lock word when the last waiter leaves the queue (a timeout, a kill, an interrupt). The kernel does not touch the word on that path (L23): the page may be gone by the time the waiter wakes, and the kernel's own physical address of the word is only good under the big lock and the address-space lock held at the call. The bit stays set; the owner's next unlock (user mode: the compare-and-swap of its tid to 0 fails because of the bit) falls to the kernel once, which finds no queue and writes 0. (2) The lock word holds 30 bits of owner id and thread ids are 64 bits (AB3), so a thread whose id is 2^30 or more gets NOT_SUPPORTED from both PI calls.

**Why acceptable.** (1) Costs one system call per give-up, never a wrong answer. (2) A billion threads created by one boot; the ids are assigned in order, so a normal system never reaches it.

**Proper fix.** (1) Re-resolve the word under the `AS` lock when a waiter gives up and clear the bit with a compare-and-swap if the queue is empty (a failed resolve is fine: the word is gone). (2) A second word format, or ids that wrap within a process (a thread's id as the process sees it), if a program ever needs more.

### T218: PI futex work done with interrupts off is quadratic in the waiters, and a thread's exit scans every bucket once any PI futex has had a waiter

*(area sched, horizon long, refs [L23])*


**What.** (1) `futex_unlock_pi` retargets every remaining waiter to the new owner; each retarget recomputes the owner's effective priority over its growing set of donors, so n waiters cost O(n^2) in one interrupts-off, big-lock region (a process may have thousands of threads). (2) After the first PI wait (`PI_USED`) every thread exit takes all 64 futex bucket locks and the donation graph's to look for PI futexes it owns. (3) The compare-and-swap loops in the lock, unlock and poison paths have no bound against another hart changing the word without end.

**Why acceptable.** A PI futex with thousands of waiters is the case the user-level mutex is not for; the exit scan is 64 uncontended locks; the retries are geometric in practice. None is a wrong answer.

**Proper fix.** Keep the donors of an owner as a count and a maximum instead of a set (the donation graph's `recompute`), and retarget in one step; index the PI owners (a counter of owners per bucket, scanned only when non-zero); bound the retries and return BAD_STATE for a word that will not settle.

### 2. Design, per part

**T218 (1): one-step hand-over.** Add `Donations::hand_over(new: Tid, waiters: impl Iterator<Item = Tid>) -> Changes`: unlink each waiter from
its target and link it to `new` (both O(1), the intrusive list), then `propagate` once from each distinct old target and once from `new`. It cannot
be refused: `new` has just been revoked, so it lends to nobody (`up(new) == 0`, no cycle), and each waiter's `height + 1` already fitted under the
old owner. `unlock` calls it in place of the retarget loop, which today swallows an `Err` and would leave PF1 broken. Cost: O(n), one change list.
- Rejected: *a count and a maximum per node* (the item's wording). A maximum cannot be lowered without the multiset when the top donor leaves; the
  exact version is 64 counters per thread, prepaid, to save a scan that the unlock's best-waiter pick does anyway.
- Rejected for now: slicing the hand-over across `irq::window()`s. It would open PF1 between slices. If B1 (100 us, SCHED-SMP-SPEC 3.12) is
  measured broken by a legal waiter count, that is a new item with a number in it, not a guess here.

**T218 (2): look only when the dying thread has donors.** By PF1 every queued waiter donates to its record's owner (a stale record too:
`audit`, `pifutex.rs:483`), so a thread with no in-edge owns no record. Add `Donations::has_donors(tid)` (`first_in.is_some()`), call it under `PI`
first in `pi_thread_gone`, and skip the bucket scan when it is false. `PI_USED` goes. The check and the scan are separated by a released lock,
which is sound only because both the exit and `futex_lock_pi`'s enqueue run under the object lock: say so in a comment that names T70.
- Rejected: per-bucket atomic record counts (the item's wording): 64 more atomics to keep exact on five paths, and a thread with no waiters still
  reads all of them. Rejected: a per-owner key list: user code takes the lock with no call, so the kernel learns of an owner only from a waiter;
  the list would need a lock above the buckets.

**T218 (3): bound the retries.** `const SETTLE_TRIES: usize = 16` in `pifutex.rs`. `lock` and `unlock` return `PiError::BadState` when the word
changed that many times under them (before anything is queued or handed: check that the `reserve_waiter` room taken on an abandoned pass is
harmless, it is only capacity). `poison` gives up silently (its waiters are already ended with `Died`). `SYSCALLS.md` gains the BAD_STATE case for
both calls. The tests' `Word` gets a mode that changes on every load.

**T216 (1): clear `WAITERS` on the last give-up.** The order forces the shape: `AS` (2) is before `FUTEX` (4), so the give-up path becomes
`locked_state` -> `AsLocks::one` -> resolve -> bucket -> `PI`. Steps: (i) a new `ksys::futex_pi_peek`, a translate-only resolve: it commits
nothing, breaks no copy-on-write, raises no pager need (a page that is not there and writable means skip; `futex_pi_resolve` would allocate and
set the `take_need` slot, see `waits.rs:326-330`); (ii) `PiFutexes::cancel` takes `Option<&W>` and, after `leave_queue`, if no record is left for
the key and the word is `owner | WAITERS` with no `OWNER_DIED`, makes **one** compare-and-swap to `owner` (a failure is fine: someone else moved
it); (iii) a dead process or a failed resolve passes `None`. Then drop the sentences in `SYSCALLS.md:1141` and `pifutex.rs:11`, and amend PF1-PF2.
- Rejected: clearing it from the woken thread without `AS` (the stored physical address may be a freed frame: the reason L23 did not do it).
  Rejected: a retry loop on the clear (adds a fourth unbounded loop for a bit that is only an optimisation).

**T216 (2): not planned.** Both fixes named change the ABI of the word for a case that needs 2^30 thread creations in one boot. Leave the text,
keep NOT_SUPPORTED (Q2).

**T217 and T77 (budget): bill and demote by effective band, to the job the priority came from.** Needs Q1 first. The proposal:
1. The graph tracks where each effective priority comes from: `Node.src: Tid` (the thread whose base is the maximum; itself when its own base
   wins or ties), computed in `recompute`, carried in `Change { tid, eff, src }`. `propagate` must push on a change of `src` alone. `audit` checks
   that `base(src) == eff` and that `src` reaches the thread along edges.
2. `pi_apply` hands the scheduler `src`'s job tag with the priority (`set_effective_on` grows an argument); `ThreadSched` gains `bill: u32`, equal to
   `job` when nothing is lent.
3. `charge_job` adds RT time when `band(eff) == Rt`, to `bill`; `cpu` still goes to `job` (AC1 untouched). `demote_if_exhausted` and
   `is_exhausted_rt` drop the RT-base test and ask `exhausted(bill)`. A demoted donor's job is an exhausted job, so its borrower is demoted at
   its next accounting point: T217 (b) falls out with no call from `RQ` into `PI` (which the order forbids).
4. `jobsched::charge`'s parameter is renamed (`rt_base` -> `rt_band`).
- Rejected: *bill the borrower's own job* (T217's wording). Inside one job it is the same thing. Across jobs it breaks the point of donation: by
  4.9's policy a launched program's job has no RT budget (`a_job_with_no_budget_gets_no_real_time_at_all`), so a server lent priority 50 by a
  driver would be demoted at its first accounting point and the inversion is back.
- Rejected: teaching the graph about demotion (`set_base` at the demotion point): demotion happens under `RQ` (9), the graph is under `PI` (7).
- Not planned: donating CPU time. Nothing consumes it until the fair class exists (T72); it stays the residue of this item or moves to T72 (Q4).

**T221: the provisional edge.** Needs Q3. The proposal:
1. `WaitTable::commit` reports, for each released thread, the touched object that released it (for a port waiter, the bound object whose touch
   evaluated the port). Same prepaid vector, a wider element; nothing new allocated (T248).
2. In the `sync` commit of `channel_call` (`notify_sync`), if **exactly one** released registration is on the call's peer end, `pi_donate(caller,
   it)`, in the same object-lock section as the wake. Several (plain `object_wait` waiters are all released): no provisional edge.
3. `lend_to_reader` retargets (`thread::pi_retarget`, new) when the caller already lends to another thread; `AlreadyDonating` goes away as a
   silent path, and a refusal is counted as today.
4. Drop rule: the thread record keeps `provisional: Option<(Tid, call number)>`; when that thread next registers a wait or exits without having read
   the call, the caller's edge is revoked if it still points at it. The caller's own exit from the call revokes as today (DC1's end).
- Rejected: an edge to every released waiter (a donor has one out-edge, by OD88). Rejected: a timer to drop an unconfirmed edge (the call's
  deadline already bounds it, and a server that reads and never answers holds the same boost today).
