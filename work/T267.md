### T167: A freshly started user thread was seen taking 0.7 to 2.4 s to start running on an idle two-hart machine

*(area sched, horizon near, risk M)*


#### Shortcut

While writing the L12c test, at `-smp 2` on a loaded development machine, a user thread started with `user::start` was not observed running on any hart for 673, 1474 and 2375 timer ticks (several runs; it passed at once on a quiet host and at four harts), with and without the L12c fast path. Possibly host load stretching a TCG vCPU, possibly a real delay (a runnable thread behind equal-priority work on hart 0 with hart 1 slow to pull). The watchdog (500 ms, two samples) did not fire. Not diagnosed; the test now waits 5000 ticks.

#### Why acceptable

Seen only under heavy host load, never on CI; no wrong behaviour, only latency.

#### Proper fix, and when

Reproduce with `os-repeat` of a boot that starts a user thread at `-smp 2` under CPU load (the T157 burner method), record the thread's queue, hart state and pending marks at 300 ticks, and find where it waits. Before L13 (no tick), where an unmarked idle hart would make it permanent.

### T219: a_real_time_thread_stays_responsive_while_hogs_run_and_a_normal_one_does_not woke 4299 us late once (bound 4 ms) in smoke a of the phase 9b epic gate

*(area sched, horizon near, refs [L8, OD140, T178])*


**What.** In the epic gate of PR 410 (run 45034672496, head after the L23 test fix) `kernel (smoke a)` failed this test: "a real-time thread woke 4299 us late with a hog on every hart (bound 4 ms)". The same suite on the previous head of the same epic (run 45033938295, smoke a) measured **515 us**, the phase 6c epic's smoke passed it, and the kernel's own probe in the failing run reported `rt_latency_p99` 205 us. The failing head differs from the passing one only in the PI futex tests' change.

**Why it is not just re-run.** TESTING.md rule 11: an intermittent kernel-test failure is a defect until its cause is known. The candidates, none shown: a pause of the shared CI runner (steal time: a vCPU thread not run for 4 ms delays the timer interrupt it should have taken; the bound's own comment says a loaded host delivers one "up to a few ms late"); a real scheduler delay (the wake of a prepared RT thread behind the throttle's `rt_blocked`/`normal_has_work` logic of L25, or the new `PI` lock on the base-priority path (`thread_set_sched` of this test's probe and hogs now takes it)); a regression from the phase 6c locks (`AS`, futex buckets) on the timer path. The test takes the worst of 30 samples, which is the most exposed statistic to a single pause.

**Related.** T178 records the same bound failing on a loaded development machine (seen up to 9.2 ms), for the kernel-thread version of the probe; this is the first time on CI.

**Proper fix.** Reproduce at four harts in a loop (`make os-repeat` over the one test, a soak-sized run: only if the owner asks, or on a repeat in the gate); until then watch `rt_user_latency_max_us` in every smoke a log (515 us, 4299 us so far). If it repeats, print the per-sample lateness and what each hart ran, find the delayed wake, and fix that; if the cause is runner jitter, make the bound a percentile of the samples (the 95th of 30) with the worst case reported, so that a pause cannot fail it while a scheduler that delays every wake still does.

Progress (2026-11-24): the user-mode test now bounds the second-worst of its 30 samples at 4 ms and the worst at 30 ms (a pause of the host delays one wake); the negative control still uses the worst. Kept open until it has passed several gate runs.

Observation (2026-11-26, IOMMU7, development machine): a kernel-only boot (`OS_SHARD=k`, two harts, debug kernel) failed it with the
worst sample 21269 us and the second worst 16129 us (`rt_user_latency_max_us` 21269). The host was heavily loaded: a four-hart boot
and a cargo build of a second kernel ran at the same time. The same kernel passed at one, two and four harts when the boots ran one
after another on an otherwise idle host. This fits the host-pause candidate (two samples above 16 ms, both above the second-worst
bound). No kernel cause was shown.

### T178: realtime_thread_stays_responsive_under_load fails on a loaded development machine (bound 4 ms, seen up to 9.2 ms)

*(area testing, horizon near, refs [OD140, T174, L13])*


The kernel test `realtime_thread_stays_responsive_under_load` (`kernel/src/sched_tests.rs`) asserts a wall-clock bound: a real-time thread woken by a timer while three hogs run must be at most 4 ms late. On the development machine, whenever it is busy with other builds or QEMU runs, the emulator delivers the timer interrupt late: 12 of the 180 failing-boot logs kept under `target/fail-logs/` hold this failure, with lateness from 1.7 ms to 9.2 ms (today's, 6.4 ms, was one failure in a `make kquick` run that was never reproduced in eleven reruns). The bound's own comment records that 2.2 ms was seen. It is not a defect of the kernel's wake path (the idle and tickless work of L13 measure it in instructions elsewhere) but of measuring a latency in host time on a shared host; it is the same class as T174 and is closed the same way. Why acceptable for now: a rerun passes and CI runners have not shown it. Risk: a flaky gate (OD140). Proper fix: measure the same wake with no hogs in the same boot and bound the loaded lateness by a multiple of it plus a floor, or run the test under `-icount` where the guest clock is the instruction count, then tighten.

Seen again 2026-11-21 (the overnight soak, three boots at a time, and later two chaos jobs beside other builds and boots): `realtime_thread_stays_responsive_under_load` failed on every loaded boot (woke 5 to 31 ms late against the 4 ms bound), and once `wait_is_woken_by_the_peer_closing` ("the close came after about 3 ticks (waited 0)") failed in a one-hart boot beside two chaos jobs and passed in the next two runs: the same cause (host load), a second timing test with a tight bound to review in the same pass.

Progress (2026-11-24): the bound is now on the 99th sample (the next to worst of 50) with the worst held to 30 ms, so one pause of the host cannot fail it; the negative control still uses the worst. Kept open until it has passed several gate runs; the second timing test named above (`wait_is_woken_by_the_peer_closing`) is still to be reviewed.

Progress (2026-11-26, IOMMU5): `wait_is_woken_by_the_peer_closing` reviewed and fixed. On the IOMMU machine (`iommu-sys=on`) at two harts it failed with "waited 0" in most kernel-only boots: 5 of 7 with the IOMMU5 kernel, and 1 of 3 with the unchanged epic kernel on the same machine, against 0 of 4 on the old machine. The test's `tt:` time was 83 to 123 ms although its wait returned at once, so the suite thread was held off about 100 ms around its `channel_write`, after the send. The helper's three ticks ran out meanwhile. The test now reads its clock before the send, so the close can never look early (lower bound 2 ticks). The stall itself, a user thread on a two-hart machine not running for about 100 ms right after a send that wakes a kernel thread, is the latency of T167 above: not diagnosed, and still open.

### T49: Timing-sensitive tests that flake under host load

*(area testing, horizon long, risk L)*


#### Shortcut

**Timing-sensitive tests that flake under host load.** (Seen once in CI at four harts: `a_thread_killed_before_it_ran_runs_no_user_code` got BAD_STATE on its kill because the thread had already run and ended the child; it passed on rerun. The test assumes a freshly created thread has not run yet, which SMP does not promise.) (Also fixed: `threads_created_but_not_run_when_the_process_ends` raced on SMP, its second thread could end before the first thread left, making the first the last; the second now waits 20 ticks.) `bkl_is_released_on_user_entry_and_idle` (its threshold "lock found held < 1/4 of takes" failed twice at `-smp 4`, with 22% and 47% held, while the host was busy; relaxed to "free at least as often as held", which still fails for a lock held across user mode) and the sleeper-arrival naps in the S7b futex tests (`nap_ticks(15)` to let a thread reach the kernel's table) assume the host keeps up. (`futex_wake` used to wake every blocked thread in the system when it woke a sleeper; since slice W step 2 it wakes exactly the sleepers it removed, by id.)

#### Why it was acceptable

The gate passes on an unloaded machine; a rerun settles a flake.

#### Proper fix, and when

Observe instead of waiting (a readiness signal or a kernel-side sleeper count a test can read); a per-futex wake instead of the global queue wake (T12).

**Seen 2026-11-26: `harts_go_offline_and_come_back` (`kernel/src/smp_tests.rs`), smoke b, four harts** (the epic smoke of `epic/iommu-kernel`, run 45906519497, head 84421c9): "round 6: the sleepers made 11 wakes in 10 ms with hart 2 offline (baseline 78)"; the bound is a quarter of the baseline. Not reproduced under rule 11: five `make os-boot-test-smoke-b` runs of that head (four harts) and 35 kernel-only boots at four harts all passed on a quiet host. Under heavy host overload (other QEMU boots in parallel) the same head failed 5 of 203 and the fork point (58894ca, before the IOMMU changes to `hart_set_online`) 1 of 203, so it is load-sensitive on both. A diagnostic build (per-hart tick, IPI, idle-entry, idle-time and big-lock deltas over the window, printed on failure) caught one: elapsed 10.1 ms of guest time, harts 0 to 2 idle 7 to 9 ms of it with 4 to 6 ticks and about 10 lock takes each, 20 wakes against a baseline of 88. The sleepers (0.3 ms sleeps) were not woken on time by idle harts, which is what a stalled vCPU thread looks like (guest time runs on while the host does not schedule the hart) and also what a timer left on the wrong hart by the evacuation would look like for one window. The failure message now carries those per-hart deltas (the iommu-kernel smoke-fix PR). Next occurrence: look at whether the sleepers' deadlines sit on an online hart's timer; a stalled vCPU shows every hart idle with few ticks, a misplaced timer shows the deadlines on the offline hart.

### T223: The instruction counts vary from run to run by more than the 5% that the counts job checks

*(area testing, horizon long, risk L, refs [KT5, T178])*


#### Shortcut

The counts job (a `kfast` k-shard boot at one hart under `OS_ICOUNT=shift=0,sleep=off`, `OS_BENCH_FULL=1`) compares seven instruction counts with `bench/counts.tsv` at 5%. **It is deterministic for a commit** (the phase 11 epic PR's counts job, re-run, gave the same numbers to the instruction: `channel_write_read_64` 31701, `handle_dup_close` 19265, `futex_wake_no_waiter` 907), so a failure is a change between commits, not noise (an earlier version of this item said noise: wrong). But the numbers moved more than the commits explain: CI gave `channel_write_read_64` 26302 (the old baseline), 30648 (before the thread binding was written once, PR 428), 27142 (after it, the phase 6e gate) and 31701 (the phase 11 gate); and two **local** boots with the job's own command, at the phase 6e merge commit `a3f4e1a` and at the head of `epic/phase-11`, gave identical counts (`channel_write_read_64` 30236, `futex_wake_no_waiter` 942) which are not CI's. So phases 5 to 11's kernel code did not move the counts on a developer machine, and CI's counts rose 6 to 21% between the two gates: what differs is what CI builds and runs (the C programs, the boot image, a clean cache, the QEMU build), or the code of the intervening PRs acts differently there.

#### Why it is open

The counts job is the only check on the cost of the hot syscalls (KT5), and its baseline was re-recorded from CI at the phase 6d, 6e and 11 gates without the cause of each rise being known.

#### Proper fix, and when

Bisect on CI, not on a laptop: dispatch the job's workflow on the four merge commits of PRs 433 to 436 (`epic/phase-11`'s history) and on `a3f4e1a`, and read the counts; then find the instructions (a `rdinstret` split of the loop into kernel and user, or the suite's `perf`-style trace) that the rise adds. Also find why the developer machine's numbers differ from CI's by 15% at the same commit (the build profile of the counts job, features, the number of programs in the image). Do it with the next change to the syscall dispatch path (phase 6f).

#### 2026-11-23 (phase 6f gate)

The counts rose 15-23% on the call paths (channel round trip, handle dup/close, thread create/join) once the syscall path took the object lock per section instead of one big lock (L20: each section enters and leaves `irq::without`, commits wake state, and the trap tail is skipped). This is the expected price of the sectioned entry, not noise; re-baselined from CI at the 6f gate.

Second re-baseline the same day: the next gate run, after only a test-code change (#457), read four counts 7-9% higher again (channel write/read 41522, event signal/wait 42181, futex wake 887, handle dup/close 25794). The counts are deterministic per commit but move with changes that do not touch the measured paths, which is what this item is about.

Third re-baseline, at the phase 10 gate (PM1, PM3, PM4, SC2 first step, T215 before it): channel call round trip 191512 to 203358 (x1.06) and thread create/join 235369 to 248774 (x1.06), read from the CI log; nothing in the phase touched those paths directly (the call path now copies big messages outside the object section, T215; thread creation takes the placement masks), and the counts move 6% with them. Recorded, not isolated.

**2026-11-23 (the 6g gate):** a fourth re-baseline. The counts job was also cancelled at its 7 minute limit twice (once for a cold cache, once for real: the boot of the k shard under icount has grown with the suite), so `benchmarks_run_and_report` (14.7 s of guest time under `OS_BENCH_FULL`) and `jobs_do_not_leak` are marked `slow` in `init/ktests.txt` (the counts boot skips them; the other boots run them), which takes the guest time from 31 s to 13 s and moves counts again (channel_write_read_64 40014 to 37114): the counts depend on what ran before them, which is T223's point.

**2026-11-23:** the limit is 25 % now, not 5 %: a hosted runner and a laptop differ by up to 10 %, and unrelated changes move the counts by a few percent, which cost four re-baselines in a week for no regression found. A real regression of a syscall path is far above 25 %. The baseline still needs recording from the runner when a count falls (printed, not failed).
**2026-11-23 (the 6g gate, again):** the counts recorded on the development machine (macOS) differ from the hosted runner's by up to 10 % (the same tree gave 37114 and 39367 for `count_channel_write_read_64`), so a baseline recorded locally fails the job. The baseline is recorded from the CI log of the job (`make os-count-record` on the runner, or the values its output prints), never from a laptop.

### T252: Investigate why pair scaling at four harts is 1.4 (futex) and 0.9 (channel_call), not 3.0 and 2.5

*(area sched, horizon long, refs [T213, L20, L14, T70, SCHED-SMP-SPEC])*


**What.** `pair_scaling` at four harts was measured on 2026-11-24 (release build, QEMU TCG, `-smp 4`, one run): futex 1.38, `channel_call` 0.93. The owner accepted these figures as they are (2026-11-24; SCHED-SMP-SPEC amendment of that date), so they no longer gate T213, L14 or L20. This item is the later investigation.

**Why acceptable.** Nothing is wrong or unsafe; the calls are correct and merely not as scalable as the plan hoped. The measurement instrument (TCG, harts as host threads on a loaded laptop) may itself bound the figure.

**Risk.** A real kernel serialisation point (a lock's hold time, the idle and placement path) stays unfound; throughput on real hardware might be better or the same.

**Proper fix.** Do the measurements Fable's plan in `docs/records` (written into `work/T213.md` before it closed; see git history) listed and not yet built: M1 `lock-stat` (contended takes and waited time per lock class per round trip), M3 instructions retired over all harts per round trip, M4 pinned pairs (one pair per hart: the kernel's lock scaling alone), `-accel tcg,thread=single`, and `channel_call` with the same counters. Already known: with the firmware suspend refused (`idle=nosuspend`) one futex pair takes 4.3 us per round trip with no IPIs, four pairs 57 us, so the one-pair cost is the suspend and its placement and the four-pair cost is something serial. If pinned pairs scale near 4.0 and unpinned stays near 1.4, the limit is the emulator's IPI and halt cost, and the question becomes a pinned acceptance figure or KVM or hardware. If a lock is convicted, the plan's PRs 2 to 5 follow (idle spin before suspend, the resched arms without `OBJ`, per-switch `TT` takes, `futex_wait_enter` without the memory locks); T70's trigger (3.13: below 2.5 **and** more than 30% of syscall time in `OBJ`) is evaluated from M1.

**When.** After the freeze decision (FZ1), or when scaling matters to a use.

**Tripwire built (2026-11-24).** `bench/scaling.tsv` holds floors for the scaling ratios, checked by `bench_compare.py --scaling-floor` in `make os-bench` and `make os-latency` (soak tier; self-tested). Three full four-hart runs: futex n4 0.97, 1.27, 0.51; `channel_call` n2 1.07, 1.03, 0.99 and n4 0.85, 0.82, 0.82. The investigation proper (M1, M3, pinned pairs) is still to do.

**Taken over from SC2 (2026-11-24).** (1) The scaling at more harts: the pair counts 8, 16 and 32 are in the full run where the machine has the harts. A ten-core laptop boots and passes at 8 harts (one run, kernel-only boot, debug kernel): futex 0.53 and `channel_call` 0.51 at eight pairs (0.77 and 0.74 at four in the same run), so scaling falls further as pairs are added. At 16 and 32 harts the boot does not finish cleanly on this host (`sleep_wakes_on_time` sleeps seconds, the heap-leak checks trip on the noise, the required SMP tests are not reached): those runs, and with them the page-fault pairs the spec lists, need a host with that many cores (the owner's soak). (2) SCHED-SMP-SPEC 3.13's trigger (below 2.5 at four harts **and** more than 30% of syscall time in `OBJ`): the first half holds (0.74 and 1.4 against 2.5); the second needs `make os-latency` (soak tier, the owner's) and the lock statistics of M1. The decision to split `OBJ` or leave T70 as someday is made here, on those two numbers.

Observation (2026-11-27, `epic/no-testdev` smoke, run 46025538457, `kernel (smoke a)`, four harts, CI): failed with the second-worst
sample 5624 us and the worst 6475 us (`rt_user_latency_max_us` 6475), above the 4 ms second-worst bound. The epic's changes
(T282, #610; the close-chain test fix, #611) touch no scheduler or timer path. The previous smoke of the same epic (run
46018655715) and the next one (run 46026639448, the same code) passed it. Two samples above 5 ms fits a host pause longer than one
wake. No kernel cause was shown.
