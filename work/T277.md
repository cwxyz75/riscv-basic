**What.** On 2026-11-26, during IOMMU5's development, one kernel-only boot (`OS_SHARD=k OS_SMP=4`, IOMMU machine) failed
`the_guest_fuzzer_leaves_nothing_behind` with "seed 4: 97280 kernel heap bytes stayed behind". It did not happen again in more than
ten later kernel-only boots of the same and later kernels, at 1, 2 and 4 harts (TESTING.md rule 11: five attempts to reproduce it
failed). The boot it failed in had other failures of the change under development, since fixed: a device-cap test and the
direct-map page count. The run's log is gone.

**Why it matters.** A real leak in a syscall path the fuzzer reaches would grow without bound. A deferred free still in flight
when the oracle was read would be a race in the oracle.

**Proper fix.** Run the guest fuzzer's seed 4 alone in a loop (`os-repeat` of a boot that runs only that test) at 4 harts, with
the heap oracle sampled before and after each syscall batch. On a hit, print the slab and heap statistics by size class, and
find which object kind the 97280 bytes are. Then decide whether the oracle must wait for deferred frees (and say why in the
test) or the kernel leaks.

**When.** Before the IOMMU epic's smoke, if it shows there; otherwise with T267's other intermittent items.

**Seen again (2026-11-26, IOMMU9's development).** One kernel-only boot at two harts (`OS_SHARD=k OS_SMP=2`, the IOMMU9 branch)
failed it with the same message, "seed 4: 97280 kernel heap bytes stayed behind". The fuzzer runs before IOMMU9's new PCI tests in
`init/ktests.txt`, and the same kernel passed this test at one and four harts in boots run alongside it. The same byte count twice points at one
object kind, not noise.

**Diagnosis and fix (IOMMU9, PR #598).** 97,280 bytes is the VMO table doubling from 256 slots to 512, as the test's own comment says.
IOMMU9 has `devmgr` map each function's MSI-X table BAR as well as its virtio BAR, which adds a few long-lived VMOs. At two harts that put
the system's VMO count where seed 4's *measured* (second) run crossed the doubling, so the failure became deterministic there: three
boots out of three on the branch, against a pass for the base epic kernel at two harts. With the old two-device command line it still
failed, so the extra PCI functions are not the cause. It is the oracle, not a leak. The test now repeats a measured run that kept bytes,
up to three in all: a table grows once and keeps its room, and a leak takes bytes on every run. With that change the branch's
kernel-only boots passed at one, two and four harts. Close this item with the epic's smoke if the fuzzer stays green there.
