**What.** On 2026-11-26, during IOMMU5's development, one kernel-only boot (`OS_SHARD=k OS_SMP=4`, IOMMU machine) failed
`the_guest_fuzzer_leaves_nothing_behind` with "seed 4: 97280 kernel heap bytes stayed behind". It did not happen again in more than
ten later kernel-only boots of the same and later kernels, at 1, 2 and 4 harts (TESTING.md rule 11: five attempts to reproduce it
failed). The boot it failed in had other failures of the change under development, since fixed: a device-cap test and the
direct-map page count. The run's log is gone.

**Why it matters.** A real leak in a syscall path the fuzzer reaches would grow without bound. A deferred free still in flight
when the oracle was read would be a race in the oracle.

**Proper fix.** Run the guest fuzzer's seed 4 alone in a loop (`os-repeat` of a boot that runs only that test) at 4 harts, with
the heap oracle sampled before and after each syscall batch. On a hit, print the slab and heap statistics by size class, and
find which object kind the 97280 bytes are. Then decide whether the oracle must wait for deferred frees (and say why in the
test) or the kernel leaks.

**When.** Before the IOMMU epic's smoke, if it shows there; otherwise with T267's other intermittent items.
