### T228: A hart that goes offline parks in its idle loop; it does not call SBI HSM `hart_stop`, and does not come back through `hart_start`

*(area sched, horizon long, refs [PM1, KERNEL-V1-SPEC])*


**What.** PM1 (`hart_set_online`) takes a hart out of the scheduler, the shootdown and poke sets and the interrupt routing, and returns its caches, but the hart stays powered in its idle loop (an offline hart still takes the reschedule IPI, which is how it is told to come back). The item text also names the firmware's `hart_stop` and `hart_start` (a real power state, and a bring-up through the secondary entry on the way back).
**Why acceptable.** On QEMU the difference is only power, which nothing measures; the logical state is what every invariant (HT1, HT2) is about, and the test covers it. A stopped hart cannot be told anything but by `hart_start`, so the real thing needs the secondary entry to re-run the per-hart bring-up (stack, IMSIC file, trap vector, `percpu` state kept) without re-initialising shared state.
**Risk.** None for correctness; an offline hart is not idle in the power sense (it takes a wake-up per interrupt, which it does not receive but the one-shot timer and the IMSIC are still live).
**Proper fix.** HSM stop at the end of the draining step and `hart_start` at the secondary entry, with the bring-up made re-entrant; do it with the first user of a measured power difference (a platform with real cores), or with PM3 if `system_suspend` needs the same re-entry.

### T229: `system_suspend` has no firmware path: the harts are not stopped through HSM and the resume entry is not written

*(area sched, horizon long, refs [PM3, T228])*


**What.** PM3 built the save and restore sequence (`kcore::powerseq`, host-tested) and the call, which answers NOT_SUPPORTED. The SBI system-suspend extension requires every hart but the caller to be in the HSM `STOPPED` state, and resumes the caller at a physical entry with the MMU off; the kernel's offline harts are parked, not stopped (T228), and there is no resume entry.
**Why acceptable.** The reference machine's firmware (OpenSBI on QEMU `virt`) has no SUSP extension, so the path cannot run anywhere the project runs; code written blind for it would be dead and unverified. The item's own acceptance allows closing on the host model plus the NOT_SUPPORTED check.
**Risk.** None today. On a platform with SUSP the call is refused rather than attempted.
**Proper fix.** After T228 (stop and start through HSM, the bring-up re-entrant): the resume entry (the early-table dance of `secondary_entry`, then `Saved::apply` over the real CSRs and the IMSIC and APLIC state), the sequence in the call (every other hart offline then stopped, device sources masked and re-enabled from a saved set, the timer re-armed on every hart), and a QEMU test on firmware that offers SUSP.

### T230: PM1 acceptance gaps: no shuttle test of a hart going offline, no test of an interrupt aimed at an offline hart, no k-shard run under an offline loop

*(area sched, horizon long, refs [PM1])*


**What.** PM1 was closed with three parts of its acceptance not built: a device interrupt aimed at an offline hart is delivered (the QEMU test has no device source in use), the `k` shard's tests run while harts go offline and online (the QEMU test runs sleepers only), and PM1's shuttle test. The shuttle test is asked for as:  (HT1, HT2 under random interleavings of offline, wakes, sleeps expiring and pulls). Built instead: single-threaded model walks and a two-thread test of the last-hart race.
**Why acceptable.** The races the review found (the last-hart check, publishing Draining early, placement onto a hart that just went offline) are each closed by a check under the run-queue lock and have a test; the QEMU test runs the call against live sleepers.
**Risk.** A further interleaving not yet seen (a wake attaching to a hart between `set_offline` and the drain).
**Proper fix.** A model in the style of `rq_concurrency.rs` with an offline/online loop as a fourth model hart; run under `make os-test`.

### T185: SC1 leftovers: per-hart records and boot and emergency stacks are static for 64 harts, not allocated at boot

*(area sched, horizon long, refs [SC1, KERNEL-V1-SPEC])*


KERNEL-V1-SPEC 2.3 says per-hart records, boot stacks and emergency stacks are allocated at boot for the harts found. SC1 made `MAX_HARTS` 64 and took the harts from `/cpus`, but `percpu::HARTS`, `percpu::EMERGENCY` and `smp::BOOT_STACKS` are still static arrays (about 2.6 MiB of `.bss` at 64: 64 x 32 KiB boot stacks, 64 x 8 KiB emergency stacks, the records), as are the arrays in `chaos`, `latency` and `fp` (`[T; MAX_HARTS]`). Why acceptable: the memory is cheap and zero-filled on the one target, the boot hart's record has to exist before the heap does, and nothing else depends on it. Risk: a machine with few harts wastes the memory; a machine with more than 64 harts is capped at 64 with a boot line. Proper fix: keep the boot hart's record static, allocate the others (and the stacks, from frames, through the direct map) once the harts are counted, and make the three debug arrays vectors; then the `.bss` falls back to the 8-hart size. The acceptance boots (`-smp 8`, 16 and 32 on the `k` shard) and the 16 and 32 hart scaling checks of SCHED-SMP-SPEC 6.1 are soak runs the owner asks for. From the SC1 review: the `-smp` boots are the only check of the 64-hart paths (watchdog arrays, the shared start-up deadlines now 2 s plus 0.1 s per hart), and `aia::send_ipi` assumes the linear IMSIC layout with no group bits (refused by `aiatree`).

### T179: AR1b review leftovers: SBI calls and hart-mask encoding still in smp.rs, the arch check's blind spots, register-number accessors, whole-module re-exports

*(area platform, horizon long, refs [AR1, KERNEL-V1-SPEC])*


The Fable review of AR1b (2026-11-20; no behaviour change found) left boundary gaps that the docs check does not catch. Why acceptable for now: none changes behaviour, the moved code is line-for-line the old code, and AR1c and AR1d (the generic page tables, `abi::arch`, the AArch64 stub) do not depend on them. Risk: the boundary is weaker than its check says, so a second architecture would find leaks at compile time (a loud failure, not a silent one). Proper fix, as one PR before the AArch64 stub is trusted:

* **SBI out of `smp.rs`.** `smp.rs` still calls `sbi(...)` and names `EID_*`/`FID_*` (IPI, HSM start, status and suspend, RFENCE) and encodes the hart mask. Move the bodies into `arch/riscv64` as `ipi_send(hart)`, `tlb_shootdown(hart)`, `cpu_start(hart, index)`, `cpu_status(hart)`, `cpu_suspend()` (the spec's names), make `sbi` private to `arch/riscv64`, and add the SBI names to the check.
* **The check's blind spots** (`scripts/check_docs.py check_arch`): `naked_asm!`, `core::arch::` paths, more CSR names and numeric CSRs (`0x14d`, `0x180`), `mret`, `ebreak`, `fence.i`, `cbo.*`, `rdtime`, register names, the Sv39 constants (`8 << 60`, `>> 38`, `1 << 63`, `0xffffffff00000000`); a missing walked directory passes silently; `kernel/build.rs`, `abi`, `rt` and `libc` are not walked; and a self-test with planted lines (the "planted `csrr` in `ksys`" control is manual today).
* **Remaining leaks.** `selftest.rs` decodes the address-space token (`>> 60 == 8`) and the Sv39 canonical rule (`>> 38`): give `arch` `paging_enabled()` and `is_kernel_address()`. `user/trap.rs` uses `frame.arg(17)` and `arg(10..15)` (RISC-V register numbers): give `TrapFrame` `syscall_number()` and `syscall_args()`. `main.rs` re-exports whole RISC-V modules at the crate root (`use arch::{aia, finisher, fp, irq, timer, trap}`), so the interface is everything `pub` in them, and `TrapFrame`'s `sepc`/`scause`/`stval`/`sstatus` fields are `pub`.
* **Smaller.** `FaultKind` has no PAGER kind and no discriminants (AR1d numbers them; EX2 needs PAGER); the page-fault access belongs inside `FaultKind::PageFault(Access)` (the `unwrap_or(Read)` goes away); `arch/riscv64/trap.rs` still holds generic policy (big lock, scheduler tick, `lock_free_syscall`); `flush_tlb` there duplicates `cpu::tlb_flush_all`; the new `arch` files lack the per-file KT3 `deny` header; an interrupt cause (bit 63 set) reaching `user_trap` truncates in `cause as i32` and exits as `-1013` (pre-existing; make `decode_user` return a distinct value and treat it as a kernel bug); the instruction-count criterion of AR1 (1%) is checked against a 5% bar (`make os-count` `--max-ratio 1.05`): record the deltas in the PR that moves code.
