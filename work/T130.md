## Shortcut

**`authd` and the login (UV5a) shortcuts** (2026-11-17):

- (1) salts are unique (clock, counter, name) but not random: the session stack has no random service yet (scrypt needs uniqueness, not secrecy, from a salt, but a random one is the design)
- (2) the profile and credential the setup session makes live in memory only, so a reboot of an empty image starts setup again: the boot image is read-only and there are no home volumes yet (S10)
- (3) the right to a session that `authd` grants is a text reply on a channel only `init` holds, not an attenuated handle; `sessiond` (OD116) holds the channel, so `authd` and the manager are separate processes
- (4) the password crosses the serial line in clear, is read by `init` (the manager sees the password, never a verifier), and travels to `authd` as text: a login service that holds the console and hands `authd` a secret handle is the proper shape
- (5) no lockout or rate limit on failed logins
- (6) recovery is typed at the login prompt as `!reset` and honoured only when the kernel command line had `recovery` (a real console flag would be a key held at boot)
- (7) the images the tests build use the test scrypt cost (log2 N 4); the strong cost (16 MiB of working memory per check) is checked only on the host
- (8) the test overlays (`OS_BOOTFS_OVERLAY`, `tests/uv5a/`) and the seed credential file are for tests; a real image has `etc/boot` without `autologin=on` and no `etc/credentials`
- (9) `os-auth-test` runs in the soak tier (`os-serial-test`), not the smoke gate.

## Why it was acceptable

Meets the UV5a acceptance on QEMU with a console user; each item is behaviour the QEMU test pins as it stands.
