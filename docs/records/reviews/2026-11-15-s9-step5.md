# Review: S9 step 5, the system random service (branch `rng-crate`)

Date: 2026-11-15. Reviewer: Fable (fresh context, independent of the author). Scope: `git diff origin/main...rng-crate`:
`rngcore/`, `proto/src/random.rs`, `proto/src/devmgr.rs`, `rt/src/random.rs`, `init/src/bin/rngd.rs`,
`init/src/bin/devmgr.rs` (`claim_rng`), `init/src/bin/netsup.rs` (`secret_env`), `init/src/bin/netd.rs` (SECRET), the test
and script changes. Read against `INVARIANTS.md` (D1 to D5, T42), `SYSCALLS.md` and `S9-SPEC.md` 5.10.

Method: reading, plus one independent oracle. A scratch program (outside the repo) printed `rngcore` outputs for 708 cases
and a Python reference (hashlib/hmac, a separately written ChaCha20 block, a model of `Drbg`) reproduced every one:
SHA-256 for every length 0 to 299 and six larger (one-shot and split updates), HMAC for 9 key lengths by 8 message lengths
(keys of 0, 64, 65, 200 bytes included), HKDF for 8 shapes (empty salt, 8160 bytes, 33 bytes), ChaCha20 blocks at counters
0, 1, 2, 0x12345678 and 0xffffffff, and the generator's stream through reseeds and requests of 0 to 65536 bytes.
`cargo test -p rngcore` passes (12 tests). Nothing was booted in QEMU for this review; the driver and service findings
are from the code.

Summary: the primitives and the generator construction are correct. No path was found that returns bytes from an unseeded
generator, and no memory-safety problem in the driver for an honest device. The findings are about what happens off the
happy path: the stack's secret can be downgraded to a guessable one, the service can be denied to everyone by one client,
`rngd` never recovers from a failed claim, and the driver's queue handling is wrong after a timeout.

No High. Medium: 1, 2, 3, 4. Low: 5 to 13. Notes: 14.

---

## Medium

### 1. The TCP secret silently falls back to a 12-bit stand-in, and an unprivileged client can force that (M)

`init/src/bin/netsup.rs:671-689`. `secret_env` gives the random service 4 s to appear and 4 s to answer; on any failure
(`Sys`, `Closed`, `TimedOut`, `NotSeeded`, `Garbled`) the seed becomes `sha256("netsup stand-in" || clock_get())`.
`clock_get` is 1 ms ticks since boot (`SYSCALLS.md:143`), so the seed has about as many values as there are milliseconds
in the plausible boot window: a few thousand. An off-path attacker who sees one SYN or SYN-ACK from the guest can try
every candidate, recompute `F(four-tuple, key)` and recover the key; ISNs and ephemeral ports (TCP and the resolver's UDP
port, 5.10) are then predictable for the whole boot. Three things make this worse than T99 (2) says:

* It is reachable on a machine that **has** an entropy device. Anything that makes `rngd` unavailable for 8 s at the moment
  `netsup` starts downgrades the secret: finding 2 (one client holding the connection pool), finding 3 (`rngd` lost the
  claim race and is unseeded for good), a slow start, or `rngd` simply not being started (T99 (3): `init` does not start
  it, so every boot outside `start_full` takes this path, after a 4 s delay).
* The choice is made once and kept for the boot (`Held.secret_env`), correctly for the restart contract, so a transient
  failure at boot is permanent.
* It is weaker than the stand-in the spec itself described (5.10 (b): SipHash over the MAC, the clock at several points
  and the DHCP exchange), and under `-icount` the clock value is the same every boot, so the key is a constant.

The message is loud (`##NETSUP tcp secret from stand-in`), but nothing fails: the boot script only complains when
`OS_NET != 0` and `udpecho ready` appeared (`scripts/os_boot_test.py`).

Suggested fix: decide "is an entropy device expected" from fact, not from a timeout: if `devmgr` reports an rng device (or
`rngd` is part of the boot plan), `netsup` waits for the service without the short deadline, or does not start `netd` and
reports a failed start; the stand-in is taken only when the machine has no device. Make the stand-in at least what 5.10 (b)
said (MAC, several clock samples, the DHCP transaction), and add a negative control (`FAULT=no-rng`) so the harness sees
the stand-in line when and only when it should.

### 2. One client can deny the random service to everyone (M)

`init/src/bin/rngd.rs:237-250, 348-353`. Every forwarded open becomes a new account under the root with `conns: 4`; the
pool is `conns: 64` and the listener takes one. There is no idle timeout (the `30_000` passed to `Core::new` is the
held-reply timeout, `rt/src/service.rs:96`), no limit on opens per caller, and a connection lives until its peer closes
it. A program that opens `/svc/random` 63 times and keeps the handles makes every later open fail: `accounts().open` or
`add_conn` refuses, `rngd` closes the newcomer's end, and the client sees `Closed` on its first `fill`. That is a denial
of `getrandom` for the whole system, and through finding 1 it is how an unprivileged program turns the stack's secret into
the stand-in if it runs before `netsup` asks. T99 (5) records "no per-client rate limit"; this is a different and larger
hole (T98 (6) is the same shape in `netd`).

Suggested fix: the connections carry no state (the `Conn::Client` variant is empty and every request is independent), so
when the pool is full close the least recently used client connection and admit the new one; a well-behaved client
reconnects on `Closed`. Alternatively serve a bounded number of requests per connection and close it. Either way add a
suite test that opens connections until refused and then checks a fresh client is still served.

### 3. `rngd` asks for the device once; any failure leaves it answering NOT_SEEDED for ever (M)

`init/src/bin/rngd.rs:299-343`. The claim is one request with a 3 s wait. `Busy`, a late reply, a failed map, or any
`Device::init` error (20 to 24) all end in `dev = None`, after which `pull` returns `false` at once and the service
publishes itself and refuses every request for the rest of its life. Nothing retries and the process does not exit, so a
supervisor would see a healthy service. Ways to get there:

* **Restart race.** The claim is released when `devmgr` notices the old connection closed
  (`devmgr.rs:339, 447-452`). A new `rngd` that is started as soon as the old one dies sends its claim on a different
  connection; if `devmgr` handles that message before the old connection's PEER_CLOSED it answers `Busy`. So the first
  restart of `rngd` can leave the system without randomness permanently.
* **Any other holder of a device-manager connection** can claim the device first (finding 10).
* `Device::init`'s reset wait is a bounded spin of register reads (`rngd.rs:100-106`) with no time base.

Suggested fix: on `Busy` or a timeout retry with backoff for a bounded time, then exit with a distinct code so the starter
can see it and restart; do the same when `init` fails. Keep "no device on this machine" (`NoDevice`) as the one case where
the service runs unseeded. Add a QEMU test that kills `rngd`, starts another at once and requires seeded output.

### 4. The virtqueue handling is wrong after a timeout: in-flight descriptor reuse, ring overrun, stale completions credited as entropy (M)

`init/src/bin/rngd.rs:142-179`. `read` returns `None` after 2000 ticks but the request stays with the device. Nothing
records that, so:

* The next `read` rewrites descriptor 0 and publishes it again while the device still owns it (a violation of virtio 1.x
  2.7.13: a descriptor must not be reused until it is returned). With a device that stays silent, the fifth request puts
  more entries in the available ring than `QUEUE_SIZE` (4): the driver overwrites ring slots the device has not consumed.
* Completions and requests go out of step. Concretely, with a slow but honest device: read A times out; read B is
  published; the device completes A and B (both write the same 64 bytes at `DATA`) before the driver looks. The driver
  consumes used entry 1, takes the bytes and zeroes `DATA`. The next `read` publishes C, sees `used.idx (2) != last_used
  (1)` immediately, and reads `DATA`, which is the zeroes it wrote itself, with the length from B's used element. `pull`
  then calls `reseed` with 64 zero bytes and adds 64 to `mixed`. If the earlier real completion was short (a device may
  return fewer bytes than asked), `is_seeded()` becomes true with less than 32 bytes of entropy in the key. From then on
  every pull is one completion behind.
* A late completion leaves device bytes in the DMA page until the next read (the comment at line 176 says they are not
  kept). Those bytes will later be mixed into the key, so they are secret material sitting in a page that a second mapping
  holder could read.
* `used.id` is never checked and `used.idx` may jump by any amount; each read consumes one entry whatever it was.

The `min(CHUNK)` on `used.len` is right and prevents an out-of-bounds read of `out`; the device cannot make the driver
read or write outside its two pages. With QEMU's device answering promptly none of this happens, which is why the test
passes; it is a correctness hole exactly where the driver is supposed to cope with a bad device.

Suggested fix: keep an `in_flight` flag. While a request is outstanding do not publish another: poll for its completion
instead. On a timeout either keep waiting on later calls (non-blocking check) or reset and reinitialise the device (which
is the only way to take a descriptor back) and zero both pages. Require `used.id == 0` and `used.idx == last_used + 1`;
anything else is a broken device: reset it. Zero `DATA` before publishing as well as after reading, and treat an all-zero
or repeated block as a failed read rather than as entropy (finding 6).

## Low

### 5. A silent device blocks the whole service for 2 s per request (L)

`rngd.rs:266-271` and `367`. `pull` is called inside `request`, and `Device::read` naps in a loop for up to `TIMEOUT`
(2000 ms) on the service's only thread. With a device that initialised but does not answer, every request from any client
costs 2 s during which no other client is served, and start-up publishes the name 2 s late. A client with `inflight: 4`
on several connections can keep the service asleep continuously. Nobody loses bytes they would otherwise get (the
generator is unseeded in that state), but after seeding the same stall happens once per `RESEED_AFTER` if the device dies
later, and `self.served = 0` is set whether or not the reseed worked (line 268), so a failed reseed is not retried for
another mebibyte and is not reported.

Suggested fix: make the device read a state machine driven by `Service::next_deadline` (publish, return, check on the next
wake) so the request path never sleeps; answer `NOT_SEEDED` at once while a read is pending. Reset `served` only when the
pull succeeded and log the first failure.

### 6. Entropy is credited by byte count with no check on what arrived (L)

`rngcore/src/drbg.rs:26-34`, `rngd.rs:174, 207-212`. `is_seeded` is `mixed >= 32`, and `mixed` grows by whatever length
the device's used element claims. A device that reports 64 and writes nothing (or the stale-completion case of finding 4)
seeds the generator with zeroes and the service then hands out a stream anyone can compute: `HMAC(0^32, "rngcore reseed" ||
0^64)` is a constant. The device is the root of trust and nothing can fix a hostile one, but a cheap health check turns a
silent failure into a refusal.

Suggested fix: in `pull`, refuse a block that is all zero or equal to the previous block (keep a hash of the last one),
and require the first seeding to be 32 bytes from one or more checked blocks. Consider a second source mixed at start
(the device tree's `rng-seed`, clock jitter across the device read); T99 (4) already notes there is none.

### 7. `netd` runs with an all-zero secret, silently, when SECRET is missing or malformed (L)

`init/src/bin/netd.rs:1879-1903`, `netcore/src/tcp.rs:155`. If the variable is absent, not 32 characters or not hex, the
block is skipped without a word and the stack keeps the default key of sixteen zero bytes, which is worse than the
stand-in: every ISN offset and port choice is public. `netsup` always passes one today, so this needs a bug or another
starter of `netd` (T99 (3) expects one) to bite, but it fails open and leaves no trace in the serial log. The boot script
only catches it on the network boot.

Suggested fix: `netd` exits with a distinct code (or at least prints `netd: NO tcp secret`) when it has no valid secret;
tests that want the fixed key pass it explicitly.

### 8. Secrets are not reliably wiped (L)

* `rngcore/src/drbg.rs:43-57`: `first` holds the **next key** in its first 32 bytes and is never cleared; `b` (the last
  keystream block) is not either. `old.fill(0)` is a dead store the optimiser may drop (the crate is built at
  `opt-level = 2` even in dev). The point of fast key erasure is that a later read of the process's memory does not give
  earlier output; stack residue of `old` gives exactly that for the latest request.
* `Drbg` has no `Drop`; `derive` leaves `base` (`drbg.rs:63-67`); `hmac_sha256` leaves `k`, `ipad`, `opad` and the inner
  state (`sha256.rs:136-157`), which during `reseed` are the generator's key; `hkdf` leaves `prk` and `t`.
* `rngd.rs:272-280`: `out` is zeroed (again a dead store before a drop) but `reply`, which holds the same bytes, goes to
  `Core::send` and is freed unwiped, or sits in the hold queue for up to 30 s.
* `netsup.rs:681-699`: `seed` is wiped; `key`, `hex` and the encoded startup message are not. `rt/src/random.rs:67`: the
  receive buffer with the random bytes is freed unwiped on every call.

None of this crosses a process boundary; it matters for a later memory-disclosure bug. Suggested fix: one helper in
`rngcore` (`wipe(&mut [u8])`: a fill followed by `core::hint::black_box` on the slice, which is the best a
`forbid(unsafe_code)` crate can do), used on `first`, `b`, `old`, `base`, the HMAC pads and `prk`; a `Drop` for `Drbg`;
wipe the reply after a successful send in `rngd`.

### 9. `hkdf` silently leaves the tail of a long output untouched (L)

`rngcore/src/sha256.rs:160-175`. For `out.len() > 8160` the loop stops after 255 blocks and returns; the rest of `out`
keeps whatever the caller put there (confirmed: a buffer of 0xAA bytes comes back with 0xAA from offset 8160). The doc
comment says "longer is cut", but the function returns nothing, so a caller cannot tell and would use a key whose tail is
its own initial bytes. No caller asks for more than 16 today.

Suggested fix: return `Result<(), TooLong>` (or `bool`, like `Drbg::fill`) and write nothing when refused; add the test.

### 10. A device-manager connection is all-or-nothing authority (L)

`init/src/bin/devmgr.rs:275-312`. Any connection may send `Connect` (minting further connections), `OpenBlock`,
`ClaimNet` and now `ClaimRng`. So `rngd`, given `Role::ServiceDevmgr` only to take the entropy device, can also claim the
network device or open block devices, and conversely every other holder of a connection can claim the entropy device and
starve `rngd` (finding 3). The claim itself is sound: one claimant, `Busy` for a second, released and the device reset
before the manager's DMA handle is closed when the connection ends (`Rng::release`, the T42 order), and the DMA VMO exists
only while claimed. Two small leaks and gaps in `claim_rng`:

* line 311-314: if duplicating the MMIO handle succeeds and duplicating the DMA handle fails, `m` is leaked;
* a claimant that closes its connection but keeps running still has the MMIO and DMA mappings, and the next claimant gets
  the same MMIO VMO: two live drivers on one device. The same is true of the net claim, and a DMA-capable driver is
  trusted in full without an IOMMU (OD14), so this is noted, not counted.

Suggested fix: scope connections at `Connect` (a mask of permitted ops/devices carried by the parent, narrowing only), so
the starter gives `rngd` an rng-only connection; close `m` on the failure path. Record the ambient authority in
`TIDY-UP.md` (it is a stand-in in the sense of the working agreement).

### 11. Spec and bookkeeping are out of step with what was built (L)

* `S9-SPEC.md` 5.10 still states, in the normative paragraph, a 16-byte secret in a one-page VMO with a read-only handle
  for `netd` "and nobody else gets any"; the "as built" note below contradicts it (environment variable). T99 (1) records
  the deviation, but the section should say one thing. The environment copy also lives in `netd`'s parsed startup `env`
  for the life of the process and in `netsup`'s heap twice (finding 8). I found no path that prints or exports the
  environment, so this is a hygiene and documentation point today.
* `netsup.rs:670` cites TIDY-UP T96 for the stand-in; the row is T99.
* `rngd.rs:1-3` says the service "never makes bytes up"; with findings 4 and 6 it can mix and credit zeroes.
* If `netsup` itself restarts it draws a new secret, so "ISNs only move forward within a boot" (5.10) holds across `netd`
  restarts only. That matches the text ("holds for the whole boot" assumes `netsup` lives) but is worth a sentence.

### 12. Restart behaviour of the service is unspecified and untested (L)

When `rngd` dies every `rt::random::Random` gets `Closed` and does not reconnect (`rt/src/random.rs:55, 77, 82`); callers
must build a new one. Nothing restarts `rngd` (T99 (3)), nothing republishes `random` if the registry restarts (`rngd`
keeps serving old connections and `service::run` returns 0 when the last one goes), and a restarted `rngd` hits finding 3.
A restarted generator starts from fresh device entropy with no saved state, so there is no output reuse across restarts:
that part is sound. `netsup` is unaffected after boot because it never asks again.

Suggested fix: decide who supervises `rngd` (with step 6, as T99 says), make `Random::fill` reconnect once on `Closed` when
it was built by `connect`, and add the kill-and-restart test of finding 3.

### 13. The acceptance check passes when the driver is broken (L)

`init/src/net_tests.rs` `random_service_gives_seeded_distinct_bytes` returns `Ok` on `NotSeeded`, so a driver that never
gets a byte passes the suite; only the boot script's `netd: tcp secret from rngd` line notices, and only on the network
boot. There is no negative control (CLAUDE.md asks for independent oracles and `TESTING.md` for controls on kernel and
security slices) and no test for: a second claimant getting `Busy`, release and re-claim, a silent device, the connection
pool limit, `BAD_REQUEST` and the violation path, or pipelined requests against `held_bytes` (four 4104-byte replies
exceed 16 KiB; the runtime holds one at a time so this is safe by construction, but it is not pinned). The statistical
bounds in the test are sound (about 7.8 and 8.5 standard deviations) and will not flake.

Suggested fix: have the boot script tell the suite whether an entropy device was given (an environment flag or a `debug`
query) and require seeded output when it was; add `FAULT=rng-silent` and `FAULT=rng-zero` controls for findings 4 and 6.

## Notes

14. Smaller points, no severity:
    * `rngcore::drbg::fingerprint` is public API in production builds; it only exposes `sha256(key)`, but it belongs
      behind `#[cfg(test)]` or a `test-util` feature.
    * `rngd` leaves `avail.flags` at 0, so the device raises an interrupt per completion that nobody acknowledges; set
      `VIRTQ_AVAIL_F_NO_INTERRUPT`. `rngd` does not check `dma_pages >= 2` before touching the second page, and does not
      close the claim handles on its failure paths.
    * `Device::init` zeroes only the first DMA page (`dma_write(0, &[0u8; DATA])`); the data page relies on the kernel's
      zeroed frames, which `SYSCALLS.md` guarantees for a fresh VMO.
    * `rt::random::Random::fill` leaves `out` partly filled on an error after the first chunk; say so in the doc comment
      or zero it.
    * `let _ = Sys::Ok;` at `rngd.rs:386` only silences an unused import.
    * The secret reaching `netd` as lower-case hex is parsed with `to_digit(16)`, which also accepts upper case; harmless.

## Checked and found sound

* SHA-256, HMAC-SHA256, HKDF-SHA256 and the ChaCha20 block: 708 comparisons against an independent reference, no
  difference; padding boundaries (55, 56, 63, 64, 119, 120), keys longer than a block, empty salt and info, the 255-block
  boundary. No secret-dependent branches or table lookups in any of them.
* `Drbg::fill`: the key is replaced by the first half of block 0 on every call, zero-length included; output never comes
  from the half that becomes the key; block counters start at 1 for the rest and cannot wrap (`MAX_REQUEST` is 1024
  blocks; `rngd` caps requests at 4096 bytes); the fixed zero nonce is safe because no key is used for two requests. An
  unseeded generator and an over-long request write nothing. `reseed` is `HMAC(key, label || input)`, so known or chosen
  input cannot reduce what the key already holds.
* The HKDF use in `netsup` (fixed salt as a domain label, 32 bytes in, a fixed info string, 16 bytes out) is fine; the
  weakness is the input on the stand-in path (finding 1), not the derivation.
* No path returns generator output while `is_seeded()` is false. The `while !seeded && pull()` loop terminates (each
  successful pull adds at least one byte; a failed one ends it).
* `used.len` is clamped to `CHUNK`; all DMA accesses are at constant offsets inside the two pages; `vmo_create_dma`
  guarantees the contiguity that `pa + DATA` assumes; the torn two-byte read of `used.idx` cannot produce a false
  "unchanged".
* Request decoding is total (every truncation refused, zero and over-limit lengths answered `BAD_REQUEST`, under four
  bytes is a violation); stray handles are closed; memory per client is bounded by one held reply; the client skips
  replies with a stale txid and honours its deadline.
* `devmgr`: one claimant per device, `Busy` otherwise, release on connection close and at manager exit, reset before the
  manager's DMA handle closes (T42), the DMA VMO exists only while claimed, handles are closed when a claim reply cannot
  be sent. D1 to D4 are not weakened by the diff.
* `netsup` keeps the secret for the boot and gives every `netd` the same one, so the ISN contract of 5.10 and 5.11 holds
  across stack restarts.
