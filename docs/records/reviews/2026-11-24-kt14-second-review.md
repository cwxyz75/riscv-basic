# KT14: the second review of the `unsafe` blocks that changed since the first audit (2026-11-24)

The first audit (`2026-11-23-kt14-unsafe-audit.md`) covered 162 blocks. By 2026-11-24, 167 blocks stood in `kernel/src`, and 46 of them had a hash the first audit did not contain: changed or new since, each recorded by its author in `kt14-unsafe-audit.tsv` but not read by anyone else. (The docs check passes on a hash match, so it cannot tell a reviewed row from a self-recorded one.) Three fresh-context reviewers, each given one third by area (kmem, console, heap, thread statics, kstack, dtb; the riscv64 arch blocks; the user-state and entry-frame blocks and the AArch64 stubs), read every block, traced its callers and judged the `// SAFETY:` condition against the code. They ran nothing.

**Result.** 41 ok, 3 weak, 2 bug before the fixes below; after them 44 ok and 2 weak (`kstack.rs` `Deref`, `calls.rs` `general_of`, both named in the TSV with their item). No memory-safety path from user mode.

- **Bug, fixed:** `console.rs` `write_str` and `write_user`. The comment said breaking the UART lock cannot alias `LINE`; it can: the panic path breaks the lock without stopping the other harts, so a hart inside `with_uart` and a hart that then took the freed lock both held `&mut LINE`. Effect: a garbled line state while the machine is dying (plain data, no corruption path). Fix: `break_lock` sets `BROKEN`, and every later `Console` write returns before touching `LINE`; the panicking hart writes through `PanicConsole`.
- **Weak, fixed:** the debug guard against a nested `&mut UserState` was set by `with_state` only; `locked_state` and `any_state`'s unlocked branch did not set it, so a nested open through them was not caught. `locked_state` sets it now (`StateOpen`), and the comment on `state()` says which entries are guarded. The `Sync` impl of the AS-lock scratch now says an `AsLocks` never escapes its closure.
- **Found by the widened guard, fixed (three real nestings):** with the guard on `locked_state`, the kernel-only boot panicked three times in turn, each a second `&mut UserState` opened under a live one: (1) `take_interrupt_held`, the callback `ksys`'s `channel_call_send_staged` and `channel_call_reply_deferred` call while holding fields of the state; it now takes the two fields it needs (`ksys::set_interrupt_in`) and opens nothing; (2) `debug_stat_call` holds the state and delegated the backstop counters (120 to 124) to `wake_stat`, which opened it again; they are read from the held state now; (3) `fp::write_fp` and `write_vec` (from `thread_state_call`, state held) charged the job through `job_of_thread`, which opened it again; the caller passes the job. None corrupted anything (each touched different fields), which is why nothing failed before. After the three, the four-hart kernel-only boot passes (305 tests, one run).
- **Comments corrected:** the `kmem` guard structs' "every use is `kmem::get().field`" (copy-pasted, and `get()`'s clause about the kernel address space was not true of it); `snapshot_kernel_half` names the thread-table lock that orders the store before the first reader; `sbi5` says the soundness is that every caller passes its own ids; the FP `state()` says the lock check is debug-only; "`c` at its fcsr" in the FP load.
- **The audit file:** six of the seven `fp.rs` rows carried the condition text of a neighbouring block (the verdicts were right); each now describes its own block. The rows of the blocks whose comments changed took their new hashes.
- **Stays weak, filed:** `T253` (the kernel-stack slice, the firmware window fallback in `aia.rs reg()`, the public fields of the `kmem` guards, a hard check of the FP lock, and four things the reviewers did not trace); `T241` keeps the `general_of` race.

**What the reviewers could not verify:** that thread ids are never reused (`light_save` relies on it); that the trap-exit assembly restores `sstatus.FS` and `VS` from the frame; the hardware behaviour of whole-register vector loads and stores while `vill` is set; whether `cow_sync_held` is ever reached with an `AsLocks` live. They are in T253.
