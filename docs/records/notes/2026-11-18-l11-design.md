# L11 design note: per-hart run queues under `RQ` locks (2026-11-18)

A working note, not a spec. It reads SCHED-SMP-SPEC task 11 (sections 3.2, 3.3, 3.9, 4.1, 4.4, 7.1) against the code as it is today
and proposes how to cut the work into steps that each leave the system green. It changes no code. Items that I did not check in the
code are marked *unchecked*. Work items: L11 (this), L12 (the rest of the first peel, blocked by L11), T107 and T108 (the stand-ins
this removes). Plan 3 left L11 and L12 unstarted for the reasons in `WORK-PLAN.md`; this note is what a session needs to start.

## 1. Where the code is

- `kcore::sched_smp::Sched2<N>` is **one value**: `Vec<HartRq<N>>` plus shared state: `loc: BTreeMap<Tid, usize>` (which hart holds a
  thread's record), `next_tid`, `pending[h]` and `pokes` (the owed IPIs), `online[h]`, `transit[h]` (the thread a hart has queued but
  not finished switching away from) and counters. Every operation is `&mut self` and may read or change any hart's queues: `pull`
  (moves a record from hart `g` to `h`), `push_marks` (reads every hart's `cur_eff`), `settle` (a hart makes its own designation right),
  `balance`, `wake_on` (may migrate).
- The kernel holds it as `SCHED: klock::Spin<Option<KSched>>` of class `Rq` (`kernel/src/thread.rs`): one lock for all harts, taken for
  one call at a time, with interrupts off. The **big kernel lock** (`bkl`) is still held across context switches and "follows the
  thread"; `transit` stands in for the spec's `finish_switch` (T108 (4)).
- The timer tick (`timer_tick_fast`) and the reschedule IPI (`reschedule_fast`) already run without the BKL, under `SCHED` only
  (task 12 step one). So `SCHED` is the lock every hart's tick contends on: this is the contention L11 removes.
- `klock` already has class `Rq` with "two, ascending hart index" (`Class::allows_two`) and the order checker; nothing uses two yet.
- Idle is `idle_main`: `wfi` in a loop with interrupts on, no `RQ` check before it (the lost-wake window of spec 3.9 is covered today
  by the pending IPI, not by the protocol). Exited detached threads go to a `zombies` list and a reaper thread (`reaper_main`).
- Models that exist: `kcore/tests/sched_smp_model.rs`, `sched2_smp_model.rs`, `sched2_differential.rs`, `sched2_kernel_walk.rs`,
  `idle_concurrency.rs` (shuttle), `tick_starvation.rs`, `park_concurrency.rs`. GP1 and GP2 are `Sched2::audit`.

## 2. What the spec's task 11 asks for, split by independence

| Deliverable | Needs the others? | Risk |
|---|---|---|
| A. `Sched2`'s cross-hart operations written over `&mut [HartRq]` (spec 4.1: "the same two-hart functions") | no | low: pure, the models stay valid |
| B. shared state made per-hart or atomic: `pending`/`pokes` into each hart's record, `online`, `transit`, counters | A | low to medium |
| C. `loc` and `next_tid` without a global lock | A | medium: lookup/migrate race |
| D. `[Spin<HartRq>; MAX_HARTS]`: the real per-hart `RQ` locks, taken inside the BKL | A, B, C | **high**: first real concurrency in the scheduler |
| E. `need_resched` (X7): a wake sets a flag, the switch happens at the defined points | D | medium |
| F. `finish_switch`, the dead list and reap by the hart | D | medium: changes who frees a stack |
| G. the idle loop of 3.9 and the starvation watchdog | D | medium; the watchdog is a debug detector |
| H. the negative-control kernels `fault-skip-poke`, `fault-early-reap`, `fault-skip-pull` | with D, F | low |

Spec 7.1 puts `finish_switch` and the dead list in task 11 and "the lock is released at a switch (G4)" in task 12. I read that as: in
L11 the BKL still follows the thread across a switch (as now), and `finish_switch` is the *per-hart `RQ` lock hand-over* that the new
locks need, replacing `transit`. L12 then lets go of the BKL at the switch.

## 3. The real design problems (what D to F must decide)

1. **Finding a thread's home hart without a lock.** A waker holds no `RQ` lock and must lock the hart that holds the record, which
   `pull` can change at any moment. Proposal (the spec's `TT` class 9): the thread table maps `Tid` to a record whose `home` is an
   atomic; a waker reads `home`, locks `RQ[home]`, re-reads, and retries if it moved. `loc` then disappears from `Sched2`. This is the one
   place a lock-ordering mistake is easy: `TT` (9) before `RQ` (10) means the waker must drop `TT` before it locks the `RQ`, or hold
   `TT` across it, which the table allows; decide which, and write it into INVARIANTS.
2. **Lock-free hints for placement.** `select_hart`, `push_marks` and `pull` read every hart's running priority and best queued priority.
   With one lock each, these must be per-hart atomics, `cur_eff[h]` and `queued_top[h]`, written under `RQ[h]` and read without it;
   every decision made from them is **re-checked under the locks** before it is acted on (a stale read costs a wasted poke or a missed
   pull that the next tick repeats, never a wrong move). GP1 is stated at quiescence for exactly this reason.
3. **`transit`.** Today a global list protects "queued but still executing" threads from a pull. With per-hart locks, a thread being
   switched away from is protected by being *inside the outgoing hart's `RQ` lock until the resumed thread's `finish_switch`*
   (spec X3). Under the BKL-follows-thread rule of L11 the incoming thread can run that hand-over, but the outgoing hart's `RQ` lock
   must then be released by a different thread than the one that took it: `klock::Spin` has to allow that for class `Rq` only
   (the checker's per-hart record needs a "released by the successor" operation), or `transit` stays a per-thread atomic flag for L11
   and moves to the lock in L12. **I recommend the second**: smaller, and T108 (4) already names it as the later step.
4. **Two-lock operations.** Only `pull` and a migrating wake hold two `RQ` locks, ascending. Everything else (`settle`, `tick`,
   `wake` to the same hart, `block`, `yield`, `exit`) holds one. `balance` (T107 (3)) reads other harts' lengths: atomics again.
5. **The IPI debt.** "Whoever turns `resched_pending[h]` from clear to set owes exactly one IPI" becomes a `compare_exchange` on a
   per-hart atomic, with the IPI sent after the `RQ` lock is dropped. Today's `pokes` bitmask under the one lock does the same; B is
   a mechanical move, and `fault-skip-poke` (mark without IPI) is its negative control.
6. **Allocation under `RQ`** (X8): `HartRq` queues are `BTreeMap`s and `Vec`s today, so a wake allocates. The spec allows this
   transitionally (`HEAP` is class 13, after `RQ`); keep it, and list it in T107 (5).
7. **8 harts, 32 in the pure code.** `percpu::MAX_HARTS` is 8, `sched_smp::MAX_HARTS` is 32 (the poke set is a `u32`). Per-hart arrays
   use 8 in the kernel; the pure crate keeps 32.

## 4. Proposed steps (each its own PR; D onward with a Fable review and the `soak` label)

1. **L11a (pure, A+B+C in `kcore`)**: re-express `Sched2` as `HartRq`s plus an explicit `Shared` of atomics (`home`, `pending`, `online`,
   `cur_eff`, `queued_top`, counters), still called as one `&mut` value by the kernel. No kernel change but the types. Acceptance:
   every existing model passes unchanged; a new differential test runs the old `Sched2` and the new one on the same random walk
   (`sched2_differential.rs` pattern) and compares every observable; one hand mutation per atomic hint (stale `cur_eff`, stale `home`)
   is caught by GP1/GP2 or by the differential.
2. **L11b (D, kernel)**: `[Spin<HartRq>; 8]` of class `Rq`; `SCHED` goes away. Lock sequences as in section 3, `transit` stays a per-thread
   atomic. Acceptance: GP1 and GP2 on 1 to 8 harts against the independent reference, with the audit taking every lock ascending; a loom/
   shuttle model of wake-against-pull-against-tick over the real `klock::Spin` (extend `sched_smp_model` and `idle_concurrency`); the whole
   suite at `-smp 1`, `2`, `4`; the soak targets; `bkl_profile` shows the tick still takes no BKL. Negative controls: `fault-skip-pull`,
   and a kernel that takes two `RQ` locks descending (the checker must stop it).
3. **L11c (E+F)**: `need_resched`, and the dead list drained by the hart that switched away (the reaper thread stays as the fallback
   until the dead list has run a soak). Negative control `fault-early-reap` (free the stack before the switch completes): the stack
   guard check and the canary must catch it.
4. **L11d (G)**: the idle loop of 3.9 (lock, check queues and `resched_pending`, publish idle, unlock, `wfi`) with the model of task 4
   updated, and the debug starvation watchdog. `rt_threads_take_the_harts` as the QEMU acceptance.

Rough size from the spec's own table: 900 lines of code and 800 of tests across the four; I would plan on the first two PRs being the
larger and the riskiest being L11b.

## 5. What would make this go wrong, and what to watch

- **Lock order against the BKL.** `RQ` is inside the BKL for L11; the tick and IPI paths take `RQ` without it. A path that takes the
  BKL while holding `RQ` is a deadlock; the checker catches it only on the paths a test runs, so L11b needs a test that drives every
  entry (block, wake, yield, exit, spawn, set_priority, tick, IPI, kill) at `-smp 4` with the checker's panic on.
- **The lookup/migrate race** (3.1) is the likeliest source of a lost wake; it wants the shuttle model first, before the kernel change.
- **Cost.** T108 (4): a wake takes the scheduler lock three times today. Per-hart locks make each of them cheaper but not fewer; do not
  expect the benchmark to move until L12. Measure with `os-bench` before and after and record it; a regression above the noise is a
  reason to stop, not to tune.
- **CI time.** The `smp` soak job hit its 40-minute cap on PR 238 on a slow runner day; L11b adds work to it. Raise the job's cap or split
  it before L11b, not after.

## 6. Decisions I would like from the owner before L11b (none blocks L11a)

1. Is the **per-thread `transit` flag in L11 and the lock hand-over in L12** (section 3, item 3) acceptable, or should the hand-over
   come with the per-hart locks? (It changes `klock`'s API either way; the first is smaller.)
2. **Where `home` lives**: in the thread table record (spec `TT`, which does not exist yet as a lock) or in the scheduler's own
   thread map under a short-lived lock of class `Rq`-adjacent? The first matches the spec and makes L19/L20 easier; the second is
   less code now.
3. May L11a land **before** L11b is designed in more detail? It is pure and reversible, and it makes everything after it smaller.
