# Review: L12 step one, the scheduler core behind its own lock (`SCHED`, class `RQ`), branch `l12-sched`

Date: 2026-11-16. Reviewer: Fable (fresh context, independent of the author). Scope: the working tree of the worktree
against `origin/main` (the slice is uncommitted): `kcore/src/sched_smp.rs` (transit), `kernel/src/thread.rs`,
`kernel/src/trap.rs`, `kernel/src/bkl.rs`, `kernel/src/percpu.rs`, `kernel/src/heap.rs`, the test changes
(`kcore/tests/sched2_kernel_walk.rs`, `sched2_smp_model.rs`, `kernel/src/smp_tests.rs`, `user_tests.rs`) and the
documents (INVARIANTS TR1, TIDY-UP T108, ROADMAP task 12). Read against SCHED-SMP-SPEC 3.2, 3.3, 3.5, 3.7, 3.9, 4.4
and `reviews/2026-11-16-l11b-scheduler.md`.

Method: reading, plus scratch programs outside the repository (`/private/tmp/l12review`; no source file in the worktree
was changed):

* `tests/transit.rs`: a hand-written scenario against the worktree's `kcore` (finding 1; its output is quoted there);
* `tests/walk.rs`: a random walk over `Sched2` that keeps, per hart, **the thread the hart is really executing** (the
  kernel's `percpu.running`) and checks TR1's premise after every operation: if that thread is no longer designated
  and is `Runnable`, it must be `transit[h]`. 2 to 4 harts, 300 seeds each, 2000 steps;
* a copy of `abi/` and `kcore/` with a candidate fix for finding 1 and one mutation (balance ignoring transit), run
  against the scratch walk and the repository's `sched2_kernel_walk.rs` and `sched2_smp_model.rs`.

**Nothing was booted in QEMU for this review.** The kernel findings are from the code; the pure-core finding is
reproduced on the host.

Summary: the lock structure is sound (no path takes the big lock while holding `SCHED`, no guard is held across a call
that takes `SCHED` again, every path that can change `cur[h]` under the big lock still ends in `reschedule()`, and the
pokes cannot be lost by the new split into several lock holds). **The transit rule has a hole**: one `tick_on` (and one
`yield_on`) can record transit twice, and the second record overwrites the thread that is really still executing. On
the tick's kernel-mode fast path that thread is then unprotected by both TR1 and the big lock: the double dispatch the
slice set out to remove is still reachable. The model tests cannot see it because they do not know which thread a
hart is executing.

Blocker: 1. Important: 2, 3. Minor: 4 to 9.

## Blocker

### 1. A tick that displaces the running thread and then pulls loses the transit record: double dispatch (blocker)

`kcore/src/sched_smp.rs:514-522` (`tick_on`), `293-321` (`settle`, the note at `315-317`), `202-208`
(`note_transit`); `kernel/src/thread.rs:533-549` (`timer_tick_fast`), `kernel/src/trap.rs:350-355`.

`transit[h]` is one slot and `note_transit` overwrites it. `tick_on` notes twice: once after `tick_to` (with the
thread that ran at entry) and once more at the end of `settle` (with `entry_cur`, the thread designated when `settle`
began). If `tick_to` already changed the designation (slice end with an equal peer queued, or a timer-woken thread
that outranks the running one) **and** `settle` then changes it again (its `pull` brings a better thread from another
hart), the second note replaces the executing thread by the intermediate one, which never ran.

Step by step (scratch `tests/transit.rs`, three harts, `FixedPrio`; ids from the run):

1. Hart 0 runs A (priority 10, free); B (10, pinned to hart 0) is queued there. Hart 1 runs C (20, free).
2. Hart 1 spawns X (30, pinned to 1): C is preempted, queued on hart 1, `transit[1] = C`. Hart 1 completes its
   switch: `switched(1)` releases C and marks hart 0 (`pending0=true pokes=0b1`).
3. Hart 0's **timer tick** runs before it serves that IPI (it was already in its trap, spinning for `SCHED` while
   hart 1 held it). `tick_on(0)`: `tick_to` ends A's slice, A is queued, `cur[0] = B`, `transit[0] = A`. Then
   `settle(0)`: `entry_cur = B`; `pull` takes C from hart 1; B is preempted, `cur[0] = C`; `note_transit(0, B)` sets
   `transit[0] = B`. Output: `cur0=5 (a=4 b=6 c=5) transit0=Some(6) stateA=Some(Runnable) homeA=Some(0)`.
4. A is now queued on hart 0, `Runnable`, **not in transit**, and hart 0 is still executing it: `timer_tick_fast`
   returned true and the hart is spinning for the big lock (interrupts off, on A's stack), or is inside
   `reschedule()` before `context_switch` has saved A.
5. Any other hart may take A: `push_queue(0)` at the end of the same `settle` already offers it (A is the best
   non-transit thread on hart 0's queue), and pull and balance no longer skip it. In the scratch run hart 2 does
   `reschedule_on(2)` and gets `cur2=4` (= A) with hart 0's `switched` not yet called.
6. In the kernel hart 2 (idle, IPI in kernel mode) does `reschedule_fast()` → true → `bkl::lock()` →
   `reschedule()`. Hart 0 and hart 2 now race for the big lock. If hart 2 wins, it loads A's **old** saved context
   (`kernel/src/thread.rs:461, 483`) while hart 0 is still running on A's stack. For a thread that has never been
   switched out that context is the trampoline, so the thread starts twice (the `a thread start was registered`
   failure named in the TR1 row); for any other thread it resumes inside an old `reschedule()` frame on a stack in
   use: silent corruption.

The scratch walk shows this is not a corner: the premise fails in **714 of 900 walks** (first failure per walk: 500
after a tick, 214 after a yield, none after a wake, spawn, priority change or `reschedule_on`, which note once).

Reach in the kernel today: the thread must be displaced by a tick or IPI that interrupted **kernel** code without the
big lock, and be free to migrate. That is every `spawn_free` kernel thread running with interrupts on: the SMP
self-tests' free threads (`smp_tests.rs`, the churn test), and user threads in their kernel-mode stretches with
interrupts on (`user.rs:403-409`, the first statements of `user_thread_main` — the place where the earlier double
dispatch showed — and `leave` after `user.rs:451`). Ticks from user mode and every operation under the big lock are
still safe, because the big lock is held from the displacement until `context_switch` has saved the thread and no
hart can switch without it. So the window is narrow now, and becomes the common path with the next peel named in
T108 (user-mode ticks, `thread_yield`): `yield_on` has the same double note (`sched_smp.rs:471-479`: after
`yield_now`, then in `settle`). The same overwrite also happens in multi-operation regions under the big lock
(`wake_many`, `set_priorities`, `exit`'s `wake_all_on`: a second `settle` on the same hart before `reschedule()`),
harmless only while the big lock covers the switch.

Why the tests pass: both walks call `finish(h)` before every operation on `h` and compare only against `Sched2`'s own
`transit` field (`audit`: "the transit thread is queued on its hart", which holds for B too). Neither keeps the
executing thread, so "the wrong thread is in transit" is invisible. The hand test
`a_thread_switched_away_is_not_available_...` has no second designation change.

Suggested fix (checked in the scratch copy: the scratch walk then passes 900 of 900, `transit.rs` passes, and the
repository's `sched2_kernel_walk.rs` and `sched2_smp_model.rs` still pass): the first displaced thread wins until
`switched(h)`. In `note_transit`, return early if `transit[h]` already names a thread that is still `Runnable` and not
`cur[h]`. Better, because it does not depend on call order: let `Sched2` keep `executing[h]` (set to `cur[h]` by
`switched(h)`, by `adopt_*` and at join) and define "in transit" as `executing[h] != cur[h] && state == Runnable`, with
no stored slot to overwrite; that form also covers a Blocked or Exited thread when G4 releases the big lock at the
switch. Then: add the executing-thread reference to both walks (the check in `tests/walk.rs` is ten lines), add the
mutation "transit overwritten by a later note" to the TR1 row, and add a kernel-side detector so a double dispatch is
a structured panic instead of corruption: an `on_cpu` flag per `KThread`, set when it is switched to, cleared for the
previous thread in `finish_switch`, asserted clear on the incoming thread in `reschedule()` just before
`context_switch` (all under the big lock today).

## Important

### 2. The spin watchdog's counter for `klock` locks is never reset: a false "deadlock" panic in long debug runs (important)

`kernel/src/bkl.rs:239-244` (`Machine::relax`), `206-219` (`spin_watchdog`), `kernel/src/percpu.rs:80`.

`relax` loads `percpu.spins`, adds one, stores it back. Nothing sets it to zero when the lock is acquired (the only
reset is inside the panic branch). It is therefore the **total** number of spin iterations this hart has ever made on
`SCHED` and the heap lock together, not "this long for one lock" as the comment and the panic text say. At 30 million
it panics. Every tick of every hart and every scheduler call takes `SCHED`, and every allocation takes the heap lock,
so a debug-build boot at `-smp 4` accumulates steadily; a long run (the soak targets, `smp_churn_stress`, the
thread-hog and ten-thousand-thread tests) can reach the limit with no deadlock anywhere. The failure would read `hart N
has spun for a spin lock ... for 30 million iterations` and point the reader at a deadlock that does not exist.

(The big lock's own counter, `bkl.rs:146`, is a local per wait and is right. Its bound, 30 million iterations, is
host-time dependent: a holder's vCPU descheduled by a loaded host while the waiter spins at full speed could trip it;
lower risk, same remedy below.)

Suggested fix: zero `percpu.spins` in `Machine::acquired` (`klock::Spin::lock` calls it before it starts spinning,
`klock/src/lib.rs:238`) or count in a local the way `bkl::lock` does. Consider bounding by time (`timer::now()`, for
example two seconds) instead of iterations, and print through the structured `##PANIC` path. A test: take and release
a contended `Spin` more than 30 million relax-iterations in total and expect no panic (or unit-test the counter reset
on the host with a fake `Machine`).

### 3. The models and the QEMU suite do not cover what this slice changed (important)

* **No executing-thread reference** in `sched2_kernel_walk.rs` and `sched2_smp_model.rs` (finding 1). TR1's listed
  mutations ("pull ignoring transit", "transit never recorded") do not include the one that is actually present.
* **`idle_concurrency.rs` is unchanged** and still models every hart as "operation and `take_pokes` in one lock hold,
  under one mutex". The kernel now (a) splits a big-lock path into several `SCHED` holds (`wake`: `wake_on`, then
  `reschedule()` takes the pokes in a second hold, then `finish_switch` a third), (b) lets a fast-path hart take
  **another hart's** pokes in between and send them, dropping its own bit (`send_pokes`, `thread.rs:495-496`), and
  (c) has a tick as a second way to serve a mark. I went through the interleavings by hand and found no loss (see
  "checked and found fine"), but ID1's row in INVARIANTS still cites a model that has none of these three, and the
  argument rests on an ordering inside `timer_tick_fast`/`reschedule_fast` (settle first, then take) that nothing pins.
  A negative control "take the pokes before the settle" should lose a wake in the model.
* **No negative-control kernel for TR1.** INVARIANTS says the QEMU suite shows a double dispatch as `a thread start
  was registered`. That is true only for a thread that has never been switched out; otherwise it is corruption with
  no defined symptom. There is no `fault-skip-transit` build that proves the suite can see the bug at all, and no
  test that produces the trigger of finding 1 on purpose (free kernel threads of equal priority spinning with
  interrupts on on two harts, a sleeper timing out on one of them, a third hart idle).
* `idle_harts_take_no_big_lock_for_their_ticks` measures only an **idle** hart 1. The other half of the claim (a
  kernel thread that runs through its ticks takes no big lock unless it must switch, and still switches promptly when
  it must) has no check; a regression that made the fast path always return false would pass this test and show only
  as slowness elsewhere.
* Transit under other operations is exercised only incidentally by the walks. Missing as named cases: a thread in
  transit that is woken (must stay queued, park word only), has its priority changed by another hart (must stay homed,
  its hart marked), whose process is killed; `switched(h)` when the transit thread is `cur[h]` again; `switched(h)`
  on a hart that goes offline semantics (not possible today; say so).

Suggested fix: the reference and mutation of finding 1; extend the shuttle model with the split holds, the tick and
the stolen poke plus the negative control; a `fault-skip-transit` kernel with the stress test above in the soak tier;
a `bkl_takes` check for a spinning kernel thread; the named transit cases as short hand tests next to the existing one.

## Minor

### 4. A fast path that returns "no switch" never calls `switched` (minor, hardening)

`kernel/src/thread.rs:518-527, 533-549`. `finish_switch` runs only inside `reschedule()` and `thread_bootstrap`. When
`reschedule_fast`/`timer_tick_fast` return false, nothing clears `transit[h]`. Today I could not construct a case
where a transit is recorded and `cur[h]` equals the running thread again within one fast-path operation (it needs the
designation to return to a lower thread, which neither `advance` nor `settle` does with `FixedPrio`), so this is not a
live bug. It is one line from one: a stale slot hides a queued thread from every other hart until this hart's next
`reschedule()`, which may be never on an idle hart. Suggested fix: in both fast paths, when the result is false, call
`sc.switched(h)` in the same hold (or `debug_assert!(sc.in_transit(h).is_none())`). With the `executing[h]` form of
finding 1 the question disappears.

### 5. The relaxed IPI expectation in `a_wake_preempts_a_lower_priority_hart` hides up to a third of the wakes (minor)

`kernel/src/smp_tests.rs:331-335`. The explanation (the secondary's tick, already waiting for `SCHED`, serves the mark
and takes its own poke bit, so no IPI is sent) is consistent with the code. But `ipis >= TRIALS * 2 / 3` now also
accepts four genuinely lost IPIs in twelve. Suggested fix: count the self-served marks (a per-hart counter where
`send_pokes` drops the caller's own bit on the fast paths) and assert `ipis + self_served >= TRIALS`.

### 6. Three `SCHED` round trips for every wake, not one extra per switch (minor, cost; T108 understates it)

`kernel/src/thread.rs:427-442`. `reschedule()` on its no-switch path takes `SCHED` to read the designation and again
in `finish_switch`; with the operation itself that is three acquisitions of a lock shared by all harts for each
`wake`, `spawn` and `set_priority`, and `wake_many` takes two per thread. T108 (4) says "one extra scheduler lock round
trip per switch". Suggested fix: do `switched(h)` in the same hold that reads `current_on(h)` when `next == running`
(one hold instead of two), and correct T108.

### 7. `wake_many`'s wake counter reads the state in one hold and wakes in the next (minor, statistics only)

`kernel/src/thread.rs:785-788`. A fast-path tick on the thread's home hart can fire its timer between the two holds;
`WAKES` then counts a wake that did not count. Use `wake_counted_on` in one hold.

### 8. The kernel-mode IPI switch path has no heap safe point; the tick's has (minor, inconsistency)

`kernel/src/trap.rs:392-397` against `350-355`. Not a regression (the old IPI path had none either), but now that a
kernel-mode tick that does not switch never reaches `heap::service`, the remaining safe points matter more: a hart
running one kernel thread for a long time with interrupts on reaches one only when it switches or makes a call under
the big lock. Allocation under `SCHED` in the tick is transient (records move between maps), so I see no exhaustion
path; add `heap::service()` to the IPI path for symmetry, and state in K6 which paths are safe points now.

### 9. Documents not brought in line with the peel (minor; G1 asks for it)

* `INVARIANTS.md` K1 (line 130) still says the scheduler state is asserted under the big lock; the scheduler core is
  now under `SCHED` and only `thread::kernel()` (the thread table, the waiter queues, zombies) is. Line 117 and
  `kernel/src/bkl.rs:3-5`, `kernel/src/trap.rs:323-325` still say every trap takes the big lock. K5 lists the real
  locks as BKL, HEAP, UART; `RQ` is now one of them. Spec G1: "each peel names the state it moves in INVARIANTS".
* `kernel/src/trap.rs:337` cites TIDY-UP T107; the entry is T108.
* The TR1 row and T108 should say that TR1 presently relies on the big lock for every displacement made under it
  (multi-operation regions overwrite the slot), until finding 1 is fixed.
* `ROADMAP.md` task 12 quotes "160 times for 80 ticks before, 0 now"; the test accepts up to 4. Not verified here.

## Checked and found fine

* **Every other way a still-executing thread is left reachable.** Block, sleep, exit and reap: made only under the big
  lock, which the hart keeps (K3 hand-over) until `context_switch` has saved the thread, and every wake, reap and
  switch on another hart needs that lock. Timer expiry without the big lock (`tick_to` on the fast path) fires only
  timers in the hart's own queue, for threads homed there; a thread that is blocked but still executing is homed on
  the hart executing it, which has interrupts off. Preempt by wake, spawn, `set_priority` (one `settle`, one note):
  recorded correctly, and under the big lock anyway. A new thread: `spawn_on` and the insert into the thread table are
  in one big-lock region, and the hart that designates it needs the big lock to switch. `reschedule_on` (IPI fast
  path): one note, correct. Balance and pull skip transit threads (the mutation "balance ignoring transit" is caught
  by `sched2_kernel_walk.rs`). The idle thread is never queued, so it needs no transit.
* **`finish_switch` coverage.** `context_switch` has one call site; the resumed thread calls `finish_switch` right
  after it, a new thread in `thread_bootstrap` before it releases the big lock, and the no-switch exit of
  `reschedule()` calls it. Every `pub` function of `thread.rs` that can change `cur[h]` or set a mark ends in
  `reschedule()` in the same interrupts-off region; both fast paths that return true go straight to `bkl::lock()`,
  `switch_if_designated()`. `cur[h]` is changed only by hart `h` (no remote `resched`), so the designation cannot
  move while the hart spins for the big lock.
* **Pokes.** Fast paths settle and take the pokes in one hold, so their own marks are never left behind. A big-lock
  path's marks can be taken by a fast-path hart between its holds; that hart sends them, and drops only its own bit,
  after its own `settle` in the same hold has served the mark. `finish_switch` and the top of `reschedule()` run only
  under the big lock, so they cannot take a big-lock path's pokes from between its holds. `switched` marks at most
  one other hart and its pokes are taken in the same hold.
* **Lock order and deadlock.** No path takes the big lock while holding `SCHED`: every guard is a block-scoped
  binding or a statement temporary; the `if sched()...{ reschedule() }` forms drop the guard before the body (an `if`
  condition is a temporary scope; the `match` in `join` was the one that was not, and is fixed). `exit`, `wait_until`,
  `wake_one`, `wake_all`, `join` hold the guard only across `Waiters2` calls and a `Vec` push (heap, class 13, after
  `RQ`). `klock::Spin` turns interrupts off before the order check and the wait, and restores after release;
  `irq::without` outside it is the right nesting. A holder of `SCHED` never waits for the big lock, and a holder of
  the heap lock never takes `SCHED`. The heap and the console take their locks with interrupts off, so a fast-path
  tick cannot interrupt a holder. `join_scheduler` and `init`: sound (a hart is marked only after `set_online`, has
  interrupts off until it has set `running` and `in_sched`, and ends with a reschedule).
* **`percpu.running`.** Written only by its own hart with interrupts off (`init`, `join_scheduler`, `reschedule`);
  every read is with interrupts off on the same hart (`current()`, the fast paths, `exit`, `join`,
  `current_stack_top`). No reader on another hart.
* **FP and the kill check.** `fp::trap_entry` returns at once for a kernel-mode frame, and the old kernel-mode path
  did not call `activate_current` either, so skipping both on the fast path changes nothing. The user-mode tick and
  IPI paths keep the old order (big lock, `fp::trap_entry`, scheduler work, `activate_current`). A tick cannot
  interrupt a syscall handler or any big-lock region (interrupts are off whenever the big lock is held), so the
  interrupted kernel code never holds the big lock and the outermost take in the fast path is depth 1, handed over by
  `swap_depth` as before.
* `wake_stat(16..=23)` indexes `HARTS[0..8]` (`MAX_HARTS = 8`): in bounds for any argument a user passes to
  `DEBUG_STAT`.
