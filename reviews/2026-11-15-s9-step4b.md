# Review: S9 step 4b (TCP streams in `netd`), branch `s9-step4b`

Date: 2026-11-15. Reviewer: independent pass, fresh context. Scope: `git diff origin/main...s9-step4b`
(`init/src/bin/netd.rs`, `netcore/src/tcp.rs`, `nettcp` peek/consume, `proto/src/net.rs`, `rt/src/net.rs`), read against
S9-SPEC sections 4, 5.8, 5.9, 6, 7.2, 8, `SYSCALLS.md` (ports, sockets, `object_info`) and `rt/src/service.rs`, `svc`.

**Method and limits:** code reading only. Nothing was built, booted or run by this review (no host tests, no QEMU); no
source file was changed. Every finding below is from the code as written; none has a reproducing test yet. Line numbers
are of the branch tip.

Severity summary: 3 High, 4 Medium, 6 Low. Recommendation: fix 1, 2 and 3 before merge (each breaks a stated spec
rule: 5.9, 8.5/N18, 5.8); 4 to 7 before step 5 (the C library and `httpd` sit on them).

## High

### 1. A posted accept whose half-open connection dies is lost for good: 16 SYN+RST pairs kill a listener (remote DoS)

Where: `netcore/src/tcp.rs:514-566` (the SYN pops the accept), `:694-698` (a half-open passive connection that fails
emits nothing), `:442-450` (`tcp_remove` emits only `Released`); `init/src/bin/netd.rs:1322-1341` (`Released` looks in
`streams`, which a posted stream is not in until `Accepted`); `rt/src/net.rs:499-521` (re-posts only on `ACCEPTED`).

Evidence: a SYN takes `(cookie, cfg)` with `posted.pop_front()`. If the connection never reaches ESTABLISHED (the
SYN-ACK goes unanswered for 7 s, or the peer sends RST in SYN-RECEIVED), `tcp_collect` maps the `Reset` to `None`
("the listener never knew it"), removes the entry and pushes `Released{conn}`. The accept is never put back
(`push_front` exists only on the `MAX_CONNS` path). In `netd` the stream stays `Phase::Posted` forever: its entry in
`accepts`, its 32 KiB reservation, its connection slot, its `held_socks` entry and both kernel objects stay until the
client closes a channel it has no reason to close, because nothing is sent on either channel. `rt::net::Listener`
believes the accept is still posted.

S9-SPEC 5.9 says the opposite: "A half-open connection whose SYN-ACK goes unanswered **frees its accept** after 7 s",
and that a SYN flood "denies that listener" only while it lasts. As built, any remote host that can reach the port
sends 16 SYNs (each followed by a RST, or just left alone for 7 s) and the listener accepts nothing ever again; the
dead posted streams also hold the account's whole `stream_bytes` (16 x 32 KiB = 512 KiB), so re-posting fails with
`Quota` even if the library tried.

Fix: in `netcore`, when an entry with `from = Some((lid, cookie))` and `!established` is removed, push the accept back
on the listener's `posted` queue (keep its `TcpConfig` in the `Entry`), if the listener still exists. Add a host test
in `netcore/tests/tcp.rs` (SYN, then RST; SYN, then 7 s of silence; then a second SYN must be accepted by the same
cookie) and a QEMU case in `net_stream_quotas_and_bad_handles`.

### 2. `PeerFin` is sent when the FIN arrives, not when the data before it has been delivered: a stack crash (or a closed channel) after it turns a truncated stream into a clean end-of-file (N18, S9-SPEC 8.5 and 5.8)

Where: `init/src/bin/netd.rs:1288-1295` (`TcpEvent::PeerFin` sends the notice at once); `netcore/src/tcp.rs:689-693`
(the event is raised when the FIN is in order, with bytes possibly still in R); `rt/src/net.rs:672-690`
(`end_of_stream`: `peer_fin` is tested before `chan_closed`).

Evidence: S9-SPEC 5.8: "when everything before it has been written into the client's socket the stack sends the notice
`PeerFin` ... and **then** shuts down its socket end". The code sends `PEER_FIN` as soon as the peer's FIN is received.
With a slow reader the socket buffer B is full (64 KiB) and R still holds up to `rcv_buf` more. In that window:

- `netd` dies (any crash; `FAULT=crash-on-magic` does it on purpose). Its socket ends close; the client reads the
  64 KiB in B, then `PEER_CLOSED`, runs `end_of_stream`, finds `peer_fin == true`, `reset == None` and returns `Ok(0)`.
  Up to 64 KiB of the stream is missing and the read reported a clean end. This is exactly the case 8.5 exists to
  prevent ("a stack crash ... never as a short but successful download").
- The same result without a crash when the later `RESET` notice cannot be delivered: `Core::send` closes the
  connection if a reply is already held (`svc/src/conns.rs:116`, `hold` refuses a second one) or the account's
  `held_bytes` is spent; the client then sees `peer_fin` and a closed channel and, because `peer_fin` is checked first,
  reports a clean end.

Fix: send `PEER_FIN` from the two places that shut the socket down, immediately before `socket_shutdown`
(`pump_stream` at `:1478` when `tcp_eof(id)` turns true, and the `Released` handler at `:1327`); keep `fin_seen` as
the internal flag. Then the notice cannot precede undelivered data. In `rt::net`, also treat "channel closed" as a
reset unless the socket's end-of-stream came from a shutdown the stack performed after `PEER_FIN` (with the netd fix,
the present order of tests becomes correct). Test: a negative control that kills `netd` (or injects a reset) while a
client sits on a full socket after the peer's FIN; the read must fail with `CONN_RESET`.

### 3. Closing a stream with bytes still in its socket sends a clean FIN after dropping them (silent truncation for the peer)

Where: `init/src/bin/netd.rs:1160-1184` (`stream_closed`, the `for _ in 0..4` loop); TIDY-UP T97 (3).

Evidence: on channel close `netd` reads at most `min(tcp_send_space, 16 KiB)` four times, then calls `tcp_release`
(which queues the FIN) and closes its socket end. The loop stops as soon as S is full, and S is 16 KiB by default while
the kernel socket holds up to 64 KiB. A program that writes a 100 KiB response and exits (`write_all` returns once the
socket took the bytes; `Drop for Stream` closes both handles) loses whatever is still in A: typically 48 to 64 KiB.
The peer receives a shorter stream ended by an ordinary FIN. S9-SPEC 5.8 defines the orphan as the connection that
"keeps draining" data "still in A or S"; T97 (3) records "more are lost" at severity M but does not say that the loss
is followed by a clean FIN, which is the N18 failure seen from the remote side. Step 5's `httpd` will hit this on any
response larger than S.

Fix (either): (a) keep the socket end in an orphan record and keep running the send half of `pump_stream` for it until
`socket_read` reports `PEER_CLOSED`, then `tcp_shutdown_write` and release (the handle is `netd`'s own, and buffered
bytes stay readable after the client's end closes); or (b) at minimum, if `socket_read` still has bytes when the loop
gives up, `tcp_abort` instead of `tcp_release` so the peer sees a reset, not a short success. Test: write 200 KiB,
drop the stream at once, the loopback peer must read 200 KiB or get a reset, never a short clean end.

## Medium

### 4. `rt::net::Listener` ignores a refused `Accept`, and with the default backlog every re-post is refused

Where: `rt/src/net.rs:499-521` (`accept`: `Some(EpEvent::Notice { .. }) => continue`, `let _ = self.post(0, 0)`),
`:458-497` (`post` records the accept before the stack has answered); `init/src/bin/netd.rs:1090-1113` (refusal is a
`CONNECT_FAILED` notice on the listener's channel carrying the cookie).

Evidence: a refused `Accept` (Quota, BadHandle) is reported by cookie on the listener channel; the library skips every
`Notice`, so the `(cookie, channel, socket)` it pushed in `post` stays in `posted` (two handles leaked per refusal, and
a backlog entry that is not really posted). With T97 (1) the reservation is made at post time: `listen_stream(port,
16, ..)` reserves 16 x 32 KiB = 512 KiB, the whole account. After the first `ACCEPTED`, the accepted connection keeps
its 32 KiB, so the re-post in `accept` needs a 17th reservation and is refused; nothing retries it later. Each accepted
connection therefore shrinks the live backlog by one, and after 16 the listener is dead although the program holds a
`Listener` with 16 "posted" entries. (`net_tests.rs:1585` uses a backlog of 16; worth checking that the test does more
than 16 accepts against it.)

Fix: on `CONNECT_FAILED` for a cookie in `posted`, remove the entry and close its handles; keep a count of accepts
owed and re-post them on later `accept` calls and on `ACCEPT_STARVED`; cap the default backlog so that backlog plus
live connections fits the account (or resolve T97 (1) so a posted accept reserves nothing).

### 5. The orphan limit is one global table of 32: one client can reset every other client's draining connections

Where: `netcore/src/tcp.rs:412-440` (`tcp_release`: more than `ORPHAN_MAX` orphans in the whole core resets the
oldest); `init/src/bin/netd.rs:1160-1180`.

Evidence: S9-SPEC 6.3 keeps an orphan charged to its account while the account lives and uses the 32-entry pool only
for orphans whose account is gone. As built the account always outlives the orphan (`Accounts::close` refuses while
`stream != 0`), yet the cap of 32 is applied to all orphans together. A program with two service connections can keep
32 fresh orphans alive at all times through loopback (connect to its own listener, never read on the accepting side so
the window closes, write, close the connecting stream; 8 KiB minimum reservation each) and renew them faster than
others arrive. Any other program's "write and exit" connection then becomes the oldest orphan and is reset. The victim
loses data it had been told was written (the peer does see a reset).

Fix: count orphans per account (for example at most 8, charged as now) and apply the global 32 only to orphans whose
owning service connection is gone, evicting the offender's own oldest first.

### 6. A program is not bounded by `stream_bytes`: every service connection is a fresh account, so eight of them take the whole 4 MiB pool

Where: `init/src/bin/netd.rs:1571-1600` (each forwarded `Open` on a published name opens a new account with
`STREAM_BYTES_PER_ACCOUNT`), `:1705-1710` (pool 4 MiB), `:1100-1107` (a posted accept reserves without any peer).

Evidence: the account is per service connection, not per program or job. Nothing seen in this diff stops a program
that has `/svc/net` in its view from opening it eight times; each account can then post 16 default accepts (no remote
party needed) and the pool's `stream_bytes` is gone. Every other client's `Connect` and `Accept` then fails with
`Quota` for as long as the program lives. The connection-count pool had the same shape in S8 (32 of 256 per account),
but streams are the first resource where the per-account share is one eighth of the pool and can be held with no
traffic. If the launcher or the registry already limits opens of a name per job, say so in NET-SPEC 7.4 and this drops
to Low; I did not find such a limit.

Fix: nest the accounts (the `svc::Accounts` tree already supports it): one parent account per client job or per
registry-forwarded identity carrying the 512 KiB limit, service connections as children; or lower the per-account
share until T97 (1) is resolved.

### 7. Closing a posted stream whose accept a SYN has already taken releases the reservation while the half-open connection lives on

Where: `init/src/bin/netd.rs:1149-1158` (`Phase::Posted`: the result of `tcp_cancel_accept` is ignored);
`netcore/src/tcp.rs:394-401`.

Evidence: between the SYN and the final ACK the accept is no longer in `posted`, but `netd` still thinks the stream is
`Posted`. If its channel closes in that window, `tcp_cancel_accept` returns `false`, the reservation is released and
the socket closed, while the SYN-RECEIVED connection keeps its buffers in the core for up to 7 s (or until the
handshake completes and the `Accepted` handler aborts it, `:1240-1243`). That is memory in `netd` reserved by nobody,
which 6.2 forbids ("the sum of reservations never exceeds the pool"). A client can repeat it as fast as SYNs arrive
(its own over loopback, or a helper's), up to the core's `MAX_CONNS` of 512, which also makes every other client's
`Connect` fail with `TooMany`.

Fix: make `tcp_cancel_accept` also remove a not-yet-established connection whose `from` is `(listener, cookie)` (the
same sweep `tcp_close_listener` does), so `Released` and the reservation end together.

## Low

### 8. The stream pump is a window of 32 over all table entries, not over ready streams

Where: `init/src/bin/netd.rs:1409-1423`, `:1425-1522`.

- A socket event sets `more`, but the next pass serves the next 32 keys in round-robin order, which need not include
  the stream that fired. With more than 32 streams and nothing else moving, a ready stream waits for the 10 ms safety
  poll once per window (up to about 80 ms at 256 streams). No wake-up is lost: every pass calls `socket_read` whatever
  `rd_armed` says, and `next_deadline` never exceeds 10 ms, so I found no permanent stall in the one-shot logic
  (`port_rearm` is level-checked per `SYSCALLS.md`; the stale-`rd_armed` race resolves when the queued event is
  dequeued). The price is that the one-shot bindings are not what drives the work.
- `streams.values()` includes connecting streams, orphans and streams whose channel has closed; they take window
  slots and do nothing.
- Each `pump_stream` zero-fills two 16 KiB stack buffers before it knows there is anything to move (`:1437`, `:1493`),
  on every pass, for every stream in the window: about 1 MiB of memset per pass at 32 streams, 100 passes a second
  when idle, more when one busy stream keeps `more` set. Under TCG this is measurable.

Fix: keep a ready set (keys whose binding fired, plus streams with bytes in R or a due retry) and serve from it; peek
the length before filling a buffer (`tcp_readable`, and a zero-length-safe check on the socket's signals).

### 9. Socket bindings are never unbound

Where: `init/src/bin/netd.rs:1202-1214` (`stream_over`), `:1147-1186` (`stream_closed`).

A binding disappears only when its object is destroyed (`SYSCALLS.md`, Ports). A client that keeps a duplicate of the
socket end it passed keeps the object alive after `netd` closes its handle, so both bindings (32 bytes each of
`netd`'s queued-data quota) stay on `netd`'s port until the client lets go. Bounded by the client's own object quota
and lifetime, and the stale one-shot bindings fire at most once each (`other_event` finds no connection; keys are
never reused, so nothing is misdirected). Fix: `port_unbind` both keys wherever the socket handle is closed.

### 10. A second notice while one is held closes the stream's (or listener's) channel

Where: `rt/src/service.rs:277-292`, `svc/src/conns.rs:116`; callers `netd.rs:839-843` (`notice`), `:1259-1270`.

`Core::send` holds one reply per connection and closes the connection on a second. A stream can receive `CONNECTED`,
`PEER_FIN` and `RESET` with no request in between, and a listener a burst of `ACCEPTED`; a client at its IPC quota
loses the channel. For a stream that is the safe direction once finding 2 is fixed (closed channel means reset); for a
listener it ends the listener. Worth one sentence in S9-SPEC 8.4 and a test.

### 11. Wrong reasons reported

- `Abort` on a connecting stream is reported as `CONNECT_FAILED` with `CONN_REFUSED` (`netcore/src/tcp.rs:705`,
  `Reason::Aborted => FailReason::Refused`).
- `ClearConfig` marks streams `lost`, but only the `Reset` arm reads the flag (`netd.rs:1300`); a stream still
  connecting gets `CONN_REFUSED` rather than a link-lost status.
- A second `Connect` on a stream answers with a `CONNECT_FAILED` notice (`netd.rs:1002`), which `rt::net` and a C
  library will read as the failure of the connection that is in fact established or in progress.

### 12. `tcp_connect` takes any destination

Where: `netcore/src/tcp.rs:292-351`, `netd.rs:985-1038`. Destination `0.0.0.0`, `255.255.255.255`, the subnet
broadcast, multicast and port 0 are accepted and reserved for; they then fail by ARP or SYN timeout (up to 15 s). No
broadcast frame leaves (there is no broadcast MAC mapping in `route`), so this is not a way round the `BROADCAST`
privilege. Refuse them at `Connect` with `NO_ROUTE` or `BAD_REQUEST` (RFC 1122 4.2.3.10).

### 13. Listener address is not checked and ports are first come, first served

Where: `netd.rs:938-964`, `netcore/src/tcp.rs:237-253`. `local_addr` may be an address that is not ours (the listener
then never matches); a listener on a port excludes every other listener on it whatever the address. Any unprivileged
client can occupy any port from 1024 up. By design as far as 7.4 goes; recorded so that it is a decision.

## Checked and found sound

- **Handle admission** (`admit_socket`, `:854-891`): a channel or any non-socket fails the zero-length read/write
  probe; a socket without READ, WRITE or WAIT fails; a held socket, a duplicate of one (same koid) and the peer of one
  are refused in both directions; a socket whose own end was shut down fails the write probe. A duplicate kept by the
  client only lets the client read or inject its own stream. The scratch port is closed on every path.
- **`held_socks`**: `forget_socket` is reached on every exit I could find (Connect: quota, connect error; Accept:
  quota, `add_conn` failure, `tcp_post_accept` failure through `stream_closed`; `stream_over`; `stream_closed` in every
  phase). Koids are never reused, so a stale koid cannot alias.
- **Charges**: each `charge_stream` has exactly one release. Connect: inline on error, else `charged` and `Released`.
  Accept: inline on `add_conn` failure, `stream_closed(Posted)` otherwise, or moved to `charged` at `Accepted`
  (`mem::take` prevents a double release). `Released` is pushed by `tcp_remove` only, once, and every removal goes
  through it. Account ids cannot be recycled under a live charge (`close` refuses while `stream != 0`). Exceptions are
  findings 1 (over-held) and 7 (under-held).
- **Keys**: connection keys are never reused (`svc/src/conns.rs:64`), `ConnId`/`ListenerId` share a counter that only
  grows, so stale entries in `streams`, `accepts` and stale binding keys cannot reach another client's stream.
- **Decoders** (`proto/src/net.rs`): `decode_ep_request` and the `CONN_INFO` arm check lengths before indexing and
  exact sizes for the new ops; padding is checked. Total.
- **`netcore` deferred removal**: `closed_pending` entries are removed when read out, or by `abort` (which always
  raises `Reset`, also in `Closed`) when the owner goes; TIME-WAIT conversion waits for R to empty unless orphaned; I
  found no entry that can stay in the table without an owner. `Closed` precedes `Released` on every path.
- **Bounded memory in `netd`**: `accepts`, `held_socks`, `charged`, `streams` are bounded by connections; the loopback
  queue (32), TIME-WAIT (64) and events per poll are bounded. `Abort` repeated in one batch yields duplicate `RESET`
  notices (at most `BATCH`), harmless.
- **No blocking call** on a client-controlled object: every socket and channel call is non-blocking; quota refusals
  go to a retry timer capped at 500 ms.
